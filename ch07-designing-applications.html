    Hotel Application Design · Cassandra and Microservice Architecture

    從資料模型到應用程式：微服務三原則

    Data model 只決定 table 的形狀，真正讀寫它們的是應用程式。本章選擇 microservice 風格來設計這個應用程式，這一節先看它的三項原則，以及每一項對資料庫的用法意味著什麼。

    要回答的問題Hotel Application Design

    前面幾章依序談了 Cassandra 如何表示資料、如何建立 data model，以及叢集架構如何把資料分散開來，同時維持快速、可靠的存取。第 7 章要把這些知識放進真實的應用程式設計。

    場景回到第 5 章的 hotel domain。假設你被要求開發一個應用程式，使用你已經建好的 Cassandra data model，涵蓋 hotel、房間可用性（room availability）與 reservation。

    書中接著問：怎麼從 data model 走到應用程式？Data model 不會獨立存在，一定有軟體負責對你設計的那些 table 做寫入與讀取。可行的架構很多，本章只談 microservice 這一種架構風格。

    Cassandra 與微服務架構Cassandra and Microservice Architecture

    作者的論點有兩層。第一，近幾年 microservice 風格已經是 cloud-native 應用程式的基礎。第二，Cassandra 是從頭為雲端設計的資料庫，因此很適合 cloud-native 應用程式。這是作者在本章開頭的定位陳述，書中沒有在這裡進一步論證。

    作者也說明不打算完整討論微服務的好處（並推薦 Sam Newman 的 Building Microservices，O'Reilly），只引用其中原則的一個子集。這個子集就是下表的三項。

    原則書中怎麼說對資料庫用法的含意
    Encapsulation
    封裝    		服務專注做好一件事（single responsibility principle）。不直接存取別的應用程式的資料庫；對外提供介面，例如 RPC 或 messaging。
    Autonomy
    自主性    		每個 microservice 都能獨立部署，不依賴其他 microservice。可以不停機、逐步推出新版本；每個服務可以有自己的 data store（polyglot persistence）。
    Scalability
    擴充性    		依需求動態增減某個服務的 instance 數量。應用程式的不同部分各自擴充；hotel 與 inventory 相關服務預期比 reservation 相關服務擴得更多。

    封裝：資料庫不當整合點Encapsulation

    書中把 encapsulation 換成另一種說法：服務只專注做好一件事，也就是 single responsibility principle。

    對照組是許多企業的現況：資料庫就是中央整合點（central integration point）。應用程式也許對外開了 RPC 或 messaging 介面，但一個應用程式直接存取另一個應用程式的資料庫也很常見。書中明講這違反 encapsulation，並且在應用程式之間產生難以隔離、難以除錯的依賴。Figure 7-1 就是這組對照，下面的互動版把它重畫出來。

    對 Cassandra 的用法來說，結論很直接：一組 table 應該有一個擁有它的服務，其他程式改走那個服務對外的介面取得資料（這是依封裝原則的讀法，書中此處沒有逐字這樣寫）。本章後面把這個想法寫成「服務擁有特定的 table」，並在 部署一節 建議每個服務使用自己的 keyspace，再用存取控制（第 14 章）讓服務只能讀寫自己的 keyspace。

    機制說明

    為什麼直接讀 table 的依賴在 Cassandra 上特別具體？第 5 章的 query-first 設計是先決定 query，再讓 table 圍繞 query 組織；hotel schema 裡每個 table 的 comment 也標明它服務哪一條 query（例如 hotel.available_rooms_by_hotel_date 是 Q4）。所以一個 table 的 partition key 與 clustering column，本身就是某個 access pattern 的形狀。另一個應用程式若直接查詢它，就把自己的 query 綁在這個形狀上。

    第 4 章的 “Primary keys are forever” 寫明 table 建好之後無法修改 primary key。由此可推，要改變存取路徑時，做法是新建 table 再遷移資料（這一步是推論，書中沒有在這裡寫）。如果讀取方散在 owner 看不到的地方，每一個讀取方的 query 都得跟著改。

    自主性：獨立部署，各自選 data storeAutonomy

    Autonomy 指每個 microservice 都能獨立部署，不依賴其他任何 microservice。書中列出的好處是：可以獨立演進已部署應用程式的某一塊、不需要停機，並且能逐步推出服務的新版本，把每次部署的風險降到最低。Cassandra 這一側的配置（每個服務對應的 keyspace、共用或獨立的 cluster、多個 data center），見 部署一節。

    第二個含意落在資料層：每個 microservice 可以有自己的 data store，並且選最適合該服務的技術，這就是 polyglot persistence。Designing Microservice Persistence 一節會逐一檢視 hotel 應用程式的各個服務（Table 7-1），並承認 Cassandra 不一定是每個服務的理想選擇。

    擴充性：依流量調整每個服務的 instance 數Scalability

    Microservice 讓你依需求動態地多跑或少跑某個服務的 instance，所以應用程式的不同部分可以各自擴充。

    書中的例子取自 hotel domain：shopping（找房間的流量）與 booking（客人真的下訂、形成 reservation 的流量）之間差距很大，後者低得多。因此作者預期，與 hotel 和 inventory 資料相關的服務，要擴充到比儲存 reservation 的服務更高的程度。

    書中這一段只談服務 instance 的數量，沒有給任何流量數字，也沒有談 Cassandra 這一層如何縮放。資料層與服務的對應（共用或獨立的 cluster，視各服務的 workload 而定）留到 部署一節。

    Microservice Architecture for a Hotel Application

    從資料模型推出 microservices

    第 5 章只決定了 tables。要把它們變成應用程式，還得決定每張 table 由哪個 service 擁有。書中讓這個決定跟著 data modeling 的三個階段，一步步收斂出來。

    要為 hotel application 設計 microservice 架構，書中說要先找出三樣東西：services、它們的 interfaces，以及 services 之間如何互動。

    書中借用 Eric Evans 的 Domain-Driven Design 來做這件事。這本書成書時 microservices 還不流行，作者仍認為它是有用的參考。取用的是它的一條核心原則：先有 domain model，再從中找出 bounded contexts。書中說，這套流程已是辨識 microservices 時被廣泛推薦的做法。

    本節沒有展開 DDD 的其他概念，「bounded context」的用法也很窄：一群相關 entities 的分組。後面的步驟都建立在這個定義上。

    書中重點：與 data modeling 的三階段對照
    • Conceptual data modeling：辨識 entities 的同時，辨識 bounded contexts，也就是相關 entities 的分組。
    • Logical data modeling：把 bounded contexts 細化成 services。每個 service 負責一張 table，或一組相關的 denormalized tables。
    • 設計流程的最後階段：確認每個 service 的設計、選定 database，並完成 physical data models 與實際的 database schema。

    辨識 bounded contextsIdentifying Bounded Contexts

    先重用第 5 章的 conceptual data model。它的 conceptual domain 包含 hotels、rooms（及其 rates、availability 與 amenities）、points of interest、guests 和 reservations。書中把它們分成兩群：

    • Hotel Domain：hotels、它們的 rooms 與 availability 資訊。
    • Reservation Domain：reservations 與 guests。

    書中描述 Hotel Domain 時沒有提到 points of interest，但下一步它拆出的 services 包含 points of interest，所以 POI 資料也在這個 context 裡。書中還指出，這兩個 context 剛好對應初始資料模型的兩個 keyspace：hotel 與 reservation。

    書中重點：keyspace 與 context 的重合

    第 5 章把 tables 放進兩個 keyspace，理由是讓設計保持簡單，並說真實系統可能分到更多 keyspace 來分離關注點。本節用 “happen to” 描述兩者重合，沒有把「一個 bounded context 等於一個 keyspace」當成規則。

    書中的歸屬原則

    1. 設計可以有很多種，但一個好的通則是：對應度高的 tables 歸同一個 service。
    2. 用 Cassandra 時，自然的做法是把代表同一種基本資料型別的 denormalized tables 放進同一個 service。
    3. services 要符合 object-oriented 設計的 coupling 與 cohesion 原則：同一個 service 擁有的 tables 之間要有高 cohesion（高度相關），不同 context 之間要有低 coupling（低相依）。
    機制說明

    原則 2 背後是 denormalization 的成本。Cassandra 沒有 joins，也不維護 tables 之間的 referential integrity，所以要讓查詢快，就得把同一份資料依不同 key 各存一份（見第 5 章 No joins、No referential integrity、Denormalization 三段）。第 5 章也先假設這些副本由應用程式自己手動維護，並預告第 7 章後面會回頭看 materialized view。副本若分屬兩個 services，就是兩個 services 共同維護同一份事實。放進同一個 service，維護責任只有一處。

    Designing Microservice Persistence

    服務的持久層：選資料庫，並在 CQL 裡表達其他資料模型

    資料建模的最後一步是 physical model。放到架構上，它就是替每個 service 決定用哪種資料庫、schema 長什麼樣。

    資料建模的最後一個階段是建立 physical data model（物理資料模型）。對應到架構這一側，這就是設計 service 的工作，其中和資料庫有關的決定有兩項：選哪一種資料庫，以及建立 schema。

    上一節已經把 logical model 的表分給五個 service：Hotel、Point of Interest、Inventory（Figure 7-4），以及 Reservation、Guest（Figure 7-5）。這一節先逐個 service 看資料庫怎麼選，再看 Cassandra 當資料庫時，怎麼在 CQL 裡做出 key-value、document、graph 三種模型的樣子。

    每個 service 各選資料庫Polyglot persistence

    microservice 架構的好處之一，是每個 service 都能獨立部署（independently deployable）。這讓你可以替每個 service 選不同的資料庫，這種做法叫 polyglot persistence。

    作者在一本 Cassandra 的書裡直接寫明：Cassandra 不一定是每個 microservice 的理想 backing store，尤其是那些用不到 Cassandra 擴充能力（scalability）的 service。

    需求變多時：再加一張表，還是加 index

    非 primary key 欄位不能直接查Secondary Indexes

    hotels 表以 id 為 primary key。直接用 hotel 的名稱查詢，會得到錯誤：

    cqlsh:hotel> SELECT * FROM hotels
WHERE name = 'Super Hotel Suites at WestWorld';
    InvalidRequest: Error from server: code=2200 [Invalid query] message="Cannot execute this query as it might involve data filtering and thus may have unpredictable performance. If you want to execute this query despite the performance unpredictability, use ALLOW FILTERING"

    錯誤訊息的意思是 Cassandra 預設不允許這種查詢；如果你接受效能不可預期，可以加上 ALLOW FILTERING 強制執行。書中接著說明強制執行的實際含義：name 欄位上沒有任何 index，Cassandra 必須請叢集裡所有節點掃描所有儲存的 SSTable 檔案，找出名稱符合的 hotel。在較大或負載較重的叢集上，這會造成 query timeout，也會增加各節點的處理負載。

    第 9 章在 Range Queries, Ordering and Filtering 一節對 ALLOW FILTERING 的結論相同：不建議使用，因為可能產生非常昂貴的查詢；真的需要這類查詢時，應該回頭檢查 data model，看是否該有一張支援它的表。

    不想多建一張以 name 為 primary key 的表時，另一個辦法是替 name 欄位建 secondary index。Secondary index 就是建在「不屬於 primary key 的欄位」上的 index。

    建立、命名與查詢

    cqlsh:hotel> CREATE INDEX ON hotels ( name );

    index 可以選擇性地取名，語法是 CREATE INDEX <name> ON…。沒有指定名稱時，cqlsh 依 <table name>_<column name>_idx 的格式自動命名。剛建的 index 叫什麼，可以用 DESCRIBE KEYSPACE 查：

    cqlsh:hotel> DESCRIBE KEYSPACE;
...
CREATE INDEX hotels_name_idx ON hotel.hotels (name);

    機制 書中說名稱由 cqlsh 自動產生。實際上，語句沒有指定名稱時，預設名稱是由 Cassandra server 在處理這個語句時產生的，不是 cqlsh client 端。

    有了 index，原本被拒絕的查詢就能照常執行，語句中不需要 ALLOW FILTERING：

    cqlsh:hotel> SELECT id, name FROM hotels
WHERE name = 'Super Hotel Suites at WestWorld';

    Secondary index 的陷阱Secondary Index Pitfalls

    Cassandra 把資料分散在多個節點上，所以每個節點都得就自己擁有的 partition 資料，維護屬於自己的那一份 secondary index。因此用到 secondary index 的查詢通常會涉及更多節點，成本明顯更高。

    書中列出三種不建議使用的情況：

    高 cardinality

    幾乎每列都不同的欄位

    例：hotel.address。絕大多數地址都是唯一的，書說對它建 index 可能非常昂貴。

    極低 cardinality

    只有少數幾種值的欄位

    例：第 4 章 user 表的 user.title。用它查出每一個 “Mrs.” 沒有意義，因為 index 裡會出現一條 massive row。

    頻繁更新或刪除

    會留下大量 tombstone 的欄位

    建在這類欄位上的 index，若被刪除資料（tombstone）累積的速度快過 compaction 能處理的速度，可能產生錯誤。

    tombstone 是刪除時留下的標記，要等它比 gc_grace_seconds 還老、並經過 compaction 才會被清除，見第 6 章 Deletion and Tombstones。

    書中結論

    要得到最佳的讀取效能，通常優先選擇 denormalized table 設計或 materialized view（下一節）。Secondary index 的價值，在於支援初始 data model 沒有考慮到的查詢。

    SASI：另一種 secondary index 實作SASI: A New Secondary Index Implementation

    Cassandra 3.4 引入了一個實驗性的 secondary index 替代實作，稱為 SSTable Attached Secondary Index（SASI）。SASI 由 Apple 開發，並以開源方式釋出，是 Cassandra secondary index API 的一個實作。

    名稱已經點出它和原本實作的差異：SASI 的 index 是在每個 SSTable 檔案內計算並儲存；原本的實作則把 index 放在獨立的 “hidden” 表裡。SASI 與傳統的 secondary index 並存，用 CREATE CUSTOM INDEX 建立：

    cqlsh:my_keyspace> CREATE CUSTOM INDEX hotel_name_sasi_idx
ON hotels (name)
USING 'org.apache.cassandra.index.sasi.SASIIndex'
WITH OPTIONS= {'mode': 'CONTAINS'};

    書中沒有解釋 OPTIONS 裡的 mode，只在這個例子裡用了 'CONTAINS'。

    SASI 提供傳統實作沒有的功能：可以對 index 欄位做不等號（大於、小於）搜尋，也可以用 CQL 的 LIKE 做文字搜尋。書中的例子是找出名稱含有子字串 “world” 的 hotel，並說明這個比對不分大小寫：

    cqlsh:hotel> SELECT id, name FROM hotels
WHERE name LIKE '%world%';
     id    | name
-------+---------------------------------
 AZ123 | Super Hotel Suites at WestWorld
(1 rows)
    書出版後 · 已查證

    「不分大小寫」和書中的 index 定義對不上。SASI 文件（doc/SASI.md，4.0 分支）裡，被稱為 case-insensitive 的 index 另外設了 'analyzer_class': 'org.apache.cassandra.index.sasi.analyzer.NonTokenizingAnalyzer' 與 'case_sensitive': 'false'；4.0 原始碼裡 case_sensitive 的預設值是 true。書中的 hotel_name_sasi_idx 只設了 'mode': 'CONTAINS'。

    照這個定義，LIKE '%world%' 很可能比對不到 “WestWorld”，要加上那兩個 option 才會得到書中的輸出。這是讀文件與原始碼得到的推論，沒有實際跑過，使用前請在自己的版本上測。

    效能方面，書說 SASI 比傳統 index 好，因為省去了讀取額外表的步驟；但和 denormalized 設計相比，它仍然需要從更多節點讀取。本章後段談實驗性功能時，SASI 也被列為實驗性功能之一。

    書出版後 · 已查證

    5.0 多了一種索引，SASI 仍是 experimental。本書以 Cassandra 4.0 為準，以下是查證日 2026-10-10的現況。

    • SAI（Storage-Attached Indexing，CEP-7）隨 5.0 釋出。5.0 文件稱它是多數使用情境下最合適的索引方式，並建議新建索引改用 SAI，不再用傳統 secondary index。

    • SASI 預設停用：enable_sasi_indexes: false（4.0），4.1 起改名 sasi_indexes_enabled。cassandra.yaml 的註解寫明它是 experimental、不建議用於 production。在預設設定的 4.0 以上叢集，書中的 CREATE CUSTOM INDEX … SASIIndex 要先開這個設定才能執行。

    Extending Designs · Materialized Views
    
    
    Materialized View：把 denormalization 交給 Cassandra 維護
    
    
    Secondary index 在高 cardinality column 上要動用 ring 裡大多數節點；materialized view 改成預先存好支援該查詢的 view，並由 Cassandra 負責和 base table 同步。這一節看語法規則、3.0 的限制，以及 Reservation 設計為什麼把 reservations_by_confirmation 做成 view。
    
  
    

  
    為什麼需要 materialized viewMaterialized Views
    
  
    
    
    前一節的 secondary index 有個結構性的弱點：每個節點只為自己擁有的 partition 維護 index，所以用 index 查詢會牽涉更多節點。對高 cardinality 的 column 尤其明顯，書中的說法是 ring 裡大多數甚至全部節點都會被查詢。Materialized view 就是為了補這個缺口而加入的：把支援查詢的 view 預先存好。
    
    
    每個 view 支援的查詢，條件是一個不屬於 base table 原本 primary key 的 column。後面的 3.0 限制和 MV 產生器都從這句話來。
    
    
    對 application 的好處是不必自己維持多張 denormalized table 同步，Cassandra 負責讓 view 和 base table 保持一致。代價落在 base table 的寫入：維持一致性需要做一些讀取，寫入因此變慢。書中的比較對象是「由 application client 自己管理 denormalized table」，MV 的效率比那樣好。View 的更新在內部以 batching 實作，書中把細節留給 Chapter 9（寫入成本一節整理了書中幾處相關的說法）。
    
  
    
  
    
    
    
      
    做法誰維持一致性書中對查詢與寫入的描述
    
      
        
    Secondary indexCassandra（每個節點為自己擁有的 partition 維護一份 index）查詢涉及更多節點；高 cardinality column 上效能差
    
        
    Materialized viewCassandra預先存好支援查詢的 view；base table 的寫入需要一些讀取
    
        
    手動管理的 denormalized tablesapplication（client）要自己讓多張 table 同步；書中說效率不如 MV
    
          
    
    
  
    
  
    
    機制說明
    
    View 在物理上是另一張 table，有自己的 partition key。所以用 confirm_number 查詢時，查詢條件就是 view 的 partition key，這是 single-partition read，不必像 secondary index 那樣向 ring 上多數節點詢問。
    
    
    超出本章文字：書中只說 MV 解決了這個問題，沒有展開原因，這段是補充的機制說明。書中其他章節只旁證「view 是一張 table」：第 13 章稱之為 materialized view tables（nodetool proxyhistograms 輸出的 View Write Latency 欄位說明）；第 6 章說 view 的建構由 system.view_builds_in_progress 與 system.built_views 追蹤，建好的 view 列在 system_schema.views。「有自己的 partition key」與 single-partition read 兩點，書中沒有直接寫。

    部署：keyspace、cluster 與 data center
    
    
    動手實作之前，有兩類部署決定要先想：service、keyspace 與 cluster 如何對應，以及 service 部署在哪些 data center。
    
  
    

  
    
    
    書中指出，進入實作階段後，有幾個與部署和整合有關的因素要考慮：這個 service 要怎麼部署，以及怎麼與其他 service 和支援的基礎設施整合。以下兩個考量都和 Cassandra 的設定直接相關。
    
  
    

  
    Service、keyspace 與 clusterServices, Keyspaces, and Clusters
    

  
    Keyspace：每個 service 一個
    
  
    
    
    經驗法則是每個 service 使用一個 keyspace，以促進封裝（encapsulation）。第 14 章介紹的 access control 可以為每個 keyspace 建立一個資料庫 user，讓每個 service 容易設定成對自己 keyspace 內的所有 table 擁有專屬的讀寫權限。
    
  
    
  
    CREATE USER reservation_service WITH PASSWORD '<password>';
GRANT SELECT ON KEYSPACE reservation TO reservation_service;
GRANT MODIFY ON KEYSPACE reservation TO reservation_service;
    
  
    示意（語法依第 14 章）：為 Reservation Service 建立專屬 user 並授權。密碼以占位符代替；第 14 章在 cqlsh 內以 cassandra 這類 superuser 身分執行這些語句。
    
  
    
    書中補充（第 14 章）
    
      
      
    • Cassandra 預設的 authorizer 是 AllowAllAuthorizer，授權所有 client 存取所有 keyspace 和 table。要啟用以 role 為基礎的存取控制，要在 cassandra.yaml 把 authorizer 改成 CassandraAuthorizer，並重啟叢集。
      • 
      
    • 這兩條 GRANT 讓該帳號能讀寫 reservation keyspace，但不能做其他操作。想收得更窄，可以改用 SELECT ON TABLE、MODIFY ON TABLE 限定到單一 table。

    Java driver 4.x 預設的 load balancing policy 要求指定 local data center，query plan 只會包含該 data center 的 node。舊版 driver 的 DCAwareRoundRobinPolicy 會在 local 的 node 之後再納入 remote 的 node，4.x 不再這樣做；書中的理由是，local data center 的所有 replica 都掛了時，多半是整個 data center 層級的故障，把流量轉到其他 node 在實務上有難以除錯的副作用。
    
  
    
  
    
    機制說明

    另外，本機沒有該 cluster 的 node，4.x 預設 policy 就沒有可選的 node。這是由上面第 8 章的文字推得的結果；書中在本節給的理由是「最快的存取速度」。

    Interactions Between Microservices
    
    
    跨 microservice 的資料一致性
    
    
    每個 microservice 嚴格擁有自己的資料，分屬不同 service 的資料之間，一致性關係由誰維持？書中給了兩種整合 pattern，並列出三種處理錯誤情境的技術，同時明說詳細的錯誤處理不在本章範圍。
    
  
    

  
    問題：嚴格的資料所有權之下Consistency across services
    

  
    
    
    本章前面建議一個 service 對應一個 keyspace，讓每個 service 對自己的資料有獨佔的讀寫權。接下來的問題是：兩個 service 各自擁有的資料型別之間有一致性關係時，這個關係要靠什麼維持？
    
    
    書中先講清楚兩件事：
    
    
      
      
    • Cassandra 沒有機制可以強制跨 table 或跨 keyspace 邊界的 transaction。
      • 
      
    • 這個問題並非 Cassandra 獨有。只要不同 service 管理的資料型別之間需要一致性，不論背後是哪一種 store，都會遇到同樣的設計挑戰。
      • 
    
    
    
    書中拿旅館應用當例子：inventory 與 reservation 由不同的 service 管理，客人訂房時，要怎麼確保 inventory 記錄被正確更新？依本章前面的切法，Reservation Service 擁有 reservation keyspace 的 table，inventory availability 屬於 Hotel Domain，由 Inventory Service 擁有，並有自己的 keyspace（本章一個 service 一個 keyspace；keyspace 名稱只出現在 Figure 7-8，原圖未取得）。即使兩個 service 共用同一個 cluster（Figure 7-11 的情境），keyspace 的邊界仍然在。
    
  
    

  
    
    機制說明
    
    書中那句話的依據，可以從其他章節拼出來：
    
    
      
      
    • LWT 的範圍是單一 partition。Cassandra 的 lightweight transaction 以 Paxos 為基礎，Paxos 狀態是每個 partition 各存一份（見第 6 章、第 9 章）。batch 在書中的定位也不是 transaction 機制（見第 9 章）。
      • 
      
    • 沒有跨 table 的參照完整性。書中明說 Cassandra 沒有 referential integrity 的概念（見第 5 章側欄「No Referential Integrity」）。
      • 
      
    • 推論：reservation 與 inventory 在不同的 table，資料一定落在不同的 partition，LWT 的範圍涵蓋不到。LWT 可以保護單邊：書中提到它常用來管理 inventory 數量，做 check-and-set（見第 9 章、第 15 章）。但它保護的是 inventory 自己的值，不會把 inventory 的更新和 reservation 的寫入綁成一個單位。
      • 
    
    
  
    


  
    
    書出版後 · 已查證
    
    「沒有跨 table 的 transaction」在目前的正式版仍然成立。查證日 2026-10-10，最新 GA 是 5.0 系列（5.0.9），4.0、4.1、5.0 都沒有跨 partition 的 transaction。
    
    
      
      
    • General-purpose transactions（Accord，CEP-15）列在 6.0-alpha1 的變更記錄裡。6.0 目前只有 alpha 版（alpha1 於 2026-04、alpha2 於 2026-08），官方說明只供開發與測試。

    • trunk 文件描述的語法是 BEGIN TRANSACTION … COMMIT TRANSACTION，可以跨多個 partition 與 table，需要啟用 accord 並替 table 設定 transactional_mode。是否能跨 keyspace，文件沒有寫，這次無法確認。trunk 文件在正式版之前可能再變。
      • 
      
    • 即使 6.0 正式釋出，它處理的是同一個 Cassandra 叢集內的資料。本節的問題是「兩個 service 各自擁有資料」，如果兩邊不共用叢集、或其中一邊不是 Cassandra，下面兩種 pattern 與三種技術仍然是要面對的設計題。這一點是推論，不是查證結果。

    兩種整合 patternService integration patterns
    

  
    
    
    書中列出兩種常見做法（Figure 7-13）。
    
  
    

  
    
    
    
      
    Orchestration圖左
    
      
    多加一個 Booking Service，由它協調 reservation 與 inventory 兩邊資料的變更。
    
      
    這類做法常見於把 service 分成兩種的架構：CRUD service 負責單一資料型別的 create、read、update、delete；另一種 service 實作 business process。

    Choreography圖右
    
      
    用 message queue 或 streaming platform（例如 Apache Kafka）產生資料變更事件的 stream，讓其他 service 與 application 非同步消費。
    
      
    例如 Inventory Service 可以訂閱 Reservation Service 發布的 reservation 事件，據以調整 inventory。

      choreography 的變體
      
      CDC 作為事件來源
      
      
      做法事件的來源改成資料庫的 change data capture（CDC），不再依賴 service 先可靠地把資料存進資料庫、再自己發出事件。
      
      
      書中說適合通常用來保證 application 之間介面上高度一致的互動；也可以用在個別 service 之間。
      
      
      書中的界線本章沒有說明 CDC 怎麼運作；Cassandra 的 CDC 在第 15 章。
      
    
      
  
      

  
      
    機制說明
    
      技術 1：LWT 為什麼能當 locking primitive。以下是書中其他章節的說法加上推論，Scalar DB 本身書中沒有展開。
      
    
        
      
      • 書中對 LWT 的描述（第 6 章、第 9 章）：以 Paxos 為基礎，提供 linearizable 的 check-and-set，語法是 IF NOT EXISTS 與 UPDATE … IF <conditions>；範圍限於單一 partition；一次成功的 LWT 需要 coordinator 與 replica 之間四次 round trip，比一般寫入貴。
        • 
      
      • 推論：鎖需要一個原子的 check-and-set，LWT 在單一 partition 內提供這個原語，所以 library 可以把它當作鎖的底層，再往上協調跨 service 的多筆變更。
        • 
      
      • 推論：建立在 LWT 上的鎖，會付上面提到的 round-trip 成本。
        • 
    
      
  
      

  
      
    機制說明
    
      技術 3：CDC 要解的 dual-write 問題。這一段是對書中那句話的補充說明，不是書中原文。
      
    
      一個 service 先寫資料庫、再發布事件，做的是兩個獨立的操作，兩者之間沒有共用的 transaction。在兩者之間當機，就會留下「寫入了、卻沒有事件」；如果順序反過來，則是「有事件、卻沒有寫入」。把事件改成從資料庫自己的變更紀錄產生，資料庫的寫入就成為唯一的事實來源，事件只是它的副產品，這個縫隙就不存在了。上面互動面板裡 Choreography 的第 3 步失敗，就是這個縫隙。
      
  
      

  
      
    機制說明
    
      技術 3：Cassandra 的 CDC 長什麼樣（見第 15 章）。
      
    
        
      
      • CDC 在 3.8 版引入，對指定的 table 擷取一部分 commit log，記錄包含 INSERT、UPDATE、DELETE 在內的所有 mutation。4.0 改為在 commit log 寫入時就記錄位置索引，書中說這提高了速度與可靠度。
        • 
      
      • 在 cassandra.yaml 設 cdc_enabled: true 並指定 cdc_raw_directory，再逐表開啟：
        • 
    
      
    
      cqlsh> ALTER TABLE reservation.reservations_by_confirmation WITH cdc=true;
      
    
      留意：本章把 reservations_by_confirmation 建成 reservations_by_hotel_date 上的 materialized view，第 15 章這個範例卻把它當一般 table 處理。兩章不一致，本頁不判斷這條 ALTER TABLE 能否用在 view 上。
      
    
        
      
      • 必須有 consumer 處理並刪除這些 commit log；超過 cdc_total_space_in_mb 的上限，CDC 就會停止。
        • 
      
      • 書中點出的難題：每筆寫入會出現在 replication factor 指定數量的節點上，要把 CDC 串流餵給 Kafka 這類下游，得先處理各節點 CDC log 的排序與去重。
        • 
      
      • 推論：所以第 7 章說「用 CDC 當事件來源」時，在 Cassandra 上要先有人消費 commit log，並解決各節點的重複事件。
        • 
    
      
  
      

  
      
    機制說明
    
      相關：書中列出的三種之外的做法（見第 1 章）。第 1 章在討論 two-phase commit 的限制時提過 compensation：操作先提交，出錯再用新的操作還原，樣式包括放棄失敗的交易、丟棄錯誤交易之後再對帳、收到失敗通知後稍後重試。書中說這些做法在 reservation system 裡不太可能滿足需求，billing 或 ticketing 之類的應用則可以接受。第 7 章的清單沒有列入這一類。

      術語表Glossary
      
  
      下列術語依本章的用法定義。本章只提到、細節留給其他章的術語（transient replica、lightweight transaction、tombstone、CDC 等），只寫本章說了什麼，並附上全書中對應章節的一句說明。
      
  
      
    
    
  
      
  
      
    
      bounded context
      一組相關 entity 的分組，概念來自 Eric Evans 的 Domain-Driven Design。本章在 conceptual data modeling 階段辨識它，logical 階段再精煉成 service；Hotel Domain 與 Reservation Domain 剛好對應最初資料模型的兩個 keyspace。設計流程
      
    
      encapsulation
      Sam Newman 微服務原則之一，意思是 service 專注把一件事做好。一個應用程式直接讀寫另一個應用程式的資料庫，會破壞 encapsulation，也讓依賴難以隔離與除錯。微服務架構
      
    
      autonomy
      每個 microservice 能獨立部署，不依賴其他 microservice。它也意味著每個 service 可以有自己的 data store。微服務架構
      
    
      polyglot persistence
      為每個 microservice 各自挑選資料庫的做法。本章提醒 Cassandra 不一定適合每個 service，尤其是不需要它那種 scalability 的 service。Persistence
      
    
      CRUD service
      負責建立、讀取、更新、刪除某一種資料型別的 service。本章的例子是 Reservation Service 與 Inventory Service，對照的是實作 booking 這個 business process 的 Booking Service。Service 互動
      
    
      orchestration
      由一個協調者（例如 Booking Service）負責串起多個 service 的資料變更，常見於區分 CRUD service 與 business process service 的架構。Service 互動
      
    
      choreography
      透過 message queue 或 Apache Kafka 這類 streaming platform 發出 data change events，由其他 service 非同步消費並調整自己的資料。沒有中央協調者，所以叫 choreography。Service 互動
      
    
      change data capture (CDC)
      本章把它當作 event-based choreography 的一種變體：以資料庫的 CDC 功能當事件來源，不必倚賴 service 先可靠地寫入資料庫再發事件。通常用在需要高度一致的 application 介面。第 15 章會討論 Cassandra 的 CDC：自 3.8 引入，捕捉選定 table 的 commit log 片段。Service 互動
      
    
      Scalar DB
      本章提到的函式庫，用 Cassandra 的 lightweight transaction 當 locking primitive，實作分散式 ACID transaction，用於需要 strong consistency 的跨 service 變更。Service 互動
      
    
      property graph
      常見的 graph 表示法：由代表 entity 的 vertex 與代表關係的 edge 組成，vertex 與 edge 都可以有 properties。在 Cassandra 上可讓每種 vertex 與 edge 各存成一張專用的 table，再由 Gremlin 或 Cypher 這類查詢語言與處理引擎來操作。Persistence
      
    
      vertex
      property graph 中代表領域 entity 的節點（本章拼作 vertexes 與 vertices）。Persistence
      
    
      edge
      property graph 中代表 vertex 之間關係的連線，可以往任一方向走訪。Persistence
      
    
      denormalization
      第 5 章的原則：為每個 access pattern 建一張專用 table。本章問的是新增 access pattern 時要加幾張才算太多，答案取決於讀寫量與資料量。Secondary Indexes
      
    
      access pattern
      應用程式查詢資料的方式。本章把 use case 與 access pattern 歸為 UX 設計產出，會同時影響 data modeling 與 software architecture 兩條流程。設計流程
      
    
      Chebotko diagram
      第 5 章採用的資料模型圖示法（由 Artem Chebotko 推廣）。本章指出圖上的 query 箭頭可以幫忙判斷 service 之間是直接呼叫依賴，還是透過 UI 或事件的資料流。設計流程
      
    
      keyspace
      本章的經驗法則是一個 service 一個 keyspace，以促進 encapsulation；搭配第 14 章的 access control，可以為每個 keyspace 建一個資料庫使用者，讓 service 只擁有自己 keyspace 的讀寫權限。replica 數量也是在 keyspace 層級設定。部署考量
      
    
      NetworkTopologyStrategy
      本章中，keyspace 要用它為每個有部署 service 的 data center 設定要保存的 replica 數。第 6 章說它可以對每個 data center 指定不同的 replication factor，並建議用於 production 的 keyspace。部署考量
      
    
      local data center
      service instance 所在的 data center。本章建議 service instance 知道這個名稱，且對應的 cluster 在 service 部署的每個 data center 都應有 node，以取得最快的存取。部署考量
      
    
      shared / dedicated cluster
      service 與 Cassandra cluster 的對應方式。大規模使用者（本章舉 Netflix）常為每個 service 配專用 cluster；彈性做法是需求低的 service 共用、需求高的 service 專用。使用型態互不衝突時，共用才合理。部署考量
      
    
      secondary index
      建立在非 primary key column 上的 index，建法是 CREATE INDEX。每個 node 只為自己擁有的 partition 維護 index，所以查詢通常牽涉更多 node。也可建立在 UDT 欄位或 collection 的值上。Secondary Indexes
      
    
      SASI
      SSTable Attached Secondary Index，Cassandra 3.4 引入的實驗性 secondary index 實作，由 Apple 開發。index 隨每個 SSTable 計算與儲存，支援不等式與 LIKE，用 CREATE CUSTOM INDEX 建立。Secondary Indexes
      
    
      cardinality
      欄位上不同值的數量。本章的兩個反例：hotel.address 是 high cardinality（絕大多數 address 都是唯一值），user.title 是 very low cardinality（想查所有 "Mrs." 會得到巨大的 index row）。Secondary Indexes
      
    
      tombstone
      本章只提到：頻繁更新或刪除的欄位上的 index，在 tombstone 累積速度超過 compaction 的處理速度時會出錯。第 6 章的定義：tombstone 是標記資料已被刪除的 marker，刪除會先被當成放一個 tombstone 的更新，之後在 compaction 時移除。
      
    
      ALLOW FILTERING
      查詢非 primary key column 時，Cassandra 預設拒絕並回傳 InvalidRequest；加上這個關鍵字可覆寫預設行為，代價是要請所有 node 掃描所有 SSTable，可能造成 query timeout 與額外負載。Secondary Indexes
      
    
      base table
      materialized view 的來源 table，也就是 FROM 子句所指的 table。對 base table 的寫入要付出維護 view 的成本。Materialized Views
      
    
      materialized view
      由 Cassandra 維護、與 base table 保持一致的預先設定 view。每個 view 支援以單一個不在原 primary key 內的 column 為條件的查詢，primary key 必須包含 base table 的全部 primary key column。Materialized Views
      
    
      experimental feature
      社群為「牽涉重大架構變動」的新功能所訂的處理方式：標為 experimental 並預設停用，啟用要修改 cassandra.yaml。本章在這一節提到 SASI 與 transient replicas 是其他的 experimental features，並以 materialized view 的討論開頭。Materialized Views
      
    
      transient replica
      Cassandra 4.0 引入的 experimental feature，用來替極大型 cluster 節省成本。本章只說這些，細節留給第 9 章；第 9 章說明它只在 full replica 不可用時才儲存資料。Materialized Views
      
    
      lightweight transaction
      本章只在 Scalar DB 那裡提到它是 locking primitive。第 6 章說明它自 2.0 起提供 linearizable consistency，實作基於 Paxos。Service 互動
      
    
      KillrVideo
      DataStax Developer Relations 團隊與其他貢獻者建立的影片分享開源參考應用，採用 microservice 架構，用到 Apache Cassandra 與 DataStax Enterprise 的 Search 及 Graph，可視為本章設計原則的另一個範例。Service 互動
