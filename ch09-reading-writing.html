寫入 · Writing

寫入一致性等級Write Consistency Levels

寫入要等幾個 replica 確認才算成功，由一致性等級決定。這一節比較各等級的差別，並說明為什麼只有 ANY 讓 hint 算成功。

等級決定 coordinator 要等幾個 ack

寫入要多少一致性，由用戶端在每次查詢中指定，這就是 tuneable consistency。不論選哪個等級，coordinator 都會把寫入送給全部 replica。等級只決定它要收到幾個 replica 的確認 (ack)，才回覆用戶端寫入成功。要求的確認越多，越多節點確定寫好這筆資料，可用性卻越低，因為要有更多節點在線，寫入才成得了。

RF 設在 keyspace，一致性等級由用戶端每次查詢指定，而且等級以 RF 為基準，與叢集裡有幾個節點無關。QUORUM 要的確認數是 floor(RF / 2) + 1（等同書中的 floor(RF / 2 + 1)）：RF = 3 要 2 個，RF = 4 與 RF = 5 都要 3 個。以 RF = 3 計算，ONE 容許 2 個 replica 離線，QUORUM 容許 1 個，ALL 一個都不行。coordinator 若已經知道在線的 replica 湊不出所需的數量，會立刻回傳錯誤。

ANY：hint 也算成功

ANY 是寫入等級裡最特別的一個。寫入保證至少會到達一個節點，但 hint 也能算作一次成功的寫入。目標節點掛掉時，server 替自己留一張便條，也就是 hint，保留到該節點回來，或超過 max_hint_window_in_ms 設定的有效期限為止。節點回來之後，server 察覺到，檢查手上有沒有給它的 hint，再把值寫給它。

其他等級裡，hint 不算成功的 replica 寫入，不能替 coordinator 湊足 ack。只有 ANY 例外：就算所有 replica 都離線，只要 server 存了 hint，這次寫入就成功。這時還沒有任何 replica 收到值，要等節點回來才會補寫。

ONE：兼顧速度與 durability 的最低等級

replica 收到寫入後，會寫進 commit log 與 memtable 兩處，所以 ONE 的寫入已經具備 durability。節點若在寫入之後、memtable flush 之前當機，值仍在 commit log 裡，節點重啟時會 replay 回來。想同時要快的寫入與 durability，ONE 是最低可選的等級。

      寫入 · Writing

      寫入路徑The Cassandra Write Path

      一筆寫入送進叢集之後，先由 coordinator 分送給每個 replica，再在每個 replica 內依序進 commit log、memtable，最後落成 SSTable。這一節把兩個層次拆開，說明每一步為什麼這樣排。

      寫入路徑是用戶端送出修改資料的查詢之後，到資料存上磁碟為止的過程。書中分兩層來看：第一層在節點之間，一筆寫入如何送到各個 replica、何時回覆用戶端；第二層在單一 replica 之內，資料如何依序進入 commit log 與 memtable，再變成 SSTable。第二層的步驟與其他採用 log-structured merge tree（LSM-tree）設計的資料庫相同。

      節點之間

      收到請求的節點成為 coordinator。它用 partitioner 與 keyspace 的 replication factor 算出 replica 是誰，把寫入同時送給所有本地 replica。叢集跨多個資料中心時，它在每個其他 DC 挑一個遠端 coordinator，由遠端 coordinator 轉送給該 DC 的 replica；遠端 replica 的 ack 直接回給原來的 coordinator。從機制推得的理由是：判斷一致性等級是否滿足的是原 coordinator，ack 要送到它手上，遠端 coordinator 只負責在自己的 DC 內轉送。

      一致性等級只決定 coordinator 等幾個 ack 才回覆用戶端，不改變寫入送給誰，所以只要節點在線，每個 replica 都會收到。沒有在逾時內回應的 replica 會被當作 down，coordinator 替它存一個 hint。節點離線期間落後的資料，之後靠 hinted handoff、read repair 或 anti-entropy repair 補齊。

      寫入一致性等級

      示範設定：DC1 與 DC2 各有 3 個 replica（每個 DC 的 RF 為 3，quorum 為 2）。ack 的到達順序採固定假設，DC1 先、DC2 後，書中沒有規定先後。其他 replica 都在逾時之前回應。改變上面任何一個設定，步驟會從頭開始。

        1. 用戶端把寫入送給任一個節點

          用戶端可以連到叢集中的任何節點。收到請求的節點成為這筆寫入的 coordinator，由它負責找出 replica 並轉送，所以用戶端不必事先知道資料放在哪些節點上。

        2. 用 partitioner 找出 replica

          coordinator 用 partitioner 算出這筆資料屬於哪些節點，數量由 keyspace 的 replication factor 決定。示範中 DC1 與 DC2 各有 3 個 replica。coordinator 自己也可能是其中一個 replica，用戶端使用 token-aware load balancing policy 時尤其常見。

        3. 確認在線的 replica 夠不夠

          如果 coordinator 已經知道在線的 replica 少到無法滿足要求的一致性等級，就立刻回錯誤給用戶端。從機制推得：既然已知道湊不齊 ack，就沒有必要送出去再等逾時。

        4. 同時送給所有本地 replica

          coordinator 把寫入同時送給 DC1 的每一個 replica，送出的對象與一致性等級無關。每個 replica 做完下方「節點內部」面板的步驟 1 到 4（commit log、memtable、作廢快取、排定 flush）才回覆，所以一個 ack 代表這個 replica 已經把資料寫進 commit log 與 memtable。

        5. 經由遠端 coordinator 送到其他 DC

          coordinator 在 DC2 挑一個遠端 coordinator，由它轉送給 DC2 的 replica。DC2 的 replica 寫完後，ack 直接回給原來的 coordinator。從機制推得，這是因為判斷一致性等級有沒有滿足的是它。這樣只要節點在線，每個節點都拿得到這筆寫入。離線的節點會落後，之後靠 hinted handoff、read repair 或 anti-entropy repair 補齊。

        6. 湊夠 ack 就回覆用戶端

          coordinator 一邊收 ack，一邊對照一致性等級，湊夠的那一刻就回覆用戶端，不等剩下的 replica。所以回覆發生在哪一步，取決於一致性等級要求的 ack 什麼時候到齊。

        7. 沒回應的 replica：逾時後存 hint

          replica 在 write_request_timeout_in_ms（預設 2000，即 2 秒，見第 13 章 Table 13-1）內沒有回應，coordinator 就把它當作 down，替這筆寫入存一個 hint，之後補給它。hint 不算成功的 replica 寫入（一致性等級是 ANY 時才算），所以不會讓 ack 計數增加。

        節點之內

        replica 收到請求的第一件事，是把資料 append 到 commit log。記憶體裡的東西當機就沒了，所以寫入要先進磁碟上的 commit log，才算在這個節點成功；它只在節點重啟時被讀回來 replay，用戶端讀不到它。接著資料進 memtable，row cache 裡若有同一列就作廢，若 commit log 或 memtable 超過上限就排定 flush，然後節點回覆。flush 在回覆之後才執行：memtable 寫成 SSTable，commit log 清除，再檢查是否需要 compaction。

        回覆不必等 flush，因為此時資料已經在 commit log 裡，當機也找得回來。flush 只是把記憶體內容整理成檔案，晚一點做不影響這一筆寫入的耐久性。

        元件位置要記住的事
        commit log磁碟整台 server 共用一份，所有資料表的寫入都進同一份。每個 commit log 為每張資料表記一個旗標，標示它是否還有未 flush 的資料，該表 flush 後旗標設回 0。只在節點重啟時讀取（replay）。
        memtable記憶體每張資料表一個，另外可能有等著 flush 的舊 memtable。flush 不會阻塞寫入。2.1 起部分資料可放在 native（off-heap）記憶體，降低 GC 的影響。
        row cache記憶體預設關閉，開啟後放整列資料（off-heap）。寫入時，快取中的同一列會被作廢。
        SSTable磁碟每次 flush 產生新的一個，寫成後不可修改。compaction 做的是 mergesort 裡的 merge 步驟，把多個 SSTable 合併成新檔，成功後刪除舊檔；預設的 compaction strategy 是 SizeTieredCompactionStrategy。

        回覆之前

        1. 寫入 commit log

          replica 一收到請求，立刻把資料 append 到磁碟上的 commit log。放在第一步，是因為記憶體裡的資料當機就消失，只要資料先進了 commit log，節點在後面任何一步當機，重啟時都能 replay 回來。寫入要進了 commit log 才算在這個節點成功。這一步只是在檔案尾端 append，不必讀取，也不必 seek。

        2. 寫入 memtable

          接著資料寫進記憶體中的 memtable，每張資料表各有一個。memtable 先暫存這張表還沒落地的資料，累積到門檻才整批寫到磁碟（步驟 6）。SSTable 寫成後不可修改，所以每一筆寫入都不去碰既有的 SSTable，只更新記憶體裡的 memtable。

        3. 作廢 row cache 裡的該列

          如果有開 row cache（預設關閉），而且這一列剛好在快取裡，就把快取裡的那一列作廢，因為這筆寫入讓它過時了。沒開快取，或該列不在快取裡，這一步什麼都不做。

        4. 超過上限就排定 flush

          如果這筆寫入讓 commit log 或 memtable 超過各自的上限，節點排定一次 flush。這裡只排定，不執行：flush 要把整份 memtable 寫上磁碟，若在這裡做，這一筆寫入就得跟著等。門檻值在第 13 章調整。

        5. 回覆 coordinator

          到這裡寫入視為成功，節點回覆 coordinator（或直接回用戶端）。資料已經在 commit log，節點此刻當機也找得回來，所以不必等 flush。這個回覆就是上方「節點之間」面板裡的 ack。

        6. 回覆之後才執行 flush

          節點回覆之後，才執行剛才排定的 flush：每個 memtable 的內容寫成磁碟上的 SSTable，commit log 清除，之後換一個新的 memtable 接手。寫進 SSTable 的資料不再需要 commit log 保護，所以可以清掉。flush 不會阻塞寫入。

        7. 檢查是否需要 compaction

          flush 完成後，節點再排程檢查是否需要 compaction，需要就做。compaction 把多個 SSTable 合併成新檔，成功後刪掉舊檔。它只改變資料在磁碟上的排列，不改變資料本身，目的是讓讀取更有效率，成本用 sequential I/O 攤平。

        為什麼寫入這麼快

        寫入磁碟的資料只有兩種去處：append 到 commit log，或寫成新的 SSTable（flush 與 compaction）。SSTable 寫成後不可修改。寫入不需要先讀舊資料，也不需要 seek。把資料整理成適合讀取的樣子，留給排在 flush 之後的 compaction，用 sequential I/O 把成本攤平。keyspace 屬性 durable_writes（預設 true）可以關掉 commit log，寫入更快，代價是節點在 memtable flush 之前當機會遺失資料。下面的面板讓你自己試。

          commit log 與 SSTable 各放在哪個目錄、檔名由哪幾段組成，以及為什麼一個 SSTable 會是好幾個檔案。

          寫入 · Writing

          輕量級交易Lightweight Transactions

          高一致性等級擋不住「先讀再寫」的競爭。LWT 用 Paxos 把檢查和寫入合成一個操作，代價是四個 round trip。

          Cassandra 和許多 NoSQL 資料庫一樣，不提供關聯式資料庫那種完整 ACID 語意的 transaction。它有兩個帶有部分 transaction 行為的機制：lightweight transaction（LWT）和 batch。本節講 LWT，batch 在下一節。LWT 以第 6 章介紹的 Paxos 演算法為基礎，2.0 版開始提供。

          先讀再寫的競爭

          典型情境是「帳號不存在才建立」：用戶端先查詢，沒找到，再寫入。就算讀和寫都用很高的 consistency level（strong consistency），這個流程仍然有空檔。另一個用戶端可能在你讀完之後、寫入之前，也讀到「不存在」，然後搶先寫入。兩個用戶端的判斷各自都正確，合起來卻互相衝突。

          這裡需要的保證叫 linearizable consistency：在你的讀取和寫入之間，沒有其他用戶端能插進來做自己的修改。Paxos 是一種 consensus 演算法，讓對等的分散式節點不用靠一個 leader 統籌整個 transaction，也能對某個 proposal 達成共識，可以當作 two-phase commit 的替代方案。

          語法檢查的條件典型用途
          INSERT ... IF NOT EXISTS相同 primary key 的 row 還不存在才寫入，已存在就不覆寫要求唯一的資料：使用者身分與帳號、唯一的訂位紀錄

          代價：四階段 Paxos

          基本 Paxos 有兩個階段：prepare/promise 和 propose/accept。Cassandra 在上面加了兩個階段，用來支援先讀後寫（check-and-set）的語意，並在交易之間重置狀態。結果是四個階段：Prepare / Promise、Read / Results、Propose / Accept、Commit / Ack。每個階段 coordinator 和 replica 來回一次，所以一個成功的 LWT 需要四個 round trip，比一般寫入貴得多。

          1. Prepare / Promise

            coordinator 以 leader 的身分為這次修改提出 proposal。每個 replica 檢查：如果這是它見過最新的 proposal，就承諾不再接受更早的 proposal，並把它收到的最後一個進行中的 proposal 回報回來。

          2. Read / Results

            這是 Cassandra 為了支援先讀後寫（check-and-set），加進 Paxos 的兩個階段之一。從階段名稱推斷，coordinator 在這一步讀回目前的資料，才能判斷條件是否成立。書中沒有說明這個階段實際交換了哪些內容。

          3. Propose / Accept

            基本 Paxos 的第二階段：coordinator 提出要寫的值，replica 以 Accept 回覆。多數 replica 同意之後，leader 就可以 commit。

          4. Commit / Ack

            leader 把這次的值 commit，replica 回 ack。書中描述基本 Paxos 時有一條規則：leader 在 commit 自己的 proposal 之前，必須先 commit 排在它前面、仍在進行中的 proposal。走到這裡是第四個 round trip。

          LWT 限於單一 partition。Cassandra 為每個 partition 各存一份 Paxos 狀態，所以不同 partition 上的 transaction 不會互相干擾。LWT 語句可以放進 batch，但同一個 batch 裡的多個 LWT 必須作用在同一個 partition。實作在 org.apache.cassandra.service.paxos 套件。

          atomic 的範圍

          logged batch 是 atomic 的：batch 只要被接受，裡面所有 statement 最終都會成功，所以也叫 atomic batch。這和關聯式資料庫的 atomicity 不同。同一個 partition key 底下的更新會一起、atomic 地套用；不同分區之間則沒有保證，也沒有 isolation，讀取可能在 batch 完成之前，就看到某些分區的修改。上面的預約例子寫進兩個資料表，就是兩個不同的分區，讀取有機會只看到其中一邊。

          書在第 15 章換了個說法描述這個保證：只要所有 statement 都是合法的 CQL，其中任何一個成功完成後，coordinator 就會在背景繼續確保其餘的 statement 都執行，必要時靠 hinted handoff 之類的機制。

          logged batch 與 batchlog

          logged batch 的 atomic 保證靠 batchlog 達成。流程分三步：

          1. coordinator 把 batch 的副本（batchlog）送到另外兩個節點，存進它們的 system.batchlog 資料表。
          2. coordinator 執行 batch 裡的所有 statement。
          3. statement 都完成後，coordinator 從那兩個節點刪除 batchlog。

          batchlog 存在 coordinator 以外的節點，所以 coordinator 在中途失敗時，副本還在，可以 replay 這個 batch。每個節點每分鐘檢查一次自己的 batchlog，找出應該已經完成的 batch。判斷標準是 grace period：從 batch statement 的 timestamp 起算 2 × write_request_timeout_in_ms，預設 write_request_timeout_in_ms 是 2000 ms，所以是 4 秒。比 grace period 老的 batch 會被 replay，然後刪除。存到兩個節點，是多加的一層冗餘。

          unlogged batch 與單一分區的例外

          unlogged batch 跳過上面的 batchlog 步驟，所以寫入完成得比較快。代價是不同分區的寫入不保證全部完成，資料庫可能停在不一致的狀態。如果 batch 的所有 mutation 都在同一個分區，就沒有這個風險；因此你要求 logged batch、而所有 mutation 都落在單一分區時，Cassandra 實際上會當成 unlogged batch 執行，以換取速度。

            讀取一致性等級Read Consistency Levels

            先比 timestamp，再做 read repair

            讀取等級的概念與寫入等級相似，幕後的處理略有不同。等級越高，必須回應的節點越多，各 replica 持有相同值的把握也越大。兩個節點回應的 timestamp 若不一樣，最新的值勝出，回傳給用戶端。接著 Cassandra 做 read repair：發現有 replica 回的是過期的值，就把最新的值寫給它，讓全部 replica 一致。

            書中補充欄 · Aligning read and write consistency levels

            讀取的等級加上寫入的等級，以 replica 個數計算，超過 RF 時，Cassandra 保證讀取是強一致性：R + W > RF。R 是讀取要問的 replica 數，W 是寫入要確認的 replica 數。

            最簡單的做法是讀寫都用 QUORUM。RF = 3 時，QUORUM 是 3 個節點中的 2 個，2 + 2 > 3，所以保證強一致性。

            如果願意放棄強一致性，換取更高的吞吐量與對節點掛掉的容忍度，就用較低的等級。例如 QUORUM 寫入搭配 ONE 讀取，不保證強一致性，因為 2 + 1 只是等於 3。實際情況是：寫入只保證落在三個 replica 中的兩個，剩下那個可能還沒收到寫入，也還沒被修復，而 ONE 的讀取偏偏可能問到它。

            讀取路徑The Cassandra Read Path

            一次讀取要回答兩個問題：coordinator 要向哪些 replica 要什麼，以及單一 replica 怎麼用最少的磁碟工作把資料找出來。

            為什麼讀取要經過這麼多層

            寫入只是 append，讀取沒有這麼單純。一個 partition 的資料可能還在 memtable 裡、沒有 flush，也可能分散在好幾個 SSTable，每個 SSTable 各自存著其中幾個欄位。所以一次讀取至少要查 memtable，再查每一個可能含有這個 partition 的 SSTable，最後把結果合併。書中以單一 partition key 的查詢為例，把讀取路徑分成兩個層次：節點之間（圖 9-3），以及單一 replica 內部（圖 9-4）。

            replica 內部的每一層結構都在做同一件事：讓讀取跳過下一層會花掉的工作。下表依讀取檢查的順序列出它們。

            partition summary 的位置，書中有兩種說法。第 9 章把 partition summary 與 partition index 描述成存在磁碟的兩層索引；講檔案的段落則說 index summary 保存在記憶體，Summary.db 是 index 的取樣，Index.db 存著 Data.db 裡的 row 與 column offset。本節的圖依第 9 章的寫法，把兩者畫在磁碟。key cache、row cache 與 chunk cache 會定期存到磁碟，重啟後比較快暖起來。

            節點之間：只有一個 replica 回傳完整資料

            coordinator 用 partitioner 找出 replica，並確認活著的 replica 足以滿足一致性等級；涉及多個資料中心時，每個資料中心會選出一個 remote coordinator。接著它把完整的讀取請求送給 dynamic snitch 判定最快的 replica，其餘 replica 收到的是 digest 請求。digest 請求在 replica 上走的路徑和一般讀取相同，只在最後多一步：replica 對結果算出 hash，回傳的只有 hash，沒有資料。

            所以完整的資料只會從一個 replica 送回 coordinator，其餘的回應都只是 hash。coordinator 把收到的資料也算成 hash，和每一個 digest 比對。全部一致、一致性等級也達到了，就回傳那份資料；不一致，就必須做 read repair，細節在 Read Repair 一節。這裡對「為什麼只有一個 replica 回傳完整資料」的說明，是從 digest 的定義推得的，書中沒有另外解釋。

              讀取修復Read Repair

              這一節說明讀取時 digest 對不上之後，coordinator 怎麼挑出該採用的值，以及落後的 replica 何時、以什麼方式被補齊。

              從 digest 不一致開始

              在讀取路徑上，coordinator 向最快的 replica 要完整資料，向其他 replica 只要 digest（資料的 hash）。digest 只能告訴 coordinator 資料不一樣，看不出誰的 timestamp 比較新。所以 digest 不一致時，coordinator 必須做 read repair，重新拿完整資料來比。流程是五步：

              1. coordinator 對所有 replica 送出 full read request，包含剛才只回傳 digest 的那些。
              2. 逐欄位比較各 replica 回傳的值，每個欄位選 timestamp 最新的那一個，這是合併（merge）。
              3. 如果不同的值帶著相同的 timestamp，就比較值本身的 lexicographic 順序，取較大的。書中說這種情況極少發生。
              4. 合併後的結果就是回給用戶端的資料。
              5. coordinator 找出回傳舊資料的 replica，對每一個送出 read-repair request，要它們依合併結果更新。書中把這一步形容為非同步，但實際發生在回應之前還是之後，要看下一小節的規則。

              tie-break 看一個例子：兩個 replica 對 end_date 回傳 2020-06-11 與 2020-06-12，timestamp 相同。依 lexicographic 順序比較兩個值，2020-06-12 排在 2020-06-11 之後，合併結果就是它。

              修復在回應之前還是之後

              修復的時機跟一致性等級綁在一起。QUORUM 與 ALL 這兩個較強的等級，修復在資料回給用戶端之前完成。ONE 這類較弱的等級，修復是選擇性的，在回應之後的背景進行。

              一致性等級修復時機用戶端收到的值
              QUORUM、ALL回應之前digest 不一致時，是合併後的值
              ONE 等較弱的等級回應之後，在背景，不一定發生最先回應的那個 replica 的值，可能已過時

              有多少比例的讀取會做背景修復，由資料表選項 read_repair_chance 與 dc_local_read_repair_chance 決定。書中別處 DESCRIBE TABLE 的輸出把第二個選項拼成 dclocal_read_repair_chance，是同一個選項。

              ONE 的情況要看仔細。依本頁的模型（ONE 只聯絡 fastest replica），這次讀取沒有 digest 可以比對，coordinator 看不出其他 replica 有沒有落後，用戶端拿到的就是那一個 replica 的值，就算它是舊的。背景修復如果發生，是在回應之後進行，修完之後的讀取不論連到哪個 replica，看到的都會是一致的值。

              書外補充 · 高信心

              書中以 4.0 alpha 為準。正式版 4.0 已經移除機率式的背景 read repair：資料表選項 read_repair_chance 與 dclocal_read_repair_chance 不再存在。取而代之的是每個資料表一個 read_repair 選項，有兩個值：

              • BLOCKING（預設）：在讀取期間、回應之前修復，也就是上面 QUORUM 與 ALL 的行為。
              • NONE：不做 read repair，搭配 transient replication 時需要用它。

              所以在實際的 4.x 叢集上，書中所說「ONE 讀取之後在背景修復其他 replica」不會發生。本節其餘內容仍照書中的 4.0 alpha 描述，這裡只標出版本差異。

                Transient Replication

                書中補充欄 · Transient Replication

                以下整段改寫自書中的 sidebar。Transient replication 是幾家部署規模很大的公司為了壓低基礎設施成本而開發的。它加入一種新的 replica，叫 transient replica，只有在一般的 full replica 不可用時才存放資料。full replica 回到線上後，資料透過 incremental repair 移回 full replica，transient replica 上的副本就能刪掉。同樣的可用性與一致性，用的磁碟空間比較少，CPU 與 I/O 負載也比較低。從用戶端看是透明的。

                如何啟用與設定

                它在 4.0 是實驗性功能，預設關閉。先在 cassandra.yaml 開啟 enable_transient_replication，再以 keyspace 為單位指定 replica 裡有幾個是 transient。設定寫在 keyspace 上，所以同一個叢集可以同時有啟用與沒啟用的 keyspace。

                replication factor 寫成 5/2，表示總共五個 replica，其中三個 full、兩個 transient。單一 data center、原本 RF = 3 的叢集，常見做法就是改成 5/2：不用加節點，就多了兩個 replica。

                多個 data center 時，每個 DC 各寫一組。下面兩個 DC 各是 3/1，也就是各有三個 replica、其中一個是 transient，合計四個 full replica，足以達成 QUORUM。

                哪些 replica 是 transient

                RF 變大時，token 順時針方向的下一批節點會成為 replica。啟用 transient replication 之後，token 離原本那個 token 最遠的節點是 transient replica，近的是 full replica。因此每個節點對某些 token 是 full replica，對另一些 token 是 transient replica。書中的圖 9-5 畫的就是這件事，下面的 ring 可以自己點。

                  Cassandra 的刪除不會立刻移除資料。這一節說明原因，tombstone 怎麼避免資料復活，以及它在磁碟與讀取上的代價。
                  
  
                  

  
                  為什麼不能直接把資料刪掉
                  
  
                  關聯式資料庫的 DELETE 直接移除資料列。Cassandra 的資料有多個 replica，只保證最終一致，直接移除會出問題。假設刪除送出時 node3 剛好離線，沒收到這次刪除。等它回來，手上有一列另外兩個節點都沒有的資料。從它的角度看，是那兩個節點漏了一筆寫入，於是它開始修復它們，把已刪的資料送回去。第 6 章稱之為資料復活（resurrecting）。
                  
  
                  所以 Cassandra 把刪除當成一種更新：在值上放一個 tombstone，作為佔位的標記，概念上接近關聯式世界的 soft delete。漏掉刪除的 replica 等到重新可用，tombstone 就能傳播給它。代價是刪除之後資料庫不會馬上變小。
                  

  
                  gc_grace_seconds 與 compaction
                  
  
                  每個節點都記錄自己所有 tombstone 的年齡。年齡達到資料表設定的 gc_grace_seconds（預設 864,000 秒，即 10 天），就會跑 compaction 回收 tombstone，磁碟空間隨之釋出。SSTable 寫好就不可變，所以資料不會在原檔裡被抹掉。compaction 處理完 tombstone，把合併、排序過的資料重建索引，寫成一個新檔案。
                  
  
                  10 天的設計假設是：故障的節點有足夠時間在 compaction 之前恢復上線。如果你願意承擔風險，可以縮短寬限期，更早回收空間。刪除是寫入的一種，所以刪除可用的一致性等級與寫入完全相同。
                  
  
                  注意
                  停機時間超過 gc_grace_seconds 的節點，要當成故障節點並替換掉（第 6 章）。第 12 章講的是同一件事的後果：刪除發生時離線、又離線超過這段時間的節點，重新上線時可能讓資料復活。面板 A 可以重現這個情況。

                  本節重點
                  
    
                    
      
                  • 刪除寫入 tombstone，不會立刻移除資料。在 tombstone 還沒被清掉之前，漏掉刪除的 replica 回來時會收到 tombstone，不會把舊資料送回去。
