      ccm 是什麼（Cassandra Cluster Manager）

      書中拿 Cassandra Cluster Manager（簡稱 ccm）當實作工具，邊做邊認識 Cassandra 的設定。ccm 是一組 Python 腳本，作者是 Sylvain Lebresne 與幾位貢獻者，可以在同一台機器上跑出多節點叢集。你不必準備額外硬體，就能很快配出一個叢集，順便認識最常被設定的選項（書中把這些選項指向 Cassandra 文件的說明）。

      書中的背景是：Cassandra 不用先設定就能跑，下載、解壓縮、啟動，就會用預設設定運作；但它可設定、可客製的程度很高，選項多到剛開始會讓人不知從何下手。

      書中提到 ccm 讓多個節點共用一台機器的做法有三項：修改 Cassandra 原始碼、每個節點用不同的 loopback 位址（127.0.0.1、127.0.0.2…）、各節點的 conf 有各自的資料目錄、位址與 JMX 連接埠。這些細節在下面兩節會看到。

      # 用 pip 安裝
pip install ccm
# macOS 也可以用 Homebrew
brew install ccm

      裝好之後 ccm 就在系統路徑上，可以直接在終端機呼叫。要看支援哪些指令，輸入 ccm 或 ccm --help；要看某個指令的選項，用 ccm <command> -h，例如 ccm create -h。（書中印成 ccm –help、ccm add –h，破折號應是排版造成的，實際旗標是 -- 與 -。）後面幾節會用到其中好幾個指令。

      這些腳本也可以直接從自動化測試套件裡呼叫。ccm 的原始碼放在 GitHub（書中附有連結），想知道它背後做了什麼，直接讀那些 Python 腳本就行。想先看整段操作長什麼樣子，可以跳到操作重放。

      為測試建立 Cassandra 叢集

      開發應用程式時，單元測試與整合測試用真正的叢集往往比較方便。書中說 Docker 和 ccm 都適合建出小型的測試叢集，能快速建起，用完就拆掉。

      建立叢集（Creating a Cluster）

      叢集由哪些值定義

      cassandra.yaml 是 Cassandra 節點最主要的設定檔，放在安裝目錄底下的 conf 目錄。定義一個叢集的值都在這個檔案裡，關鍵的有四個：叢集名稱、partitioner、snitch 和 seed 節點。

      值每個節點都要相同說明
      叢集名稱 cluster_name必須防止機器誤加入別的叢集。預設值是 Test Cluster。
      partitioner必須書中此處只要求一致，不解釋原因。機制見 Partitioner 與 Token。
      snitch必須同樣只要求一致。機制見 Seed 與 Snitch。
      seed 節點不強制不必每個節點完全相同，但建議每個 data center 使用同一組 seed。最佳實務留到後面討論。

      叢集名稱

      叢集名稱的用途，是防止某個叢集裡的機器誤加入另一個你沒打算讓它加入的叢集。cassandra.yaml 裡預設的名稱是 Test Cluster，用 cluster_name 修改，而且要在打算放進這個叢集的每個節點上都改。

      更改叢集名稱

      如果叢集已經寫入過資料，之後才改叢集名稱，Cassandra 啟動時讀取資料檔，會發現名稱對不上，報出 cluster name mismatch 錯誤，然後關閉。

      用 ccm 建立範例叢集

      接著替前面章節討論的 Reservation Service 建一個叢集。書中說下面的輸出經過縮減。

      $ ccm create -v 4.0.0 -n 3 reservation_cluster --vnodes
...
Current cluster is now: reservation_cluster
      書中只說「三個節點」，沒有逐一解釋旗標字母。-n 對應節點數，是從指令和句子推得。
      指令的部分作用
      -v 4.0.0要使用的 Cassandra 版本。
      -n 3三個節點。
      reservation_cluster叢集名稱。
      --vnodes使用 virtual node（vnode）。

      有個容易漏掉的地方。ccm 預設建立的是單一 token 的節點，所以要用 vnode，就必須明確加上 --vnodes。加了之後，每個節點會有 256 個 token，下面的 ccm node1 status 輸出會看到。

      建好之後，ccm 把這個叢集設為目前的叢集（current cluster），之後的指令都作用在它身上。

      為了讓多個節點能共用一台機器，ccm 得先改動一點 Cassandra 原始碼，所以建立叢集時它會自己下載你指定的版本並編譯（用第 3 章下載的那份原始碼也可以）。其他建立選項見 ccm create -h。

      加入節點（Adding Nodes to a Cluster）

      先看手動加節點要做什麼，才看得出 ccm 省了多少事。手動加一個節點，要先設定新節點自己的 cassandra.yaml：seed 節點、partitioner、snitch 和網路連接埠。如果用的是單一 token 的節點，還得算出新節點的 token 範圍，並調整其他節點的範圍；書中只在單一 token 的情況下提到這最後一步。

      書中講這段時，開頭說「既然你已經了解每個節點要設定什麼」，但那些內容其實在下一部分的「節點設定」才會教，所以讀到這裡還不熟是正常的。

      用 ccm 就簡單得多：

      $ ccm add node4 -i 127.0.0.4 -j 7400

      這會建立 node4，給它另一個 loopback 位址 127.0.0.4，JMX 連接埠設為 7400。書中沒有說明 -i 和 -j 是什麼，這裡的對應（-i 是位址，-j 是 JMX 連接埠）是依句子順序推得。回頭看上一節 ~/.ccm 的 diff，位址和 JMX 連接埠正好是各節點 conf 會不同的項目，和 ccm add 要你指定這兩個值是一致的。更多選項用 ccm add -h 查看。

      加完之後再看狀態：

      $ ccm status
Cluster: 'reservation_cluster'
---------------------
node1: UP
node3: UP
node2: UP
node4: DOWN (Not initialized)

      節點建好了，但還沒啟動，所以和一開始的三個節點一樣是 DOWN (Not initialized)。這時再看一次 ring，token 沒有任何變化。

      書中出入：「token 重新分配」的說法

      把兩份節錄放在一起，會發現第一點說不通。第一份列表裡，屬於 127.0.0.1 的最小 token 是 -9181802192617819638，第二份卻出現屬於 127.0.0.1、而且更小的 −9211073930147845649。兩份都是從環的最前面節錄的，如果 node1 保有原來的 token，這個更小的 token 在第一份就該先出現。這暗示兩份節錄取自不同次的執行。這個讀法依賴前面提到的「token 接在列的下一行」的推讀，書中沒有明說。

      本頁補充：vnode 叢集加入新節點時，token 怎麼變

      非書中內容，高信心。在使用 vnode 的叢集裡，既有節點會保留自己已經擁有的 token。新加入的節點自己取 num_tokens 個新 token，這裡是 256 個。每個新 token 落在某個既有範圍裡，把那個範圍切成兩段，所以環上的範圍數從 768 增加到 1,024，平均每個範圍變小。沒有分到新 token 的範圍則維持原樣。

      這和書中的第二點（範圍變小），以及接著補充的總數 1,024 一致。只有「所有節點的 token 被重新分配」這一句，和 vnode 的實際行為不同。

      用 showlog 確認 node4 加入

      單獨一個節點的 log 是 system.log，位置依設定是 /var/log/cassandra 或 $CASSANDRA_HOME/logs。ccm 提供捷徑 ccm node1 showlog，會開啟類似 Unix more 的檢視，可以翻頁和搜尋。在接近結尾的地方輸入 /127.0.0.4 搜尋，就會找到類似下面幾行：

      INFO [GossipStage:1] 2019-11-27 15:40:51,176 Gossiper.java:1222 - Node 127.0.0.4:7000 is now part of the cluster
INFO [GossipStage:1] 2019-11-27 15:40:51,203 TokenMetadata.java:490 - Updating topology for 127.0.0.4:7000
INFO [GossipStage:1] 2019-11-27 15:40:51,206 StorageService.java:2524 - Node 127.0.0.4:7000 state jump to NORMAL
INFO [GossipStage:1] 2019-11-27 15:40:51,213 Gossiper.java:1180 - InetAddress 127.0.0.4:7000 is now UP
      書中只給整體解讀，每一行的讀法是本頁依訊息文字整理的。
      來源訊息字面意思
      Gossiper.java:1222Node 127.0.0.4:7000 is now part of the clustergossip 層把 node4 當成叢集成員。
      TokenMetadata.java:490Updating topology for 127.0.0.4:7000更新 node4 的 topology 資料。
      StorageService.java:2524Node 127.0.0.4:7000 state jump to NORMALnode4 的狀態轉成 NORMAL，也就是 nodetool status 圖例裡的 Normal。
      Gossiper.java:1180InetAddress 127.0.0.4:7000 is now UPnode4 被視為 UP。

      書中的結論是：這幾行顯示 node1 和 node4 成功地 gossip，node4 被視為已啟動，而且是叢集的一員。四行的時間戳記都在 15:40:51，從 ,176 到 ,213，前後只差約 37 毫秒。

      從這一刻起，bootstrap 開始：替 node4 分配 token，並把屬於這些 token 的資料 streaming 給 node4。這個叢集還沒寫入資料，所以實際要搬的資料很少。log 裡節點位址寫成 127.0.0.4:7000，是節點之間通訊用的位址，書中在這一節沒有解釋 7000。

      節點動態進出（Dynamic Ring Participation）

      節點可以停掉再啟動，而不影響叢集的其他部分，前提是複寫因子（replication factor，見 拓撲與複寫）與一致性層級設得合理。下面用 node4 實際看一次。

      書中的做法是先造成一個錯誤，讓一個節點下線，再確認其餘的叢集仍然正常。第一步是用 ccm stop 停掉節點，接著用 ccm status 確認，再用 showlog 看 log。書中把前提寫成「兩節點叢集」，這是前面提過的書中出入。

      本頁補充：ccm stop 與 ccm node4 stop 的差別

      非書中內容，高信心。在 ccm 裡，不帶節點名稱的 ccm stop 與 ccm start 作用在整個叢集（前面的 ccm start 就是啟動全部節點）；ccm node4 stop、ccm node4 start、ccm node1 showlog 則只作用在指定的那個節點。書中這一段寫「ccm stop 指令」而沒有節點名稱，同時卻在講停掉 node4，所以實際該下的是 ccm node4 stop。本頁的模擬器用單一節點的寫法。

      停掉 node4 之後，到另一個節點的 log 裡看，會看到 Cassandra 偵測到它下線：

      INFO [GossipStage:1] 2019-11-27 15:44:09,564 Gossiper.java:1198 - InetAddress 127.0.0.4:7000 is now DOWN

      再把 node4 啟動，回頭看另一個節點的 log。書中說，Cassandra 會自動偵測到那個參與者回到叢集，重新可以服務：

      INFO [GossipStage:1] 2019-11-27 15:45:34,579 Gossiper.java:1220 - Node 127.0.0.4:7000 has restarted, now UP

      書中出入：重啟的節錄裡沒有 state jump 那一行

      書中接著說「state jump to normal」表示 node4 又成為叢集的一員，但上面這份重啟的節錄只有 has restarted, now UP 一行。state jump to NORMAL 出現在 node4 剛加入時的那四行（StorageService.java:2524）。可能是節錄時被省略，也可能是文字在回指前面的 log。重點仍是這一行 has restarted, now UP。

      最後再確認狀態，四個節點都是 UP，書中的結論是「node4 回來了」：

      $ ccm status
Cluster: 'reservation_cluster'

          本頁補充：為什麼 partitioner 與 snitch 必須一致

          書中只寫了規則，沒有說原因，以下是一般推論，非書中內容。partitioner 決定 partition key 轉成哪個 token，也就決定資料落在哪個節點，兩個節點用不同的 partitioner，對同一筆資料會算出不同的歸屬（信心高）。snitch 提供每個節點所屬的資料中心與機架，各節點用不同的 snitch，對「誰在哪個機架」就會各說各話，複本放置與請求路由會互相矛盾（信心中等）。

          Seed 節點

          新節點加入叢集時需要一個 seed 當聯絡點。先看書中的例子（也見下方互動）：A 是 B 的 seed，B 的 seed 清單裡有 A，所以 B 上線時先找 A，從 A 得知叢集的拓撲，也就是哪些主機擁有哪些 token 區段，再以 A 為參考點去取得資料。這個過程叫 bootstrap，有時也叫 auto-bootstrap，因為它是 Cassandra 自動執行的。

          seed 本身是例外，不做 auto-bootstrap。書中給的理由是一個假設：seed 會是叢集裡最早的那批節點。換個角度看，它們前面沒有現成的叢集可以參考，自然沒有東西可以 bootstrap（這是本頁的說明）。

          Snitch

          snitch 蒐集網路拓撲的資訊，讓 Cassandra 能有效率地導引請求。它要弄清楚各個節點彼此之間的相對位置。你用 endpoint_snitch 這個屬性選擇實作，下面的寫法是示意，書中只給了屬性名稱：

          endpoint_snitch: org.apache.cassandra.locator.GossipingPropertyFileSnitch

          snitch 回報的資料中心名稱，就是之後在 keyspace 的 NetworkTopologyStrategy 設定裡要寫的名稱：這個策略用資料中心名稱指定各資料中心的副本數（RF），名稱對不上，副本數就設不到你想要的資料中心。書中在 PropertyFileSnitch 那一段說資料中心與機架名稱都是「同一組名稱」；但書中的 ALTER KEYSPACE 範例只出現資料中心名稱，機架名稱不會寫進 keyspace 設定（本頁補充，由書中範例推得，信心高）。複寫策略的細節在拓撲與複寫。

          ALTER KEYSPACE reservation WITH REPLICATION = {'class' : 'NetworkTopologyStrategy', 'DC1' : '3', 'DC2' : '3'};

          上面這行取自書中拓撲一節的範例。'DC1' 和 'DC2' 必須是 snitch 實際回報的資料中心名稱。

          變更 snitch

          在全新的叢集上，想選哪個 snitch 都可以。一旦已經寫入資料，再更換 snitch 可能需要額外的步驟。書中把這些步驟留給 DataStax 的文件，沒有列出任何一步。（本頁推論：所以最好在建立叢集時就選對。）

          SimpleSnitch

          org.apache.cassandra.locator.SimpleSnitch 是預設的 snitch。它不具機架感知（not rack aware），因此不適合多資料中心的部署。使用它時，keyspace 也應該搭配 SimpleStrategy，這個策略本來就不看節點在哪個機架。

          書中出入：「rack aware」的解釋只有半句

          書中在這裡說「一會兒就解釋 rack aware 是什麼意思」，解釋出現在下一個 PropertyFileSnitch 段落，只有半句：meaning that it uses information that you provide about the topology。本頁的讀法是，rack-aware 的 snitch 知道每個節點屬於哪個資料中心、哪個機架，所以能把這些資訊交給複本放置（NetworkTopologyStrategy 會把副本分散到不同機架）和請求路由使用。SimpleSnitch 沒有這些資訊，所以不是 rack aware。

          PropertyFileSnitch

          org.apache.cassandra.locator.PropertyFileSnitch 是 rack-aware 的 snitch，依據你自己提供的 key-value 屬性來認識拓撲。檔案是 cassandra-topology.properties，書中的範例如下：

175.50.13.200=DC1:RAC1
175.54.35.197=DC1:RAC1

120.55.16.200=DC1:RAC2
120.57.102.103=DC1:RAC2

          這個範例只有一個資料中心 DC1，裡面有 RAC1 與 RAC2 兩個機架，各三個節點。沒有列在檔案裡的節點，會被當作屬於 default 指定的資料中心與機架，這裡就是 DC1 的 RAC1。書中說檔案裡的資料中心與機架名稱，和 keyspace 在 NetworkTopologyStrategy 設定裡用的是同一組名稱；這句偏寬鬆，keyspace 設定裡實際只寫資料中心名稱（見上方 Snitch 一節）。

          Partitioner、Token 與 Virtual Node

          Partitioner 把 partition key 換成 token，token 決定資料落在哪個節點。這一節先看書為什麼只推薦 Murmur3，再看 vnode 如何把 token 環切成許多小段，以及 token 數量怎樣影響各節點分到的比例。

          Partitioners：key 如何對應到 token

          寫入或讀取一筆資料時，Cassandra 先把 partition key 交給 partitioner，換算成一個 token。每個節點負責環上的若干段 token 範圍，token 落在誰的範圍裡，這筆資料就歸誰。副本怎麼擺是複寫策略的事，見拓撲與複寫。所以 partitioner 就是「key 變 token」的規則，它決定資料怎麼分布在叢集裡。

          設定項是 partitioner，值是 partitioner 的完整類別名稱，寫在 cassandra.yaml。

          # 預設的 partitioner
partitioner: org.apache.cassandra.dht.Murmur3Partitioner

          書一開始就警告：資料寫進叢集之後，就不能再換 partitioner，所以偏離預設值要非常小心。原因可以從定義直接推出來。已經寫入的資料，是照舊規則算出 token 再放到節點上的。換了規則，同一個 key 會算出不同的 token，節點上現有的資料就和新規則對不起來。這段推論書中沒有明說。同一章在「Creating a Cluster」也要求 cluster name、partitioner、snitch 在所有節點上必須一致，道理相同：兩個節點若用不同規則算 token，對同一個 key 會給出不同答案。

          Murmur3Partitioner：預設值

          類別是 org.apache.cassandra.dht.Murmur3Partitioner，用 murmur 雜湊把 partition key 算成 token。雜湊結果在 token 空間裡近乎隨機，key 會平均散到整個環上，這是它最大的優點。缺點出在範圍查詢。一段連續範圍內的 key 經過雜湊，會散在環上許多不相干的位置，要掃一個範圍就得到處找，而且結果幾乎是隨機順序回來。書的結論很直接：新叢集一律用 Murmur3Partitioner，其餘三種只為了向下相容才留著。

          RandomPartitioner：被取代的前任

          類別是 org.apache.cassandra.dht.RandomPartitioner，是 Cassandra 1.1 及更早版本的預設。它用 MD5 這種密碼學雜湊算出 BigIntegerToken 來決定 key 在環上的位置。分散資料的效果和 Murmur3 同一類，因為兩者都靠隨機雜湊。差別在成本。密碼學雜湊慢得多，所以 Murmur3Partitioner 接手成為預設。

          OrderPreservingPartitioner：保序的誘惑

          類別是 org.apache.cassandra.dht.OrderPreservingPartitioner，簡稱 OPP。它的 token 是由 partition key 算出的 UTF-8 字串，所以資料在環上的排列順序就是 key 的排序，可以做 range slice。這個性質很誘人，但書列了三個警告：

          • 它並沒有讓範圍查詢比隨機分區更有效率。書只下結論，沒有說明原因。
          • 叢集容易失衡，有些節點存的資料比別人多，形成 hotspot。
          • hotspot 要靠 nodetool move 手動重新平衡節點，維運負擔很重。

          失衡的機制書中沒有展開，這裡補一段說明。節點的範圍事先切好，但 key 在 key 空間裡通常不是均勻分布的。姓氏集中在少數幾個字母，時間戳記一直往最大值長。key 長到哪裡，資料就堆到哪裡。下面的實驗用示意資料把這件事畫出來。

          書中出入：partitioner 不是逐表設定

          OPP 這一段說要「設定 column family 使用保序分區」。column family 是 Thrift 時代的舊詞，而且與本章自己的說法衝突：partitioner 是 cassandra.yaml 裡單一的 partitioner 設定，整個叢集共用。請以本章的說明為準。

          ByteOrderedPartitioner：另一種保序

          它同樣保序，但直接把資料當作原始位元組處理，不像 OPP 先轉成字串。書說這是 OPP 的效能改良版，沒有給套件名稱或其他細節。書也沒有逐項重述它的缺點，但保序的特性相同，上面關於 key 分布與 hotspot 的道理在原則上同樣適用，這是推論，不是書中明說。這段還順帶提到一個 collating order-preserving partitioner，但全章都沒有介紹它。

          Tokens 與 Virtual Node

          Cassandra 預設使用 virtual node（vnode）：一個節點不只有一個 token，而是同時負責許多小段。每個節點有幾個 token，由 num_tokens 決定。書的一般建議是維持預設值。書在這一段沒有寫出預設值是多少，只在側欄提到歷史預設是 256；ccm 實作那一節的輸出也是每個節點 256 個 token，4 個節點共 1,024 個。

          有兩種情況可以調整。給能力比較強的機器調高，讓它多分擔一些；給比較弱的機器調低，讓它少分擔一些。書只講做法，沒有解釋原因。原因來自擁有權的定義。節點擁有的是它所有 token 對應區段的總和，token 越多，平均分到的區段越多，擁有的資料比例也越高。

          要設幾個 vnode？（書中側欄）

          側欄的主張是把 num_tokens 從歷史預設的 256 降到較低的值，例如 16，甚至 8。這是不少有經驗的維運人員的建議，理由是 token 少一點，各 token 區段之間仍有足夠的平衡，但協調變更所需的頻寬少很多。這正好可以拿下面的 token ring 實驗對照。Jira 的 CASSANDRA-13701 提出了在未來版本更改這個預設值的可能。

          書沒有說明「協調變更的頻寬」是怎麼來的。比較合理的解讀是：總 token 數是節點數乘以 num_tokens，每個 token 都是一個要記錄、在節點之間保持一致、在節點加入或離開時重新處理的區段。區段愈多，要協調的對象與工作愈多。這是我的推論，不是書中說法，中等信心。

          這一段處理節點對外的位址與連接埠、資料在磁碟上的位置與磁碟故障時的反應，以及 cassandra.yaml 以外還有哪些啟動檔案。最後附上用 Docker 在本機拼出三節點叢集的做法。

          網路介面

          節點有兩種網路流量，各走各的連接埠和協定。一種是節點之間（internode）的溝通，另一種是用戶端到節點（client-to-node）。cassandra.yaml 替這兩條路各準備了一組設定項，每一組都由同樣三樣東西組成：節點綁定的位址、節點對外宣告的位址，以及連接埠。書中先講節點之間，再講用戶端。

          節點之間

          listen_address 是節點接受其他節點連線的 IP 位址。書中用前面建好的 ccm 叢集示範怎麼查：

          $ cd ~/.ccm
$ find . -name cassandra.yaml -exec grep -H 'listen_address' {} \;
./node1/conf/cassandra.yaml:listen_address: 127.0.0.1
./node2/conf/cassandra.yaml:listen_address: 127.0.0.2
./node3/conf/cassandra.yaml:listen_address: 127.0.0.3

          每個 ccm 節點各有一個自己的 loopback 位址，三個節點就是這樣共用同一台機器。listen_interface 是另一種寫法，直接寫網路介面名稱而不寫 IP。兩個只能設一個，不能同時設定。

          # 二選一，不能同時設定（IP 與介面名稱皆為示意）
listen_address: 10.0.1.12
# listen_interface: eth0

          兩個都沒設時，Cassandra 會用 Java 的 InetAddress.getLocalHost() 決定位址（書中這句寫的是「this property」，指代不明，這裡解讀為兩者都沒設）。細節書中指向 cassandra.yaml 裡的註解。

          broadcast_address 是節點對其他節點宣告的位址，沒設就等於 listen_address。綁定位址和宣告位址平常是同一個，需要分開的典型情況是多資料中心：資料中心內部用私有 IP 通訊，跨資料中心則要用公有 IP。這時 listen_address 留著私有位址，broadcast_address 填公有位址，再把 listen_on_broadcast_address 設為 true，節點就能同時在兩個介面上通訊。

          storage_port 是節點之間通訊用的連接埠，通常是 7000。如果流量會經過公開網路，或雲端部署橫跨多個區域（region），還要設定安全連接埠 ssl_storage_port，通常是 7001。設定它的同時也要設定 internode encryption 的選項，這部分書中留給第 14 章。

          本頁補充：第 14 章對 ssl_storage_port 的說法

          出自第 14 章「Node-to-Node Encryption」的側欄「Deprecated SSL Storage Port」：4.0 之前，節點之間的加密通訊使用獨立的 ssl_storage_port；4.0 起可以在 storage_port 上同時允許加密與未加密連線，安全埠只在把 3.x 叢集升級到 4.0 時才需要（此時要設定 ssl_storage_port，並把 enable_legacy_ssl_storage_port 設為 true）。所以本章對 7001 的建議，在 4.0 要和第 14 章合起來讀。（書中交叉引用，信心高。）

          用戶端到節點

          用戶端用 CQL 和節點溝通的那一層，書中稱為 native transport。rpc_address 是它綁定的 IP 位址，沒設時決定預設值的方式與 listen_address 相同；也可以改設 rpc_interface，用介面名稱綁定。broadcast_rpc_address 是宣告給用戶端的位址，沒設就等於 rpc_address。native_transport_port 預設是 9042。rpc_keepalive 預設為 true，允許用戶端在多個請求之間保持連線開啟。另外還有限制執行緒、連線數與 frame 大小的設定項，書中指向第 13 章。

          Thrift RPC 設定項的棄用

          側欄交代的是 rpc 開頭的名稱從哪裡來。Thrift API 又叫 RPC 介面，是 Cassandra 原本的用戶端介面，舊版 cassandra.yaml 裡 rpc 開頭的設定項大多指它。為了方便從舊版升級，rpc_address、rpc_interface 與 broadcast_rpc_address 這三個名稱沒有換，現在改為套用到 native transport。

          版本先後見圖 1：到 2.2 為止兩者都支援，預設都啟用；3.0 起 Thrift 預設關閉，4.0 完全移除。側欄還說用 CQL 的 native transport 在 0.8 首度加入，這一點和 Apache Cassandra 的 Jira 紀錄不符，見下一則書中出入。

          書中出入：native transport 不是 0.8 加入的

          側欄說 CQL native transport「在 0.8 首度加入」。依 Apache Cassandra 的 Jira，CQL 語言本身在 0.8 出現，當時走 Thrift；專用的二進位 native protocol／transport 是 CASSANDRA-2478（Custom CQL protocol/transport），修正版本為 1.2.0 beta 1。書中可能把「CQL 首度加入」寫成了「native transport 首度加入」。圖 1 照書中寫法標示 0.8，不代表 native transport 真的在 0.8 出現。（非書中內容，信心高。）

          這張圖解釋了一個容易困惑的命名。Thrift 移除之後，用戶端只剩 native transport 一條路，而保留舊名稱的理由，是讓從舊版升級的人不必改設定項的名字。所以今天讀到 rpc_address，要把它當成「CQL 用戶端連進來的位址」。連接埠就不同了，它叫 native_transport_port，沒有 rpc 字樣。rpc_keepalive 也以 rpc 開頭，書中把它歸在用戶端這一組，但側欄只點名上面那三個。

          commit log 與資料檔

          一筆寫入進來，會先在 commit log（進來的寫入的短期儲存，第 6 章介紹過）的檔尾直接續寫一筆，這是最簡單的落地方式。它是保險：節點關機或當機後，下次啟動時把 commit log 重放（replay），資料就不會遺失。書特別強調，重放是 commit log 唯一會被讀的時候，用戶端讀資料不會碰它。位置由 commitlog_directory 決定。

          SSTable（Sorted String Table）放在資料檔裡，位置由 data_file_directories 決定。寫進資料檔不是在寫入當下完成，而是非同步進行；之後 compaction（書中稱 major compaction）會定期把多個 SSTable 合併，合併相同的 key、合併 column，並清掉已過期的 tombstone，空間隨之釋放。這就是為什麼需要上面那份當下就落地的紀錄當保險。

          多個資料目錄與 JBOD

          data_file_directories 可以填多個值，Cassandra 會把資料檔平均分散到這些目錄。如果每個目錄是不同磁碟的掛載點，每顆磁碟各自承載一部分資料檔，這就是 JBOD（just a bunch of disks）部署（JBOD 的意思是不組 RAID，這是一般常識，非書中內容）。書中把 JBOD 的優缺點交給 Anthony Grasso 的一篇部落格文章，本章沒有展開。

          # 路徑與磁碟的對應皆為示意
data_file_directories:
  - /mnt/disk1/cassandra/data
  - /mnt/disk2/cassandra/data
commitlog_directory: /mnt/disk3/cassandra/commitlog

          測試環境不一定要改這些位置。正式環境如果用的是傳統的旋轉式磁碟，書中建議把資料檔和 commit log 放在不同的磁碟上，理由是效能與可用性都能達到最大。

          本頁補充：為什麼要分開磁碟

          非書中內容，高信心。commit log 是循序附加，這是旋轉式磁碟上最快的存取方式；如果資料檔的讀取、flush 與 compaction 也在同一顆磁碟上跑，磁頭要在兩種位置之間來回移動，循序寫入的優勢就被打斷。分開之後，一顆磁碟損壞也不會同時影響這兩者，這對應書中說的可用性。

          Windows 上的儲存檔案位置

          磁碟故障時怎麼辦

          Cassandra 撐得過一顆或多顆磁碟損壞，不會因此讓整個節點掛掉，並提供幾種處理方式可選。disk_failure_policy 管資料檔的故障，commit_failure_policy 管 commit log 的故障。

          用 Docker 建立叢集

          在 Docker 裡建立叢集

          這個側欄接續第 3 章那個單一的 Docker 節點。目標是在本機用多個 Docker 容器組成一個小叢集：叢集跑在自己的網路上，但對外開放標準的 CQL 連接埠，讓應用程式連得進來。下面的步驟依書中順序，指令照書中原樣。

          先建一個 Docker 網路，之後的容器都接在它上面。書中說這可以簡單到只要一行。

          $ docker network create my-network

          第一個節點沒有 CASSANDRA_SEEDS。-p 9042:9042 把容器的 CQL 連接埠發佈到主機，對應側欄所說的對外開放標準 CQL 連接埠。

          $ docker run --name node1 --network my-network -p 9042:9042 -d cassandra

          第一個節點之後的每個節點，都用環境變數 CASSANDRA_SEEDS 指定 seed。node2 以 node1 為 seed。指令照書中原樣，其中 -d 出現了兩次，見下方書中出入。

          $ docker run --name node2 -d --network my-network -p 9042:9042 -d -e CASSANDRA_SEEDS=node1 cassandra

          node3 以 node1 與 node2 為 seed，用逗號分隔。書中在這行之後印了一個 ...，意思是照這個模式繼續加節點。

          $ docker run --name node3 -d --network my-network -p 9042:9042 -d -e CASSANDRA_SEEDS=node1,node2 cassandra

          還有其他環境變數可以覆寫設定，書中說涵蓋 listen 與 broadcast 位址、叢集名稱、vnode 數量（num_tokens）和 snitch。書中只點名下面這幾個變數，位址、叢集名稱與 num_tokens 對應的變數名稱書中沒有給。

          環境變數書中的說明
          CASSANDRA_ENDPOINT_SNITCH設定 snitch，書中的例子是 GossipingPropertyFileSnitch
          CASSANDRA_DC設了 snitch 之後，也可以用它設定資料中心
          CASSANDRA_RACK設了 snitch 之後，也可以用它設定機架

          書中沒有印出把它們組在一起的完整指令。下面是依 -e 的寫法組出的示意，DC 與機架名稱也是示意值。

          $ docker run <other options> -e CASSANDRA_ENDPOINT_SNITCH=GossipingPropertyFileSnitch -e CASSANDRA_DC=DC1 -e CASSANDRA_RACK=RAC1 cassandra

          想用自己的 cassandra.yaml 整份取代，就在映像名稱後面傳 -Dcassandra.config。書中說這是主機上的檔案，但指令本身沒有任何掛載，見下方書中出入。指令照書中原樣；實際使用時還要補掛載，並把路徑改成 file:// 開頭的 URL，見下方的本頁補充。

          $ docker run <other options> cassandra -Dcassandra.config=/path/to/cassandra.yaml

          容器的儲存預設是暫時的，刪掉容器，裡面的資料也一起消失。要讓資料活得比容器久，就把主機上的目錄掛成映像裡 Cassandra 的資料目錄。

          $ docker run <other options> -v /path/to/datadir:/var/lib/cassandra cassandra

          複寫策略

          拓撲決定了每個 keyspace 的複寫策略（replication strategy）怎麼設。複寫策略的工作，是決定哪些節點負責哪些 key 的範圍，換句話說，每一筆資料的副本放在哪裡。

          書在這裡重述第 6 章的規則：第一個副本永遠是「token 所在範圍的擁有者」。partitioner 把 partition key 雜湊成 token（見Partitioner 與 Token），token 落在哪個節點負責的範圍，那個節點就放第一個副本。其餘的副本由複寫策略依拓撲決定。第 6 章介紹的兩種常用策略是 SimpleStrategy 與 NetworkTopologyStrategy。

          SimpleStrategy

          SimpleStrategy 是為單一資料中心設計的。它不知道機架，也完全沒有「資料中心」的概念，做法只有一個：從第一個副本的節點開始，沿著環往下取 N 個節點，N 就是 replication factor（RF）。

          這個機制說明了它的盲點。它只看環上的相鄰順序，所以相鄰的兩個節點剛好在同一個機架，兩個副本就在同一個機架。同一個機架的節點常因電力、冷卻或網路問題一起出事，兩個副本會同時消失。

          資料中心也是一樣。書中的圖 10-1 另外畫了第二個資料中心，用意就是強調這個策略不知道它的存在。如果下一個相鄰節點屬於另一個資料中心，它也會照放，因為它根本不認得資料中心。這是本頁從「沒有資料中心概念」推出來的結果，書中沒有明說，圖 10-1 的圖說還寫成「放在單一資料中心」；實際行為上 SimpleStrategy 是沿整個 token 環取下一批節點，信心高。

          NetworkTopologyStrategy

          NetworkTopologyStrategy（簡稱 NTS）在兩個層級分散副本。第一層是資料中心：你替每個資料中心各指定要放幾份，單一資料中心遇到災難或斷網時，就不會連所有副本一起失去。第二層是機架：同一個資料中心裡，NTS 讓副本落在不同機架，理由和前面一樣，同機架（或類似實體分組）的節點常在同一時間故障。

          容量、硬體與網路

          叢集的形狀決定之後，要估算它需要多少磁碟空間、跑在什麼規格的機器上、網路怎麼接。這一節的重點是一條磁碟空間公式，加上一組硬體與網路規則，每一項都附有可以動手調的實驗。

          估算叢集大小

          決定叢集要多大，要同時考慮三件事：要存的資料量、預期的讀寫負載，以及延遲目標。負載與延遲的調校，書中留到第 13 章，這一小節只處理資料量。節點之後可以增減，但先估出初始大小，以及隨時間成長後的規劃大小，才能預估成本，也才好決定叢集的設定。

          估算步驟

          書中把做法寫成一段散文，下面的編號是本頁加的。

          1. 對每張要支援的表，用第 5 章介紹的公式估出 S。公式依表的欄位與預估列數，算出一份資料（單一副本）放在磁碟上的大小。
          2. 乘上該表所屬 keyspace 的 RF，再乘上對應 compaction 策略的係數 CSF，得到這張表在整個叢集實際需要的磁碟空間 T。
          3. 把所有 keyspace、所有表的 T 加總，得到叢集的總需求。
          4. 總需求除以單顆磁碟的可用空間，得到所需磁碟數。書中說可用空間可以估成磁碟容量的 90%。
          5. 對照每個節點的資料量上限（歷來建議 1 TB），再依預期的成長速度與硬體成本，決定初始叢集大小。

          磁碟空間公式

          T = S × RF × CSF
          書中的公式帶下標：S 與 CSF 是每張表各有一個值，RF 是每個 keyspace 一個值。下標是依各變數的說明還原的。
          符號意義
          T這張表在整個叢集需要的總磁碟空間。
          S這張表一份資料的大小，用第 5 章的公式估出來，單位自選（本頁的試算器用 GB）。
          RF這張表所屬 keyspace 的 replication factor，也就是同一份資料存幾個副本。
          CSF代表這張表 compaction 策略的係數，取值見下一小節。

          兩個 CSF 值

          compaction 策略CSF書中給的理由
          SizeTieredCompactionStrategy（STCS）2最壞情況下，major compaction 需要多一份完整資料的空間。

          儲存

          儲存有幾個要考慮的因素，書中先點出兩項：磁碟的種類，以及磁碟的數量與組合方式。下面的「儲存配置建議」實驗把兩項放在一起看。

          HDD 與 SSD

          Cassandra 兩種磁碟都支援，選哪一種是效能與成本的取捨。SSD 的隨機讀取延遲低，整體效能更好。HDD 也能用，因為 Cassandra 的寫入是追加式的，很適合旋轉式硬碟（HDD）的順序寫入，而且過去 HDD 比較划算。不過 SSD 的價格持續下降，提供 SSD 儲存的雲端業者也愈來愈多。

          Cassandra 靠 disk_optimization_strategy 得知磁碟的種類，要依部署用的磁碟來設。書中只說依部署的磁碟選擇，沒有說明它具體調整了哪些行為。

          # 預設值。使用 HDD 時改成 spinning
disk_optimization_strategy: ssd

          commit log 放哪裡

          放法依磁碟種類而定：使用 HDD 時，datafile 與 commit log 最好放在不同的磁碟；使用 SSD 時，兩者可以放在同一顆。書中只給規則，沒有解釋原因。常見的解釋是（一般機制，非書中文字）：commit log 靠順序追加寫入維持速度，如果和 datafile 共用同一顆旋轉式硬碟，讀取與 compaction 造成的磁頭移動會打斷這種順序寫入。SSD 沒有磁頭尋道的成本，共用就沒有這個問題。

          JBOD 與 RAID

          書中建議一台伺服器掛多顆磁碟。多顆磁碟怎麼用，有兩條路：JBOD（Just a Bunch of Disks，各自獨立使用），或 RAID（Redundant Array of Independent Disks）。書中對兩者的評價是：

          • RAID 0（等量分割，striping）就足夠。Cassandra 的冗餘本來就來自跨節點的複寫，磁碟層級不必再多做一層冗餘。
          • JBOD 的整體效能最好。如果你能逐顆替換壞掉的磁碟，是很好的選擇。

          為什麼要強調能逐顆替換？這是一般機制，非書中文字。JBOD 的每顆磁碟各自獨立，壞一顆只失去那一顆上的資料。RAID 0 把資料等量分割，分散在所有磁碟上，壞一顆整個卷都失效。

          小心共用儲存（SAN 與 NAS）

          標準建議是避免 SAN（storage area network）與 NAS（network-attached storage），可能的例外書中留到雲端部署一節討論，見雲端部署。書中給了三個理由：

          • 擴展：不如本機儲存能有效擴展。
          • 網路頻寬：要透過網路連到實體儲存，會多吃網路頻寬。
          • I/O wait：讀與寫都會增加。

          不要放負載平衡器

          書中不建議在 Cassandra 前面放負載平衡器，雖然它在別的地方很常見，適合把流量分給多個服務或應用程式的執行個體。理由有三：

          • 節點之間：Cassandra 本身有機制，在節點之間平衡網路流量。
          • 用戶端這邊：DataStax 驅動程式會把用戶端的查詢分散到各個複本，負載平衡器幫不上額外的忙。

            自我檢測

            • 公有雲的第一個好處書中明說有條件：多個資料中心要 active-active 並搭配完整的備份策略，才能不另建災難復原系統。第二個好處是資料靠近客戶，使用量有季節性時，各資料中心的叢集還能各自擴縮。
            • AWS 的 region 與 AZ 通常對應資料中心與機架，GCP 的 region 與 zone 對應資料中心與機架，Azure 則是 update domain 等同機架，而 region 對應資料中心只是用詞相同，書中沒有明說。
            • AWS 單一 region 或用 VPC peering 的多 region 用 Ec2Snitch，region 之間走公有 IP 用 Ec2MultiRegionSnitch，有雲外資料中心就用 GossipingPropertyFileSnitch；GCP 用 GoogleCloudSnitch；書中說 Azure 沒有專屬 snitch，用 GossipingPropertyFileSnitch（較新版本的情況見 Azure 一節的補充）。
            • AWS 的 ephemeral storage 便宜但 instance 終止就遺失，EBS 資料持久、可加密，代價是讀取延遲與成本；書中把 I-class 配 ephemeral storage，C-class 配 block storage，Azure 則建議 Premium SSD。
            • 跨 region 的網路是額外成本：AWS 的 Direct Connect 與 VPN 要另外付費，GCP 可用單一全域 VPC，Azure 書中推薦 VNet peering；估算雲端成本時要把運算、節點與備份儲存、網路都算進去。
            • 這一節只給到類別層級的建議，沒有具體型號、磁碟規格或連接埠，也沒有談 Alibaba Cloud、Cloudstack、混合雲與 Kubernetes，實際選型要回頭查各家的官方文件。

            總測驗

            十題涵蓋整章：ccm 與叢集成形、seed 與 snitch、partitioner 與 token、網路、拓撲與容量、雲端。題目問的是機制與取捨，每題作答後會看到解釋。

            • 叢集由 cluster_name、partitioner、endpoint_snitch 三項在所有節點一致來定義，seed 則以每個資料中心至少兩個為目標。
            • ccm 用 loopback 位址在一台機器上模擬多節點叢集；節點加入時由 bootstrap 配發 token 並串流資料，節點下線再回來則由 gossip 自動偵測。
            • snitch 決定 Cassandra 認不認得資料中心與機架；多資料中心要用 rack-aware 的 snitch，名稱還要和 NetworkTopologyStrategy 的設定一致。
            • 新叢集用 Murmur3Partitioner 與 vnodes，書中警告資料寫入後不應更換 partitioner；偏好 vnodes 的原因，是單 token 節點每次增減節點都得重算並手動調整 token。
            • 容量用 T = S × RF × CSF 估算，每顆磁碟只算 90%，單節點資料量以 1 TB 為歷來的建議；網路要有 1 Gbps 以上、同步時鐘、獨立介面，而且不要在前面放負載平衡器。
            • 上雲時，各家的單位對應資料中心與機架的方式不盡相同（AWS 的 region 與可用區書中說「通常」對應，GCP 說「對應」，Azure 是 update domain 對應機架），snitch 的選法也不同：AWS 看區域互連方式，GCP 用 GoogleCloudSnitch，書中說 Azure 沒有專屬 snitch（較新版本的情況，見雲端部署一節的補充）；成本要先估，部署要盡早自動化。
