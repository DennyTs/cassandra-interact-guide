資料模型：從關聯式表格長出 partition

這一節回答兩件事：Cassandra 的資料模型為什麼要有 partition，以及 cluster、keyspace、table、partition、row、column 這六層容器各是什麼。

有關聯式背景的人讀這一章，會遇到兩種詞：全新的（keyspace），和兩邊都有、意思卻略有不同的（column）。CQL 的語法很多地方像 SQL，差異正好藏在這些詞裡。熟悉 Dynamo 或 Bigtable 的人也別太快對號入座：Cassandra 雖然源自這兩者，資料模型已經明顯不同。所以書的做法是從關聯式的術語出發，再一步步換成 Cassandra 的看法。

關聯式模型回顧

先把關聯式的做法擺出來，後面每個 Cassandra 概念都拿它對照。database 是最外層容器，大致對應一個應用程式，裡面放 table。table 有名稱，包含一個以上有名稱的 column。新增資料時，你得替每一個已定義的 column 給值，沒有值就填 null，這筆資料就是一個 row。讀取時可以用 row 的唯一識別（primary key）取單一 row，或用 SQL 條件篩選；更新改的是全部 row 還是一部分，由 WHERE 的條件決定。

「每個 row 都帶著每個 column」是關聯式的前提。Cassandra 在這一點上不同，下面的建構器第 4 步會把兩種做法並排比較。

還缺什麼

partition 的存在理由。Cassandra 設計成資料分散在多台機器上，對使用者卻像單一實例。資料一分散，就需要一個單位來決定「這一群 row 放在哪些節點」；partition key 就是這個單位的識別。同一個 partition 的 row 放在一起，所以只給 last_name，一次查詢就能載入整個 partition。反過來，只給 clustering column（first_name）、沒有 partition key 時，Cassandra 無法直接定位 partition，只能掃過所有 partition 逐一過濾，成本無法預期，因此預設拒絕這種查詢（細節見 Table 一節的 WHERE 實驗）。

Primary key 的組成

第 5 步之後，primary key 不再只是「認出單一 row」。Cassandra 用的是 composite key（也叫 compound key），它描述的是「一群相關的 row」，這一群就叫 partition。composite key 由兩部分組成：partition key，加上選用的一組 clustering column。

K

partition key

決定 row 存在哪些節點上，本身可以由多個 column 組成。每個 partition 由它的 partition key 唯一識別。

C↑

clustering column

控制資料在 partition「內部」儲存時的排序。partition 內的每個 row 由 clustering key 唯一識別。

S

static column

不屬於 primary key；同一個 partition 內的所有 row 共用同一份值。

沒有 clustering column 的話，每個 partition 就只有一個 row。書的範例 table 這樣定義：

CREATE TABLE user (
  first_name text,
  last_name  text,
  title      text,
  PRIMARY KEY (last_name, first_name)
);

PRIMARY KEY (last_name, first_name) 的讀法：第一個 last_name 是 partition key，其後的 first_name 是 clustering column。所以同姓的人在同一個 partition，partition 裡依名字升冪排列。

primary key 要拆成兩個角色，是因為它同時回答兩個不相干的問題：「這個 row 在哪個 partition、放哪些節點」由 partition key 回答；「在這個 partition 裡排第幾」由 clustering column 回答。

      Cassandra's Data Model › Columns
      
    
      Column 的兩個時間屬性
      
    
      每個 column 值都另外帶著 timestamp 和 TTL。兩筆寫入衝突時誰留下來、一個值什麼時候消失，都由這兩個數字決定。
      
  
      

  
  
      
    
      每個值都記得自己何時被寫入
      
    
      
      
      column 是資料模型裡最基本的單位：一個 name 配一個 value，值受定義時指定的型別限制。除此之外，Cassandra 替每個 column 值另外記了兩件事：它是什麼時候被寫入的（timestamp），以及它要保留多久（TTL）。
      
    
      

    

    
      
      
      每次 INSERT 或 UPDATE，Cassandra 都替被寫入的每個 column 值產生一個 timestamp，單位是微秒。兩筆寫入打到同一個值時，就比這個數字，大的留下來。這個規則叫 last write wins，下一節用實驗台操作。
      
      
      先用 writetime() 讀出幾個值的 timestamp：
      
    
      

    
      SELECT first_name, last_name, title, writetime(title) FROM user;
      
    
       first_name | last_name | title | writetime(title)
------------+-----------+-------+------------------
       Mary | Rodriguez |  null |             null
       Bill |    Nguyen |   Mr. | 1567876680189474
      Wanda |    Nguyen |  Mrs. | 1567874109804754

(3 rows)

      UUID 長度有限，並不「絕對」保證唯一，但各語言和作業系統提供的產生工具，唯一性已經足夠。

            Primary key 是永久的。table 建好之後就不能修改 primary key。原因是 primary key 控制資料如何分布在整個 cluster，更重要的是控制資料如何存放在磁碟上。所以上面的 id 只能當普通 column 加進去，沒辦法事後升格成 primary key。
            
    
            
    
            
      
            書上說 CQL 的 uuid 型別是 Type 4，更精確的說法是：uuid 這個 column 型別可以存放任何版本的合法 UUID，產生 Type 4（亂數）的是 uuid() 這個函式。只有 timeuuid 型別限定必須是 Type 1。
            
    
            
    
            
      
            dateOf() 與 unixTimestampOf() 自 Cassandra 2.2 起已被標為 deprecated，建議改用 toTimestamp() 與 toUnixTimestamp()。
            
    
            
  
            

  
  
            
    
            boolean、blob、inet
            
    
            
      
            三個小型別，各有一個容易忽略的細節：輸入與輸出的寫法不一樣。
            
    
            
    
            
      
            
        
            boolean
            
        
            單純的 true / false。cqlsh 接受輸入時不分大小寫，輸出一律是 True 或 False。
            
        
            例：輸入 true，讀出 True
            
      
            
      
            
        
            blob
            
        
            任意的位元組陣列，適合存媒體或其他二進位檔案。Cassandra 不驗證也不檢查裡面的位元組。CQL 用十六進位表示。
            
        
            例：0x00000ab83cf0
            
        
            想把任意文字編進 blob，用 textAsBlob() 函式；輸入細節見 cqlsh 的 HELP BLOB_INPUT。
            
      
            
      
            
        
            inet
            
        
            IPv4 或 IPv6 位址。cqlsh 輸入接受任何合法的 IPv4 寫法（有點或無點，十進位、八進位或十六進位），輸出一律是 dotted decimal。
            
        
            例：讀出 192.0.2.235
            
      
            
    
            
    
            
      
            IPv6 寫成八組、每組四個十六進位數字、以冒號分隔。IPv6 規格允許把連續的零壓縮，所以 SELECT 讀出來的是壓縮後的樣子：

            counter 與冪等性
            
    
            
      
            counter 是 64 位元有號整數，特別之處在於不能直接設定值，只能遞增或遞減。書上說 Cassandra 是少數能做到跨資料中心、沒有競爭問題（race-free）遞增的資料庫之一，常用來追蹤統計：頁面瀏覽數、推文數、log 訊息數。使用上有兩條限制：
            
      
              
        
            • counter 不能是 primary key 的一部分。
              • 
        
            • table 只要用了 counter，primary key 以外的所有 column 都必須是 counter。
              • 
      
            
      
            第二條限制讓 counter 很難和一般資料混在同一張 table 裡，通常自成一張，像下面的 user_visits：primary key 是一個 uuid，其餘只有一個 counter。
            
    
            
    
            CREATE TABLE user_visits (user_id uuid PRIMARY KEY, visits counter);
UPDATE user_visits SET visits = visits + 1
  WHERE user_id = ebf87fee-b372-4104-8a22-00c1252e3e05;
SELECT visits FROM user_visits
  WHERE user_id = ebf87fee-b372-4104-8a22-00c1252e3e05;
            
    
             visits
--------
      1

(1 rows)
            
    
            
      
            user_id 用的是前面指派給 Mary 的那個 uuid。範例沒有先 INSERT：對一個還不存在的 counter 做 UPDATE，就從 0 開始加，所以第一次 +1 之後讀到 1。
            
    
            
    
            
      
            冪等性（idempotence）警告。counter 的遞增與遞減不是冪等的。冪等操作是指執行多次仍得到相同結果的操作。
            
      
            問題出在分散式系統的網路互動可能失敗：節點沒有回覆請求成功還是失敗，用戶端的典型反應就是重試。重試冪等操作沒有風險；重試非冪等操作，結果無法預測，因為你不知道第一次嘗試到底成功了沒有，值可能被加了兩次。這不是致命缺陷，但用 counter 時要心裡有數。

            CQL Types › Collections · Tuples · User-Defined Types
            
    
            一個欄位放多個值：collection、tuple 與 UDT
            
    
            數量不固定的值用 collection，有結構的值用 tuple 或 UDT。這一節逐一操作 set、list、map、tuple 與 UDT，看每一種改資料時 Cassandra 要做多少事。
            
  
            

  
            
    
            Collection：set、list、map
            
    
            
      
            想讓 Mary 有多個 email，最直覺的做法是再加 email2、email3 欄位。欄位個數因此寫死在 schema 裡：有人需要第四個 email，就得再改一次 table，程式也要跟著改。書上的評語是擴充性差、容易大量重工。
            
      
            collection 把這些值當成一組，放在同一個 column 裡，元素個數不必事先決定。CQL 有三種：set（一組元素）、list（有序清單）、map（鍵值對）。set 的元素可以是前面那些簡單型別，也可以是 UDT，甚至是另一個 collection；map 的 key 與 value 可以是 counter 以外的任何型別。下面三個 column 都加在 user table 上：
            
    
            
    
            ALTER TABLE user ADD emails set<text>;
ALTER TABLE user ADD phone_numbers list<text>;
ALTER TABLE user ADD login_sessions map<timeuuid, int>;
            
    
            
      
            操作台的三個分頁各自保留狀態。所有指令都只動 Mary 這個 row，所以 WHERE 一律是 first_name = 'Mary' AND last_name = 'Rodriguez'。
            
    
            

    
            
      
            
        實驗台

            set 儲存時沒有順序，回傳時依字母排序，所以 chips 永遠是排好的，跟加入的先後無關。

              emails = { 'mary@example.com' }
              
            
            
            
            
            
              加入元素
              emails = emails + { … }
              
            
                
                
              
            
            
            
            
            
              移除元素
              emails = emails - { … }
              
            
                
                
              
            
            
            
            
            
              清空
              emails = {}
              
            
            
            
            
            
              重試加入
              把上一句「加入元素」原樣再送一次
              
            
            
            
            
            
              回到起點
              emails = { 'mary@example.com' }
              
            
            
            
          
            
          
            
            
            加入元素時 Cassandra 不必先讀出既有內容，只要把新元素寫進去。同一個元素送兩次，結果跟送一次相同，所以 set 的加入可以安全重試（冪等的意思見 Counter 一節）。
            
          
            
          
            
            
            書上「加入元素」那一步的輸出，把新 email 印成 mary.mcdonald.AZ@gmail.com，與指令裡的 mary.rodriguez.AZ@gmail.com 不一致。這裡以指令為準。
            
          
            
          
            
            
            書上只說可以用 emails = {} 清空整個 set，沒有印出讀回的結果。補充：Cassandra 不會把空的 collection 當成一個值保存，所以清空之後讀回來是 null。這個分頁、list 與 map 都一樣，操作台因此在變空時顯示 null。
            
          
            
        
            

        
        
            
          
            
            
            
              
            
              
            cqlsh 讀回的 phone_numbers
            
              
            
              
            list 預設依插入順序存放，每個元素有索引。附加放在最後，前置放在最前，依值移除會拿掉所有相符的元素。
            
            
            
            
            
              
            cqlsh · phone_numbers
            
              
            
            
            
          
            
          
            
            
          
            
          
            
            
            
              整個指定
              phone_numbers = [ '1-800-999-9999' ]
              
            
            
            
            
            
              附加 重試會重複
              phone_numbers = phone_numbers + [ … ]
              
            
                
                
              
            
            
            
            
            
              前置
              phone_numbers = [ … ] + phone_numbers
              
            
            
            
            
            
              依索引取代 可能要先讀出整個 list
              phone_numbers[i] = …
              
            
                
                
              
            
            
            
            
            
              依值移除
              phone_numbers = phone_numbers - [ … ]
              
            
                
                
              
            
            
            
            
            
              依索引刪除 可能要先讀出整個 list
              DELETE phone_numbers[i] FROM user …
              
            
                
                
              
            
            
            
            
            
              回到起點
              phone_numbers = [ '1-800-999-9999' ]，再附加 '480-111-1111'
              
            
            
            
          
            
          
            
            
            按「重試上一個附加」模擬回應遺失後的重試：同一句 + [ … ] 送了兩次，list 就有兩個一樣的元素。為什麼 list 比較貴、重試為什麼出事，下一小節拆開講。
            
          
            
          
            
            
            list 變空時，讀回來同樣是 null：Cassandra 不保存空的 collection（見 set 分頁的補充）。
            
          
            
        
            

        
        
            
          
            
            
            
              
            
              
            cqlsh 讀回的 login_sessions
            
              
            key 是 timeuuid，value 是這次登入的秒數。timeuuid 本身帶著產生時的時間，小字是從 key 解出來的。連續兩次 now() 產生的 key 只有第 1 組（時間的低位）不同，後面各組完全相同：時間欄位往前走了，所以兩個值不會重複。書上的例子是 839b2660… 與 839b2661…，只差一格（100 奈秒）。
            
            
            
            
            
              
            cqlsh · login_sessions
            
              
            
            
            
          
            
          
            
            
            
              整個指定
              login_sessions = { now(): 13, now(): 18 }
              
            
            
            
            
            
              加入一筆
              login_sessions = login_sessions + { now(): … }
              
            
                
                
              
            
            
            
            
            
              依 key 操作單一項目
              login_sessions[key] = n　／　DELETE login_sessions[key] FROM user …
              
            
                
                
                
                
                
              
            
            
            
          
            
          
            書上只提到可以用 key 參照 map 裡的單一項目。上面「依 key」的兩句是標準 CQL 的寫法。
            
          
            
            
            刪掉最後一筆之後，map 讀回來也是 null：Cassandra 不保存空的 collection（見 set 分頁的補充）。
            
          
            
        
            
      
            
      
            三種 collection 的共通點是一個 column 裡放不固定個數的元素；差別在於元素怎麼識別：set 靠值本身，list 靠位置，map 靠 key。
            
    
            
  
            

  
            
    
            為什麼 list 比較貴，附加又為什麼不冪等
            
    
            
      
            list 的元素依「位置」存放。要取代第 1 格或刪掉第 0 格，Cassandra 可能得先把整個 list 讀出來，在記憶體裡改好，再把整個 list 寫回去。set 沒有這個負擔：加入元素只是把新元素寫進去，不必先看裡面已經有什麼。list 的元素一多，兩者的差距就大。
            
    
            
    

    
            
      
            昂貴的 list 操作（書的重點框）：更新或刪除 list 中特定項目時，Cassandra 可能必須讀出整個 list、執行操作、再把整個 list 寫回去。元素多時這很昂貴，所以許多人偏好 set 或 map，尤其是 collection 的內容會被更新的時候。
            
    
            

    
            
      
            附加的問題在另一個地方。用戶端送出 phone_numbers + [ '480-111-1111' ] 之後，如果沒收到回應，它不知道這次寫入到底成功了沒有，慣常的反應是重試。set 遇到重試沒事：同一個元素加兩次，還是只有那一個元素。list 則會多出一個一樣的元素，因為兩次附加就是兩次「放到最後」。
            
      
            為什麼分散式系統裡重試是常態、「冪等」到底指什麼，Counter 一節已經解釋過，這裡不重複。書上把「往 list 加入項目」和 counter 的遞增、遞減並列為非冪等的 CQL 操作。
            
    
            

    
            
      
            
        
            操作需要先讀嗎重試安全嗎
            
        
          
            emails = emails + { … }
            set 加入元素            		不需要安全：同一元素加兩次結果不變
            
          
            phone_numbers + [ … ]
            list 附加            		書上未說明不安全：重試可能讓同一元素出現兩次
            
          
            phone_numbers[i] = …
            list 依索引取代            		可能需要（讀出整個 list）書上未說明
            
          
            DELETE phone_numbers[i] …
            list 依索引刪除            		可能需要（讀出整個 list）書上未說明
            
                    
      
            
    
            

    
            
      
            實務上的結論跟書一致：collection 的內容會被更新時，優先選 set 或 map。同一種冪等問題也出現在 counter，見 Counter 一節。
            
    
            
  
            

  
            
    
            Tuple：固定長度、靠位置辨認的一組值
            
    
            
      
            接著要記錄 Mary 的實體地址。只用一個 text column 當然存得下，但從字串裡拆出街道、城市、郵遞區號的工作就落到應用程式身上。比較好的做法是定義一個結構，讓各個部分保持完整。Cassandra 給了兩個選項：tuple 與 UDT。
            
      
            tuple 是固定長度、各元素型別可以不同的一組值。書上先用 tuple 加了一個 address column，並寫入 Tucson 的地址：
            
    
            
    
            ALTER TABLE user ADD address tuple<text, text, text, int>;
UPDATE user SET address = ('7712 E. Broadway', 'Tucson', 'AZ', 85715)
  WHERE first_name = 'Mary' AND last_name = 'Rodriguez';
            
    
            
      
            tuple 有兩個缺點：
            
      
              
        
            • 每個值都沒有名字，只能靠記住位置來分辨哪格是街道、哪格是州，用起來很彆扭。
              • 
        
            • 不能只更新其中一個欄位，要整個 tuple 一起重寫。
              • 
      
            
      
            因為有更好的替代品 UDT，tuple 在實務上很少用。書接著就把這個 column 丟掉：
            
    
            
    
            ALTER TABLE user DROP address;
            

    
  
            

  
            
    
            UDT 與 frozen
            
    
            
      
            UDT（user-defined type）讓你自己定義型別。它比 tuple 好用的地方是用名稱而不是位置指定值：
            
    
            
    
            CREATE TYPE address (
  street   text,
  city     text,
  state    text,
  zip_code int
);
            
    
            
      
            UDT 的範圍是定義它的 keyspace，也可以寫成 CREATE TYPE my_keyspace.address。執行 DESCRIBE KEYSPACE my_keyspace 會看到 address 是 keyspace 定義的一部分，同一個 keyspace 的多個 table 都能用它。
            
      
            Mary 可能有好幾個地址，所以接下來想用 map<text, address> 存 "home"、"work" 等具名地址。下面的操作台照書上的順序走一遍：先撞牆，再修正。
            
    
            

    
            
      
            
        實驗台
        撞牆再修正
        一步一步執行，也可以退回上一步
      
            
      
            
        
            
          
          
          
          步驟 1 / 4
          
        
            
        
            
          
            
            
            cqlsh · my_keyspace
            
            
            
          
            
          
            
            
            TYPE address
            
            
            user.addresses
            
            
            Mary 的 addresses
            
          
            
        
            
      
            
      
            
    
            

    
            
      
            錯誤訊息的意思是：不允許在 collection 裡面放 non-frozen 的 collection。書上的解釋是 UDT 被視為一種 collection，因為它的實作方式類似 set、list、map，所以 map<text, address> 等於要在一個 collection 裡再放一個 collection。修正的方法是把裡面那層標成 frozen。
            
    
            

    
            
      
            Freezing collections（書的重點框）
            
      
              
        
            • 2.2 之前的版本不完整支援 collection 巢狀：巢狀的 collection 實作上被序列化成單一物件，所以無法存取裡面的個別屬性，整個巢狀 collection 必須整體讀、整體寫。
              • 
        
            • frozen 是當時引入的向前相容機制。把巢狀的 collection 標成 frozen，Cassandra 就把那個值當成一整塊二進位資料（blob）儲存。
              • 
        
            • 書預告，將來完整支援巢狀 collection 時，會有「解凍」的機制讓個別屬性可以存取。
              • 
        
            • frozen 的 collection 也可以用在 primary key 裡。
              • 
      
            
    
            

    

    
            
      
            frozen 的值在儲存時是一整塊，能做的操作就是整塊換掉，所以 city 一個欄位的修改，必須連同 street、state、zip_code 一起寫回 'home'。
            
    
            

    
            
      
            書寫成之後，後續版本有了進展。自 Cassandra 3.6 起，直接作為 column 的 UDT 可以是 non-frozen（它的欄位如果是 collection，那個欄位自己必須是 frozen），因此能只更新單一欄位，例如 UPDATE … SET addr.city = '…'。但 UDT 放在 collection 裡面時（如本例的 map<text, address>）仍然必須 frozen。
            
    
            

    
            
      
            
        
            tupleUDT
            
        
          
            欄位識別靠位置靠名稱

              INSERT 多寫的那個 row marker
              
      
              書上說 insert 與 update 沒有根本差別，唯一的例外留到 lightweight transaction 再談。儲存層其實還有一個差別，而且它正好解釋了 TTL 一節的一個現象。
              
      
              INSERT 除了寫入各 column 的值，還會替這個 row 記下一筆「此 row 存在」的標記，通常叫 row marker，它有自己的 timestamp 與 TTL。UPDATE 只寫你 SET 的那些 column，不寫這個標記。平常兩者看不出差別，以下兩種情況才會浮現：
              
      
                
        
              • 所有非主鍵 column 都消失之後。用 INSERT 建立的 row 還查得到，只剩主鍵，其餘顯示 null。只靠 UPDATE 建立的 row 沒有 row marker，最後一個 column 被刪除或過期時，整個 row 就查不到了。
                • 
        
              • INSERT … USING TTL。TTL 也套用在 row marker 上。書上 Jeff Carpenter 的例子只給了兩個主鍵欄位，沒有任何可以過期的普通 column，60 秒後整個 row 卻不見了，過期的就是這個 row marker。
                • 
      
              
    
              
    
              -- 兩個 row 都只有一個非主鍵 column
INSERT INTO user (first_name, last_name, title) VALUES ('Ann', 'Lee', 'Dr.');
UPDATE user SET title = 'Dr.' WHERE first_name = 'Ben' AND last_name = 'Lee';

-- 把那個 column 刪掉
DELETE title FROM user WHERE last_name = 'Lee' AND first_name = 'Ann';
DELETE title FROM user WHERE last_name = 'Lee' AND first_name = 'Ben';

SELECT * FROM user WHERE last_name = 'Lee';
-- 只剩 Ann（title 顯示 null）：她有 row marker。Ben 那個 row 已經查不到。
              
    
              
      
              Ann 與 Ben 是為了說明而編的示意資料，不是書中範例。這個行為本身屬於儲存引擎的既定設計，把握程度高；如果你們的資料是從只用 UPDATE 寫入的舊程式搬過來的，這一點值得在測試環境實際跑一次確認。
