步驟 1 · Conceptual Data Modeling

先把旅館訂房的世界畫出來

資料模型對 Cassandra 專案成敗的影響，比任何設定或調校都大。它決定應用程式跑得多快，也決定叢集好不好維運。書的開場引用了 Patrick McFadin 的一句話，意思是你採用的資料模型，是能否成功使用 Cassandra 最重要的因素。

所以這一章教的是建模的流程與表示法。作者用一個旅館訂房的範例，從頭走完整個流程，後續章節會繼續在同一個模型上建應用程式。章末還會介紹幾個管理 CQL 腳本的工具。

第一步還不需要想 Cassandra。先畫出一個在關聯式世界一看就懂的 domain model，之後再想怎麼把它對應到 Cassandra 的分散式雜湊表模型。

為什麼選旅館訂房

書裡挑範例的標準有三個：

  • 夠複雜，能展示各種資料結構與設計模式。
  • 又不會複雜到被細節淹沒。
  • 人人都熟悉，讀者可以專心看 Cassandra，不必先學一套業務領域。

概念領域裡有什麼

  • hotel（旅館）
  • room（房間）：每間旅館有一組房間。
  • rate（房價）與 availability（可訂狀態）：每間房都有。
  • guest（房客）：入住旅館的人。
  • reservation（訂房）：為房客訂下的紀錄。
  • point of interest, POI（景點）：旅館附近的公園、博物館、購物商場、紀念碑等，房客住宿期間可能想去。

hotel 與 POI 都需要 geolocation（地理位置）資料，這樣才能在地圖 mashup 上找到它們，並計算彼此的距離。

範例的簡化

真實的旅館系統複雜得多。房價就是個好例子，它變動極大，要考慮的因素也很多。這一章刻意把它簡化，只求範例夠有趣、涵蓋到重點，又不會讓讀者失焦。

概念模型到這裡就夠了。下一節先看同一份 domain 在關聯式資料庫裡會怎麼設計，再看 Cassandra 為什麼得換一套想法。

對照 · RDBMS Design

換成關聯式資料庫，會怎麼設計

同一份 domain 放進關聯式資料庫，起手式很固定：建成一組正規化的資料表，用 foreign key 去參照其他表的資料。先看這條路會長成什麼樣子，後面比較 Cassandra 的差異才有基準。

概念模型裡的多對多關係，關聯式世界沒辦法直接表達，得靠 join table。書中 Figure 5-2 的關聯式模型有幾張這樣的表，對應四組多對多：hotels 與 points of interest、rooms 與 amenities、rooms 與 availability，以及 guests 與 rooms（透過 reservation）。

六個設計差異

步驟 2 · Defining Application Queries

先列出應用程式要問的九個問題

Cassandra 的建模從查詢開始。這一步要產出的東西很具體，一份有編號的查詢清單，加上一張把它們串起來的 workflow。後面每一張表，都是從清單裡的某一條查詢長出來的。

素材從哪裡來？書的做法是看 UI 設計。假設你已經和利害關係人談過，UX 設計師也畫好了關鍵 use case 的畫面（wireframe）。畫面上每一塊要顯示的資料，背後都有一個查詢，也就是使用者給了什麼、系統要回什麼。把這些問題逐一列出來，就是查詢清單。

旅館範例的找房流程有五個查詢（Q1 到 Q5）。使用者先挑景點，看附近有哪些旅館，點進某間旅館看詳情，接著看這間旅館附近的景點，或指定日期找可訂的房間，最後查某間房的房價與設施。

書中提示
Number your queries. 給每個查詢一個編號（Q1、Q2…）。之後畫圖、設計表、寫 comment 都可以直接用編號引用，不必每次重寫整句。本頁後面的每張表也都帶著它支援的查詢編號。

從找房走到訂房

要讓客人真的能訂房，還得選房、輸入房客資料，所以應用程式還要處理 reservation 和 guest。這裡的重點是思考角度。不要只想「這些資料要怎麼寫進去」，也要想「之後誰會用什麼條件把它查出來」。

建模的人很容易先替 reservation 和 guest 設計好存放資料的表，再回頭想怎麼查。查詢優先要反過來，先把下游的查詢寫出來，表跟著查詢走。

讀到這裡，你可能一直在想旅館和景點的資料是從哪裡來的。書說先不急，之後會處理。訂房階段另外有四個查詢（Q6 到 Q9），和找房的五個一起放在下面的圖裡。

每一步解鎖下一步

這張 workflow 的意義在於，每一步完成的任務會解鎖後面的步驟。以 Q1 為例，「看景點附近的旅館」會讓應用程式拿到幾間旅館，以及每間旅館唯一的 key。使用者選定一間，這個 key 就能拿去做 Q2，取得旅館的詳細資料。也就是說，Q1 的結果必須帶著 Q2 需要的輸入，流程才接得起來。

訂房這個動作會產生一筆 reservation 紀錄。之後房客和旅館員工都能透過其他查詢找到它，這就是 Q6 到 Q8 的來源。設計查詢清單時，可以順著 workflow 檢查，每個查詢需要的輸入，前一步是不是已經交出來了。

查詢要服務所有利害關係人

書中提示
Design queries for all stakeholders. 查詢要支援應用的各種利害關係人。不只客戶，還有員工，甚至分析團隊、供應商等。

旅館範例裡，Q7 讓旅館員工依日期看訂房，了解哪些日期客滿、哪些日期訂房不足。客人手上沒有確認碼時，可以改用姓名查（Q8），可能是客人在自助網站上查，也可能是客服人員代查。再用 guest_id 看房客資料（Q9）。每個查詢背後的表怎麼設計，留到下一節。

書中不一致
這一節有三處前後對不上，這裡照實記錄，後面的表一律以 schema 為準。
  • Q7 與 Q8 的對應前後不一。查詢清單把 Q7 寫成依旅館與日期（含房客姓名），Q8 寫成依房客姓名。schema 的 comment 也是這樣，reservations_by_hotel_date 是 Q7，reservations_by_guest 是 Q8。但後面「Reservation Logical Data Model」一節的內文，把 reservations_by_guest 稱為 Q7，把依旅館與日期查的表稱為 Q8。書中那則提示原文把 Q8、Q9 連到員工等角色，看起來沿用的是內文這一套。本頁採用查詢清單加 schema comment 的對應，因為這兩處彼此一致。
  • Q7 提到房客姓名，但表裡沒有。reservations_by_hotel_date 只有 guest_id，沒有任何姓名欄位。
  • Q5 提到房價（rate），但 schema 沒有房價欄位。amenities_by_room 只存設施。書在概念模型那一節說過，真實世界的房價計算很複雜，這裡刻意簡化。

查詢清單和 workflow 到這裡就定下來了。下一步進入邏輯模型，為這九個查詢各設計一張表，決定每張表的 partition key（分割區鍵）與 clustering column（叢集欄位）。

步驟 3 · Logical Data Modeling

邏輯模型：每個查詢一張表

Q1 到 Q9 列好之後，建模變成一連串很機械的決定。每個查詢對應一張表，再替這張表選 primary key（主鍵）。Primary key 一旦定下來，這張表能回答什麼問題、列在 partition（分割區）裡怎麼排，就都決定了。

三條規則

邏輯模型的做法是每個查詢一張表，這些表要承接概念模型裡的 entity 與 relationship。具體分成三條規則。

  1. 每個查詢一張表。表名先放查詢的主要 entity。如果是用另一個相關 entity 的屬性去查，就用 _by_ 接在後面。Q1 要找「某景點附近的旅館」，主要 entity 是旅館，查詢條件是景點，所以叫 hotels_by_poi。
  2. 用查詢決定 primary key。查詢要拿來比對的屬性，放進 partition key（分割區鍵）。再加上 clustering column（叢集欄位），一方面保證每一列唯一，一方面決定 partition 內的排序。
  3. 補上其他屬性。把查詢需要顯示的屬性加進來。如果某個屬性在同一個 partition key 底下每一列都一樣，就標成 static 欄位。
書中提示

Primary key 的重要性。Primary key 的設計非常重要。它決定每個 partition 存多少資料、資料在磁碟上怎麼組織，也就影響 Cassandra 處理讀取查詢的速度。

Chebotko 表示法

社群裡有好幾種資料模型的圖示法。本書採用 Artem Chebotko 推廣的版本，因為它簡單，又能清楚畫出查詢和表之間的關係。邏輯圖裡每張表是一張卡片，標題是表名，下面列出欄位，primary key 的欄位用符號標記。

一步步推導 hotels_by_poi 的 primary key

下面用 Q1 把三條規則走一遍。每一步同時更新三個地方：左邊是這一步的推理，中間是逐步成形的表卡，右邊是同一個 partition 內部的樣子。頁面載入時停在最後一步，按「從頭推導」可以回到第 1 步。

書中不一致

書中解釋 hotel_id 的那句話，說的是為每間旅館建立一個「唯一的 partition」。依 schema，partition 仍然是每個景點一個，唯一的是 partition 內的 row。另外，講 Q4 的那一段把 partition key 寫成 primary key，從 PRIMARY KEY ((hotel_id), date, room_number) 看，指的是 partition key。這兩處都是用語不夠精確，不影響設計。

書中提示

讓 primary key 保持唯一。設計 primary key 時，要確定它定義出一個唯一的資料元素，否則有不小心覆寫資料的風險。上面第 2 步的切換就是這個提示的實際樣子。

旅館邏輯模型

Q1 到 Q5 各一張表，合起來就是書中的 Figure 5-5。卡片之間的箭頭標的是「下一張表要支援的查詢」，箭頭旁邊的欄位是上一步的結果帶給下一步的 key。點任何一張表，下面會說明它為什麼長這樣。

沒有的表

這個模型裡沒有 rooms 表，也沒有 amenities 表，而關聯式設計裡兩張都有。原因是 workflow 裡沒有任何查詢需要直接存取它們。房間只是以「某旅館某日期的可訂狀態」出現（Q4），設施只在選定某間房之後才會被查（Q5）。

寬分割區模式與範圍查詢

Sidebar

寬分割區模式（wide partition）。available_rooms_by_hotel_date 就是這個模式的實例。做法是把多筆相關的 row 放進同一個 partition，一次查詢就能快速取得 partition 內的多筆 row。在其他支援類似模型的資料庫，這個模式有時叫 wide row pattern。從 Cassandra 的角度，說 wide partition 比較精確。

訂房這一側的三張訂房表（reservations_*）是反正規化設計：同一筆訂房的資料存成三份，只是 key 不同，各自服務一個查詢。guests 則是房客資料的單一位置。把滑鼠移到（或用 Tab 停在）任何一個欄位，其他表裡同名的欄位會一起亮起來。

每張表替誰服務

替所有利害關係人設計查詢。查詢要支援應用程式的各種使用者，不只客戶，還有員工，甚至分析團隊、供應商等。

以本頁的訂房表為例，旅館員工看訂房和客人找自己的訂房，就是兩種不同的利害關係人。書中這則提示舉的是 Q8、Q9，看起來沿用了內文那一套編號；依本頁採用的對應，旅館員工用的是 Q7。

書中不一致

Q7 和 Q8 的編號。查詢清單寫 Q7 是依旅館、日期、房客姓名，Q8 是依房客姓名查所有訂房。Schema 的 comment 也是 reservations_by_hotel_date 對 Q7、reservations_by_guest 對 Q8。但這一節的內文把兩者寫反了。本頁採用查詢清單與 schema comment 的對應，因為這兩處彼此一致。

reservations_by_guest 的 clustering column。內文說把 guest ID 納入為 clustering column，可是 schema 是 PRIMARY KEY ((guest_last_name), hotel_id)。Clustering column 實際上是 hotel_id，guest_id 只是一般欄位。

延伸推算

依這個 schema 的 CQL 語意推論：同姓的兩位房客（例如都姓 Nguyen）在同一間旅館（例如 AZ123）各有一筆訂房，這兩筆的 primary key 會相同，後寫入的會覆蓋先寫入的。這正好呼應前面「primary key 要唯一」的提示。書中沒有討論這個後果，這是推論，不是書中的結論。

模式與反模式

和其他軟體設計一樣，Cassandra 資料建模也有知名的 pattern 與 anti-pattern。旅館模型已經用了最常見的寬分割區模式。這裡再看一個值得學的，和一個要避開的。

時間序列模式

時間序列模式（time series pattern）是寬分割區模式的延伸。它把特定時間間隔內的一系列量測值，存放在寬 partition 裡，量測的時間是 key 的一部分。常見的領域有商業分析、感測器資料管理、科學實驗。

它也適用於量測以外的資料。書中舉了銀行的例子。

本頁的解讀

書中原文寫的是量測時間作為 partition key 的一部分，沒有再展開。對照本章後面的分桶做法，可以這樣理解：時間的粗粒度（例如月份）放進 partition key，讓 partition 不會無限長大；細粒度的時間戳當 clustering column，讓列在 partition 內依時間排序。這是本頁的解讀，不是書中的說明。

佇列反模式

佇列反模式（queue anti-pattern）是新手常掉的陷阱：把 Cassandra 當佇列用。每個項目帶著時間戳存在寬 partition 裡，從尾端加入、從前端讀取，讀完就刪除。這看起來很吸引人，尤其它和時間序列很像。

問題出在刪除。被刪除的項目不會消失，而是變成 tombstone（墓碑），留在 partition 的前端。下次從前端讀取時，Cassandra 必須先掃過這些 tombstone。時間一長，tombstone 越積越多，讀取效能就越來越差。

注意

任何依賴刪除資料的設計，都可能是效能不佳的設計。Tombstone 的細節在 Chapter 6。

到這裡，九張表的 primary key 都定下來了，邏輯模型完成。下一步是替每個欄位指定型別、決定表放在哪個 keyspace，這就是實體模型。

步驟 4 · Physical Data Modeling

實體資料模型，替每個欄位選型別

邏輯模型決定了每張表有哪些欄位、哪些是 key。實體模型接著替每個欄位指定 CQL 型別，並決定每張表放進哪個 keyspace。

做法很機械：把邏輯模型的表一張一張走過去，替每個欄位選型別。可用的型別就是 Chapter 4 學過的那些，包括基本型別、collection 和 UDT。走的過程中，如果發現有一組欄位總是一起出現，可以新增一個 UDT 把它們包起來，讓設計簡單一點。

型別選完還沒結束。下一步要用這個模型做容量計算、實際測試，再依結果調整，所以實體模型在這一步還不算定稿。

實體圖在邏輯圖上多了什麼

書的 Chebotko 實體圖是在邏輯圖上補資訊，一共四類：

  • 每個欄位的型別。
  • 每張表所屬的 keyspace。
  • 用 collection 與 UDT 表示的欄位，會有視覺記號。
  • static 欄位與 secondary index 欄位的標示。secondary index 留到 Chapter 7 再談，本章的 schema 裡沒有用到。

這些記號放在邏輯圖上也不是不行，但書認為它們通常屬於實體建模的考量。

九張表，兩個 keyspace

表要有 keyspace 才能存放。為了讓設計簡單，書只建了兩個：hotel 放旅館與可訂狀態的表，reservation 放訂房與房客的表。

UDT address

旅館的地址有街道、城市、州或省、郵遞區號、國家這幾個部分。把它們包成一個叫 address 的 UDT，表裡就只需要一個地址欄位。

實體圖也把 address 畫成一個方塊，名稱後面加星號。星號表示它是 UDT；它不是資料表，方塊裡沒有 primary key 欄位。hotels 與 hotels_by_poi 都用到它，guests.addresses 則把它放進 map 裡。

書中提示

善用 UDT。UDT 常用來把不屬於 primary key 的欄位做邏輯分組，address 就是例子。UDT 也可以放進 collection 裡，進一步降低設計複雜度。另外要記得，UDT 的範圍是定義它的 keyspace。

書中不一致

書在說明 hotels 表時，說這個 address 類似 Chapter 4 建過的 UDT，但欄位其實不同。Chapter 4 的版本是 street、city、state、zip_code（int）。本章 schema 的版本是 street、city、state_or_province、postal_code、country，五個全是 text。這一頁一律採用本章 schema 的版本。

Sidebar

用唯一識別碼當參照。像 hotel_id 這種屬性，用 uuid 是合理的。但書為了讓範例簡單好讀，多半用 text 當識別碼。

text 短代碼：旅館業習慣用 AZ123、NY229 這種短代碼指稱物業，書中就拿它當 hotel_id，也承認這種代碼不一定全域唯一。

uuid：用唯一 ID 去參照資料，並在代表其他 entity 的表裡用這些 uuid 當參照，可以降低不同 entity 之間的耦合。如果是微服務架構，每種 entity 由獨立的服務負責，這樣做特別有效。

reservation keyspace 的實體模型

邏輯模型有三張反正規化的訂房表：依確認碼、依房客、依旅館與日期。實體模型的第一版假設這份反正規化由應用程式手動管理，也就是同一筆訂房要自己寫進三張表，三份資料一致與否也由應用程式負責。書在 Chapter 7 會回頭考慮改用 materialized view（具體化檢視）。

步驟 5 · Evaluating and Refining

評估與調整：先算 partition 會長多大

實體模型畫完之後，要先確認每張表的 partition 不會太寬，也要估出需要多少磁碟。如果某個 partition 看起來會失控，就回頭調整 partition key 把它拆小。本節依序處理三件事：算 cell 數、算磁碟用量、拆分過大的 partition。

計算 partition 大小

書用 cell（值）的數量衡量一個 partition 有多大。Cassandra 的硬上限是每個 partition 20 億個 cell，不過在碰到上限之前，效能問題通常就先出現了。書的建議是一個 partition 不要超過 100,000 個 cell。

cell 數可以用下面的公式算。

Nv = Nr × (Nc − Npk − Ns) + Ns
Nv
partition 內的值（cell）數量
Nr
partition 內的 row 數
Nc
資料表的欄位總數
Npk
primary key 欄位數（partition key 加 clustering column）
Ns
static 欄位數，整個 partition 只存一份

括號內的 Nc − Npk − Ns 是「每一列的值數」。static 欄位不隨 row 增加，所以單獨加在最後。

欄位數相對固定（雖然執行期可以 ALTER TABLE），所以 partition 大小的主要驅動因素是 row 數。判斷 partition 會不會過大，看的就是 Nr。20 億聽起來很大，但在每毫秒量測幾十到幾百個值的感測器系統裡，數字累積得很快。

書拿 available_rooms_by_hotel_date 當例子。它有 4 個欄位，其中 3 個在 primary key 裡，沒有 static 欄位，所以 Nv = Nr × (4 − 3 − 0) + 0，cell 數等於 row 數。接著要估 row 數。這張表為每間旅館、每個房間、每一晚各存一列。書假設系統一次保存 2 年的庫存，共 5,000 間旅館，平均每間 100 個房間。這張表是每間旅館一個 partition，所以 Nr = 100 × 730 = 73,000 列。

書對 73,000 列的評語是，這個 row 數本身不成問題，但 cell 數可能是問題。如果開始保存更多天的庫存，或沒有用 TTL 好好管理庫存量，partition 就可能變得太大。所以書的態度是，即使目前還不到上限，也值得考慮拆開這個大 partition。

本頁補充。這張表每列只有一個 cell（is_available），所以 row 數和 cell 數是同一個數字，書的這個區分在這個例子裡看不出差別。真正的風險在書評語的後半句：保存的天數變多，或沒有用 TTL 管理庫存時，列數（也就是 cell 數）會繼續增加。上面的情境按鈕可以看到，保存 5 年就會超過建議值，大型旅館也是。

書中提示

Estimate for the worst case。做容量計算時，很容易只取名目值或平均值，例如 row 數。書提醒也要算最壞的情況，因為在成功的系統裡，這類預測往往會成真。

計算磁碟用量

除了 cell 數，每張表要佔多少磁碟也該先估。書給的公式算的是單一 partition的大小 St，由四項加起來。下面每一項都編了號，後面的拆解沿用同一組編號。

St = Σ sizeOf(cki)① partition key 欄位 + Σ sizeOf(csj)② static 欄位 + Nr × (Σ sizeOf(crk) + Σ sizeOf(ccl))③ 每列的 clustering＋一般欄位 × 列數 + Nv × sizeOf(tavg)④ 每個 cell 的 metadata
ck
partition key 欄位
cs
static 欄位
cr
一般（regular）欄位
cc
clustering 欄位
tavg
每個 cell 平均的 metadata 位元組數，例如 timestamp，通常估 8 bytes
Nr、Nv
row 數與 cell 數，同前一節
sizeOf()
該欄位 CQL 型別的大小（bytes）

套到 available_rooms_by_hotel_date 上，四項各是這樣。

  • ① 只有 hotel_id 一個 partition key 欄位，型別是 text。假設旅館代碼是 5 個字元，就是 5 bytes。
  • ② 沒有 static 欄位，是 0 bytes。
  • ③ clustering 欄位有 date（4 bytes）和 room_number（smallint，2 bytes），一般欄位只有 is_available（boolean，1 byte）。每列 7 bytes，乘上 73,000 列是 511,000 bytes（0.51 MB）。
  • ④ 73,000 個 cell 各 8 bytes，是 584,000 bytes（約 0.58 MB）。書補充，Cassandra 3.0 之後的儲存格式裡，每個 cell 的 metadata 量會依資料型別、以及是否替個別 cell 指定自訂 timestamp 或 TTL 而不同，所以 8 bytes 只是估計值。

四項加起來約 1.1 MB。下面的計算器可以改旅館代碼長度和 tavg，列數沿用上一節計算器 A 的房間數與天數。

延伸推算

書說這個估計只算單一副本，要得到每張表需要的總容量，還得乘上 partition 數量與 keyspace 的副本數，Chapter 10 規劃叢集部署時會用到這個總容量。書沒有算出乘積。以書的假設，單一 partition 1,095,005 bytes × 5,000 個 partition ≈ 5.48 GB（單一副本），再乘上 schema 的 replication_factor 3 ≈ 16.43 GB。兩個數字都是由 bytes 的精確值換算後再四捨五入，和計算器預設顯示的一致。

這個公式估的是 partition 在磁碟上未壓縮的近似大小，不過已經夠用。如果使用 SSTable 壓縮（Chapter 13 會談），實際需要的空間更少。另外要記得，一個 partition 必須放得進單一節點。以這張表來看，設計不會給磁碟帶來太大的壓力。

Sidebar

更精簡的儲存格式。Cassandra 3.0 重寫了儲存引擎，包含新的 SSTable 檔案格式。舊格式會在每個 cell 的紀錄裡各存一份 clustering columns 的副本，新格式消除了這個重複，資料變小，公式也跟著變簡單。上面的公式用的是新格式的樣子，clustering 欄位只在 ③ 算一次。

拆分大 partition

目標沒有變，理想上一個查詢只碰一個 partition 就拿得到需要的資料，做不到就讓碰到的 partition 越少越好。但寬 partition 的設計可能逼近 Cassandra 的內建上限。容量分析也可能顯示，某個 partition 的 cell 數、磁碟大小，或兩者都太大。

拆分的技巧很直接，在 partition key 加入額外的欄位。多數情況只要把既有欄位之一搬進 partition key 就夠了。另一個選項是新增一個欄位當 sharding key，不過這需要額外的應用程式邏輯。

以 available_rooms_by_hotel_date 為例，書列了三種做法。

  1. 把 date 加進 partition key。每個 partition 代表某間旅館在某一天的房間可訂狀態。partition 會小很多，甚至可能太小，因為連續幾天的資料很可能落在不同節點。跨多天的查詢也得查多個 partition。
  2. 分桶（bucketing）。常用來把資料切成中等大小的 partition。例如在 partition key 加入 month 欄位，也許用整數表示。month 和 date 有一部分重複，但它是把相關資料分在一組、又不讓 partition 過大的好方法。書的 Figure 5-10 比較了原設計和加上 month 桶的設計。
  3. 把房間加進 partition key。如果你很想保留寬 partition 的設計，可以這樣做。每個 partition 代表某個房間在所有日期的可訂狀態。書裡的欄位名是 room_id，本頁沿用 schema 的 room_number。

書的結論是，因為沒有任何查詢是要搜尋特定房間的可訂狀態，第一種或第二種最適合這個應用的需求。下面的比較器把四種設計（含原設計）放在一起，數字會跟著計算器 A 的房間數與天數走。

延伸推算

這組數字用了幾個本頁自己的假設。本頁假設 month 是 YYYYMM 形式的整數（例如 202601），這樣 730 天才會是約 24 個桶。書只說也許用整數表示，沒有說明編碼方式。C 的桶數用 round(天數 × 12 ÷ 365) 估，每桶的列數以 28 到 31 天計，表中顯示這個區間，狀態判斷取最長的 31 天。這張表每列只有 is_available 一個非 key 欄位，所以 cell 數等於列數。Q4 在 D 要碰 R 個 partition，是因為 Q4 問的是這間旅館有哪些房可訂，每個房間各在一個 partition 裡。

以書的假設（100 房、730 天）來看，B 把 partition 切到每間旅館每天一個，每個 partition 只有 100 列，跨日查詢卻得逐日去查。C 讓一次查詢通常只碰一到兩個 partition，每個 partition 約 2,800 到 3,100 列。上面的輸入一改，這些數字也會跟著變。D 保留了寬 partition，但它切開的維度沒有任何查詢用得到。所以書選 B 或 C，而書示範的是 C。

本章學到什麼

書的立場很明確：比起任何設定或調校，資料模型才是左右應用程式效能與叢集維運的主因。本章因此走完一套完整、可運作的 Cassandra 資料模型，並和等價的關聯式模型對照。模型先以邏輯與實體兩種形式表示，再用 CQL 實現，過程中也認識了管理 CQL 的工具。接下來的章節會繼續在這個旅館應用上往下建構。

六個步驟各帶走一句話

  1. 概念模型先用大家都看得懂的 ER 模型描述旅館、房間、景點、房客與訂房，再去想怎麼對應到 Cassandra。
  2. 定義查詢從 wireframe 與 workflow 列出 Q1 到 Q9 並編號，訂房與房客這類下游 use case 的查詢也要一起想。
  3. 邏輯模型每個查詢一張表，查詢條件進 partition key，clustering column 負責唯一性與排序，整個 partition 都一樣的值標成 static。
  4. 實體模型替每個欄位指定型別、決定表放在哪個 keyspace，UDT 的 scope 是 keyspace，所以 reservation 要把 address 再宣告一次。

和關聯式建模的六個差異

完整說明在 對照 RDBMS。

  • No joins沒有 join需要 join 時建第二張反正規化的表代表結果，client 端 join 應該極少見。
  • No referential integrity沒有參照完整性表裡可以存其他 entity 的 ID，但 Cassandra 不強制，也沒有 cascading delete。
  • Denormalization反正規化同樣的資料出現在多張表是常態，Cassandra 在反正規化的模型下效能最好。
  • Query-first查詢優先設計先列出查詢路徑，再建支援它們的表，關聯式則是表排好了才寫查詢。
  • Optimal storage為儲存而設計每張表是磁碟上獨立的檔案，目標是讓一個查詢碰到的 partition 越少越好。
  • Sorting排序是設計決策排序固定，由建表時的 clustering columns 決定，ORDER BY 只能依其順序。

這是全章的彙整版，各區段在相關位置另有就地標示。下面九條是閱讀時值得留意的地方：多數是書中文字與 schema 之間對不起來，也有用語不夠精確、欄位沒有說明，以及這份 PDF 文字層的抽取問題。

  1. Q7 與 Q8 的對應。查詢清單與 schema 的 comment 都是 reservations_by_hotel_date 對 Q7、reservations_by_guest 對 Q8，但邏輯模型一節的內文把兩者說反了。本頁採用查詢清單與 schema comment 的對應。
  2. Q7 的房客姓名。Q7 的描述包含房客姓名，但 reservations_by_hotel_date 只有 guest_id，沒有姓名欄位。本頁照 schema 呈現。
  3. reservations_by_guest 的 clustering column。內文說把 guest ID 納入為 clustering column，schema 實際是 PRIMARY KEY ((guest_last_name), hotel_id)，clustering column 是 hotel_id，guest_id 只是一般欄位。依 CQL 語意推論（書中沒有討論），同姓房客在同一間旅館的兩筆訂房會落在同一個 primary key，後寫的會覆蓋先寫的。本頁以 schema 為準。
  4. Q5 的房價。Q5 要查房價與設施，但 amenities_by_room 沒有任何存房價的欄位。書在概念模型一節說過房價在真實世界很複雜，這裡簡化處理。本頁照 schema，不補房價欄位。
  5. 磁碟大小加總的第一項。內文算出 partition key 是 5 bytes，最後的加總式寫成 16 bytes。對 1.1 MB 的結果沒有實質影響。本頁採用內文逐項算出的 5 bytes。
  6. partition size 的公式。用來整理本頁的 PDF 文字層中，公式的位置出現的是 row 數的算式，公式本身是圖片，抽取時錯位。本頁的公式依內文敘述重建。
  7. key 與 partition 的用語。內文有兩處用語不精確，一處把 partition key 寫成 primary key，一處把 row 的唯一性寫成 partition 的唯一性。本頁用較精確的說法：hotels_by_poi 每個景點一個 partition，hotel_id 讓 partition 內每間旅館各有一列。
  8. guests 的 confirm_number。schema 裡有這個欄位，內文沒有解釋。本頁照 schema 列出，不另作解釋。
  9. UDT address 的欄位。本章是 street、city、state_or_province、postal_code、country（全是 text），和 Chapter 4 的 address（street、city、state、zip_code 為 int）不同。本頁以本章 schema 為準。
