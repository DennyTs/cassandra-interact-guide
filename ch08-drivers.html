Driver 的來歷與安裝

這一節交代三件事：應用程式為什麼需要 driver、Cassandra 的 client 為什麼從 Thrift 時代的 Hector 換成 CQL 時代的 DataStax driver，以及用 Java driver 4.x 之前要先在專案裡放什麼。如果你正在把 Hector 搬到 CQL，重點在中間那段：舊 client 失效的原因，是它們依附的 Thrift 介面被伺服器移除了。

為什麼需要 driver

書用 JDBC 開場。JDBC 定義了一組共通介面，像是 Statement、PreparedStatement、ResultSet。Oracle、SQL Server、MySQL 各自提供 driver 去實作它，和伺服器溝通的細節藏在 driver 裡，應用程式只看到一致的 API。Cassandra 的處境一樣：要寫應用程式就得有 driver，而且主流語言幾乎都有。

書也點出 driver 的附加價值。它容易嵌進你自己的應用程式，而且往往提供比 CQL native 介面本身更多的功能。書舉的例子是連線池（connection pooling）與 JMX 整合和監控。

native 介面只管收請求，其餘靠 driver

第 6 章講過，節點上的 CQL native transport server 負責管理 client 連線，並把收到的請求轉給 StorageProxy 去執行。這個介面只定義伺服器怎麼收請求。正式環境的 client 還得回答另一批問題：連哪些節點、每個節點連幾條、這次請求先送給誰、失敗了換誰、叢集的長相變了怎麼知道。這批問題全落在 driver 身上，也正是本章後面幾乎每一節的主題。

Hector、Astyanax 與其他舊 client

章首有一塊向前輩致敬的 sidebar。Cassandra 早期沒有官方 client，社群為各語言做出 driver，書認為這些貢獻是 Cassandra 能被採用的關鍵推手。名單如下。

Hector
最早的 Cassandra client 之一。它提供簡單的 Java 介面，讓早期開發者不必直接寫 Thrift API，也啟發了後來的幾個 driver。
Astyanax
Netflix 在 Thrift API 之上做的 Java client，定位是 Hector 的後繼。書說它幫了許多使用者從 Thrift 過渡到 CQL。專案在 2016 年退役。
其他
Pycassa（Python）、Perlcassa（Perl）、Helenus（Node.js）、Cassandra-Sharp（.NET 與 C#）。多數已不再維護，原因同樣是它們建立在已被移除的 Thrift 介面上。

Apache Cassandra 網站有一頁列出現行與舊版 driver 的完整清單，需要查某個語言時可以從那裡開始。

Thrift 時代與 CQL 時代的 client 差在哪

把書散在各章的說法拼起來，兩個世代的 client 面對的是不同的伺服器介面，也是不同的資料模型。

  • 伺服器介面是原始的 Thrift API，也叫 RPC 介面。
  • 資料模型沿用 Bigtable 風格的 schema-free：欄位可以動態新增。過渡期有 schema-optional 的說法（第 2 章）。
  • client 的價值是把 Thrift API 包成好用的 Java 介面。
  • Thrift 在 3.0 預設關閉，4.0 移除。
  • 伺服器介面是 CQL native transport。
  • 資料模型由 CQL 定義 schema，語法接近 SQL。3.0 的儲存引擎也重寫成與 CQL 對齊。
  • driver 的形態接近 JDBC，另外負責連線池、路由、重試、metadata 與監控。
  • 成為新專案的事實標準。
先想想：Hector 本身沒有 bug，為什麼 Cassandra 4.0 一出，它就再也不能用？

Hector 是 Thrift API 的包裝。client 與伺服器之間的合約就是 Thrift 介面，伺服器把這個介面拿掉，合約就不存在了，client 寫得再好也沒有對象可以說話。書解釋所有舊 client 消失時用的是同一個理由：它們建立在已被移除的 Thrift 介面上。

Thrift 的時程

對搬遷專案來說，時程由伺服器版本決定。書在不同章節給了三個時間點。

Cassandra 版本Thrift 介面的狀態對 Hector 類 client 的意義

3.x 上怎麼讓 Thrift 活著，以及搬遷的死線

書只說 3.0 起 Thrift 預設關閉，沒說開關在哪。我對照了兩個分支的設定檔：Cassandra 3.11 的 cassandra.yaml 有 start_rpc，預設值是 false；4.0 的 cassandra.yaml 完全沒有這個設定。所以 Hector 應用留在 3.x 時，節點必須把它改成 true。

所以搬遷的死線是伺服器升 4.0 的那一天。所有走 Hector 的程式碼要在那之前換成 CQL driver，兩者可以在 3.x 上並行一段時間。來源：Cassandra 3.11 與 4.0 分支的 conf/cassandra.yaml。

抽象層級的差別：bytes 與 schema

Hector 的 API 書上沒有展開，這個導讀也不展開，以下只講 Thrift 介面本身，來源是 Cassandra 3.11 的 cassandra.thrift。

  • 資料的基本單位是 Column：name 與 value 都是 binary，另外有 timestamp 與 ttl。
  • 呼叫以 column family、row key 與一段 column 範圍為單位，例如 get_slice、batch_mutate。
  • 所以在 API 這一層，欄位名稱和值都只是位元組，怎麼編碼要由 client 這一側決定。

CQL driver 則是送出 CQL 字串（或 prepared statement），欄位名稱與型別事先寫在 schema 裡，driver 負責把 CQL 型別對應到 Java 型別。搬遷時要重想的是資料模型，不只是換掉類別名稱。Thrift 時代的 wide row 在 CQL 裡對應 clustering columns 構成的 wide partition，第 5 章的 wide partition pattern 方塊提過這兩個詞的關係。

第 15 章對搬遷的建議

第 15 章（不在本導讀範圍）談如何把應用程式搬到 Cassandra。其中兩點和 client 替換有關：用 DAO pattern 把資料存取的細節隔離在一層，之後換實作時不必動商業邏輯；零停機搬遷可以用 dual write，搭配初始的批次載入。dual write 在書裡的情境是從舊資料庫搬到 Cassandra，用在 Hector 到 CQL 時要自己判斷是否需要。

DataStax Java Driver

轉折點是 CQL。它的語法簡單又熟悉，寫 Cassandra client 的手感於是接近寫關聯式資料庫的 driver。DataStax 看準這點，把開源 driver 當成推廣 Cassandra 的策略投資，除了 Java，也涵蓋其他幾種語言。這批 driver 很快成為新專案的事實標準，原始碼與周邊的連接器、工具都放在 DataStax 的 GitHub 組織底下。

DataStax 是 2010 年 4 月由 Jonathan Ellis 與 Matt Pfeil 成立的公司，早期名稱是 Riptano。它聘有數位 Cassandra committer，免費提供 driver 與工具，另外販售企業版伺服器與支援，這些在第 2 章介紹過。下文的 DSE 指的就是這個企業版（DataStax Enterprise）。

為什麼會有一張相容性表

書只叫你去查這張表，沒解釋它為什麼存在，以下是我自己的推論。書在 Driver 設定一節提到，Cassandra 4.0 用 protocol v5，3.x 用 v4，driver 預設會自動協商版本，連混合版本的叢集也能處理。協商解決的是連得上的問題。表要回答的是另一件事：這一版 driver 是否支援你的伺服器所提供的協定與功能。協商的細節見 Driver 設定，版本相容性在出版後的狀況見 書後變化。

書選 Java driver 當全章主角，理由有兩個：它是這批 driver 裡最老也最多人用的，而且新功能通常最先出現在它身上。學會它的功能，換到 DataStax 的其他語言 driver 時，多半能對得上。其他語言留到本章最後一節，見 其他語言的 Driver。

開發環境設定

你可以直接下載 driver 的 jar 自己管理相依性，但現代 Java 專案通常交給 Maven 或 Gradle。用 Maven 的話，在 pom.xml 放進 java-driver-core，版本號自己指定。

java-driver-core 只是核心。書在後面講 Query Builder 與 Object Mapper 時，會要求你另外加對應的 artifact。座標在書出版之後有變動，書上的 groupId 與 git clone 位址現在對不上，見 書後變化。

  • 文件：有線上手冊和 Javadoc。Javadoc 也包含在原始碼發行版裡，離線時可以從那裡看。
  • 原始碼：所有 DataStax driver 都是 GitHub 上的開源專案。書給的做法是 git clone 取得唯讀的主幹。
  • Developer guide：想了解 driver 內部怎麼運作，或想參與貢獻，DataStax 文件網站另有 developer guide。

看 import 就知道有沒有碰到內部 API

書沒提。4.0 起 driver 用套件名稱區分公開與內部：com.datastax.oss.driver.api 底下是正式的公開 API，遵循語意化版本，次要版本之間保證二進位相容；com.datastax.oss.driver.internal 底下是內部實作，只盡力維持相容。要檢查自己有沒有誤用，在程式碼裡搜尋 import com.datastax.oss.driver.internal 即可。來源：4.1 手冊的 API conventions 一頁。

Driver API 的重大變更與策略調整

Driver API changes

Java driver 4.0 對 API 與設定做了重大的不相容變更，目的是簡化應用程式開發，並避開違反最佳實務的設定方式。全書採用新 API。書也提到，第二版的 "Clients" 章仍是使用 3.x 以前版本者的好參考。

書沒有把這些變更集中列成一張表，而是散在各節順帶提到。我把書自己講過的整理在一起，方便你讀後面的小節，也方便判斷網路上的舊範例能不能用。

書沒提的 4.0 差異：套件、Java 版本與設定方式

下面三點出自 4.0 升級指南（我讀的是 4.1.0 標籤上的版本），對搬遷者很實用。

  • 4.0 不具二進位相容性，套件也改了：3.x 的類別在 com.datastax.driver.core，4.x 在 com.datastax.oss.driver.api.core。Maven 座標同樣不同，3.x 是 com.datastax.cassandra:cassandra-driver-core（這一項憑我的記憶，升級指南只寫 4.x 是新座標）。看到範例以 Cluster.builder() 開頭、import 來自 com.datastax.driver.core，就是 3.x 的寫法，不能直接貼進 4.x 專案。
  • 4.x 需要 Java 8 以上，且不再把 Guava 暴露在 API 上（內部仍使用，但已 shaded）。
  • 設定的主要方式從零散的設定類別改成 Typesafe Config 檔案。聯絡點這類執行期才知道的值，仍保留程式碼裡的 setter。

2019 年的 driver 策略調整

2019 年 9 月，DataStax 宣布調整 driver 策略。在那之前，DataStax 分開維護兩套 driver：給 Apache Cassandra 用的開源版，以及給 DSE 用的企業版。2020 年初，各語言的兩套程式碼合併。結果是開源 driver 的使用者也拿到幾項原本只有 DSE 客戶才有的效能與可用性改善。DSE 專屬的 driver 功能不在書的範圍內，書指引你去看 DataStax 的文件。

對只用 Apache Cassandra 的團隊，這個調整的實際意義是 driver 的版本線變成一條，不必再在兩套 artifact 之間選擇。DSE 專屬功能可以略過不讀。

  • Driver 的角色類似 JDBC，但承擔更多：連線池、路由、重試、metadata 與監控都在 driver 這一層，native 介面本身只負責收請求。
  • Hector、Astyanax 等舊 client 建立在 Thrift API 上。Thrift 在 3.0 起預設關閉，4.0 移除，這些 client 因此失去可以連的介面。
  • Hector 搬遷的時程由伺服器升級決定：client 要在伺服器升 4.0 之前換成 CQL driver，而且需要重想資料模型，不只是換 API。
  • CQL 讓 driver 的形態接近關聯式資料庫的 driver。DataStax 的開源 Java driver 成為事實標準，書以它為主講完整章。
  • 用 Maven 加入 java-driver-core 就能開始。4.0 的 API 與設定大幅改版（Cluster 併入 CqlSession、單一預設 policy、CompletionStage），網路上 3.x 的範例不能直接套用。
  • 2019 到 2020 年，DataStax 把開源與 DSE 的 driver 程式碼合併，開源使用者因此拿到原本只有 DSE 客戶才有的效能與可用性改善。

Connecting to a Cluster · p.276

連線到叢集

Java driver 的所有操作都從 CqlSession 開始。你給它 contact points、local datacenter 和可選的 keyspace，build() 就連上叢集、取得 metadata，並替節點建立連線池。這些連線讓它成本不低，一個應用程式通常只該建一個。

範例背景：Reservation Service

本章的程式碼都圍繞 Reservation Service。它是旅館訂房系統裡的一個微服務，資料模型來自第 5 章，應用設計來自第 7 章。第 7 章把它設計成：以 Spring Boot 管理服務的生命週期，用 DataStax Java Driver 存取 Cassandra，對外提供 REST API 並以 Swagger 文件化。目標是做出一個精簡但能運作的參考實作。原始碼公開在 GitHub（jeffreyscarpenter/reservation-service），後面每一種查詢技術各有一個分支。

第 7 章還給了一條經驗法則：一個服務一個 keyspace，再搭配每個 keyspace 一個資料庫使用者，讓每個服務只能讀寫自己的 keyspace（第 14 章會講授權）。所以這個服務專屬的 keyspace 叫 reservation，主要資料表是 reservations_by_confirmation。「一個服務對一個 keyspace」這個前提，後面在決定 session 怎麼切的時候會用到。

書的前後不一致：confirm_number 與 confirmation_number

書裡兩種寫法並存。第 5 章的 schema、第 7 章的 materialized view DDL 與第 9 章的 LWT 範例用 confirm_number。第 8 章的 SimpleStatement、QueryBuilder、SchemaBuilder 與 mapper 範例用 confirmation_number。同一張 reservations_by_confirmation 不會有兩個欄位名稱，這是書的不一致。照第 5 章的 DDL 建好表之後，原樣貼上第 8 章的 CQL 會因為欄位不存在而失敗。本導讀的範例統一用 confirm_number。

CqlSession 與 builder

在 Java driver 裡，和叢集的連線以 com.datastax.oss.driver.api.core.CqlSession 表示，它是 driver 的主要入口。API 採 builder pattern 的 fluent 風格：從 CqlSession.builder() 開始串接設定，最後呼叫 build() 取得 session。

這段同時給了 contact point 和 local datacenter。4.x 只給 contact point 是不夠的，原因在 local datacenter 一節。

Cluster 物件消失了

舊版 DataStax driver 有 Cluster 物件，由它產生 Session。4.0 之後的 Java driver 把兩者合併成 CqlSession。

合併前後各自持有什麼

書只說兩者合併了。3.x 的 Cluster 持有設定、metadata 與控制連線，Session 持有連線池與查詢的執行，同一個 Cluster 可以產生多個 Session，彼此共用 metadata。4.x 合併之後，每個 CqlSession 自成一體，有自己的設定、metadata、控制連線與連線池。這一點會影響「每個 keyspace 一個 session」的成本，在最後一節會回頭用到。

Contact points

在 driver 的用語裡，建立 session 時你明確指出的那些節點叫 contact points。書把它類比成 seed node。seed node 是 Cassandra 節點啟動時用來認識叢集其他成員的入口（第 10 章）。contact point 則是 client 認識叢集的入口。

先想想：只給兩個 contact points，之後的查詢也只會送到這兩個節點嗎？

不會。contact point 的任務是讓 driver 進入叢集並取得 metadata。metadata 列出叢集裡的節點，driver 替它們建連線池，之後的請求再依 load balancing policy 分散出去（細節見 Driver 設定）。所以 contact points 是入口，不是之後所有請求的目的地。

在 Kubernetes 上拿 service 當 contact point

第 12 章提到，Cassandra operator 的 CRD 可以描述一個 service，把一個或多個節點的對外端點暴露出來，供 client 應用程式當作 contact points 使用。

contact point 連得上，不代表其他節點也連得上

書沒提。session 建好之後，driver 從 contact point 讀 system.local 與 system.peers（對 4.0 以後的伺服器是 system.peers_v2）來認識其他節點。其他節點的位址取自它們各自對外宣告的 broadcast RPC address，也就是第 10 章的 broadcast_rpc_address，沒設時等於 rpc_address。取得之後還會經過 AddressTranslator 才拿來連線，預設的 PassThroughAddressTranslator 原樣通過。

含意是：在 Kubernetes 或 NAT 後面，如果節點宣告的位址對 client 不可達，就會出現「第一個 contact point 連得上，其他節點全部失敗」的現象。處理方式在 advanced.address-translator，這一節不展開。

另外有三個關於 contact points 的細節，都來自 4.1 的 reference.conf 與原始碼。builder 上給的與設定檔裡的 contact points 會合併，不是擇一。設定檔裡的主機名稱預設在啟動時解析成 IP（advanced.resolve-contact-points = true），一個名稱解析出多個位址時全部都會用到。容器環境若 DNS 記錄會變，可以把這個選項改成 false。

Local datacenter

正式環境除了多個 contact points，還要告訴 driver 本地資料中心（local data center）的名稱。書在這裡一筆帶過，說資料中心的命名留到第 10 章。原因要到負載平衡那一節才完整交代：4.0 之後的預設 policy 要求設定 local DC，而且它的 query plan 只包含 local DC 的節點。

書在負載平衡一節還解釋了為什麼這樣設計。3.x 的 DCAwareRoundRobinPolicy 會在本地節點之後附上遠端節點，原意是當本地的 replica 全部不可用時提高可靠度。實務上，本地 replica 全掛通常是整個資料中心層級的事故，把流量轉到別的資料中心會帶來意料之外的副作用，也很難除錯，所以 4.0 的預設 policy 不再這樣做。換個角度看，local DC 就是你替這個 client 劃定的活動範圍。完整機制見 Driver 設定的 Load balancing，那裡另有一則書外補充：3.x 的這個遠端備援要另外設定才會生效。

名稱從哪裡來

driver 要的名稱必須和叢集自己認定的資料中心名稱一致。書在第 10 章談 snitch 時說明了名稱的來源：

  • 用 GossipingPropertyFileSnitch：每個節點的 cassandra-rackdc.properties 裡寫 dc=DC1 與 rack=RAC1。
  • 用 PropertyFileSnitch：cassandra-topology.properties 裡以 IP=DC1:RAC1 的格式逐一列出節點。
  • 書中用 ccm 起的本機叢集，nodetool status 顯示的資料中心名稱是 datacenter1。

這些名稱和設定 NetworkTopologyStrategy 的 replication 時用的是同一組。第 7 章的多資料中心部署範例也說，服務實例應該知道本地資料中心的名稱。

擴充資料中心之前先設好 client

第 12 章在新增資料中心的步驟裡提醒（"Don't forget your clients"）：要在把 keyspace 的 replication 延伸到新資料中心之前，先確認 client 已經把既有的資料中心指定為 local data center。用了 QUORUM 的 client 在加入新資料中心後，查詢會跨資料中心，也可以考慮改用 LOCAL_QUORUM 限制延遲。

書的第一個範例在 4.x 會失敗：local DC 的規則

書說建立 CqlSession 最少只要一個 contact point，並說零參數的 build() 和只加一個 contact point 的範例等價。我讀 4.1.0 的原始碼，結果不是這樣：

  • 完全沒給 contact point 時，driver 才允許省略 local DC。它連 127.0.0.1:9042，並採用那個節點所屬的資料中心。
  • 只要有明確的 contact point（來自 builder 或設定檔，包括明確寫成 127.0.0.1:9042），又沒設 local DC，初始化就丟 IllegalStateException，訊息要你明確指定 local DC。

所以書的第一個範例（只加一個 contact point）在 4.1.0 會失敗。兩種寫法連到的節點相同，但對 local DC 的要求不同，不算等價。

失敗的時機也值得知道。這個檢查發生在連上 contact point、讀完節點清單與 schema 之後。叢集本身連不上時，你會先看到連線例外，而不是這個。另外，若你設定的 local DC 和 contact point 實際所屬的 DC 不同，預設 policy 會記一則 WARN。這一句我只讀過原始碼，沒有實際執行驗證，把握度比上面兩點低。

方法名稱也有一個小地方：書在負載平衡一節把它拼成 withLocalDataCenter()（大寫 C），實際方法是 withLocalDatacenter()。出版後的行為變化見 書後變化。來源：4.1.0 的 DefaultLoadBalancingPolicy、MetadataManager 與 DefaultSession 原始碼，以及 4.1 手冊的 core 一頁。

Keyspace

建立 session 時可以順便指定 keyspace，例如連到 reservation。不指定的話，後果是之後每個查詢裡的 table 都要帶上 keyspace 前綴。

用設定檔的話，對應的設定鍵是 basic.session-keyspace（書在 Driver 設定一節的範例裡用過）。

什麼時候指定 keyspace

依第 7 章的經驗法則，一個服務對一個 keyspace，這時 withKeyspace("reservation") 最省事，程式碼裡的 CQL 也短。如果服務會碰多個 keyspace，書給的選項是每個 keyspace 一個 session（見最後一節的提示框），或者不指定 keyspace、每個 table 都帶前綴。

keyspace 的四個細節

以下都出自 4.1 的手冊、reference.conf 與原始碼，書沒提。

  • 忘了指定時的症狀：沒有 keyspace 又沒帶前綴，伺服器以 INVALID 錯誤回應，driver 端是 InvalidQueryException，訊息大意是沒有指定 keyspace。
  • 不要用 USE：執行 USE 會改變這個 session 的預設 keyspace。session 通常被多個執行緒共用，執行期切換 keyspace 不是執行緒安全的，可能造成莫名的查詢失敗。
  • 大小寫：withKeyspace(String) 和 withKeyspace(CqlIdentifier) 兩個版本都有。設定檔的 session-keyspace 格式和 CQL 相同，區分大小寫的名稱要加雙引號（寫在 HOCON 裡要跳脫）。CqlIdentifier 見 Metadata 的提示框。
  • keyspace 不存在：driver 在每條連線初始化時送 USE。如果所有連線池都回報 keyspace 無效，build() 會丟 InvalidKeyspaceException。

另外，4.1 的手冊與 reference.conf 提到，對 Cassandra 4 以上的伺服器可以在單一請求上指定 keyspace。這個功能書沒有提，我也沒有實際測試過，需要時請查手冊。

拼起來：程式碼與設定檔

contact points、local datacenter 和 keyspace 都可以寫在程式碼裡，也可以放進設定檔。書在 Driver 設定一節說，多數情況下用設定檔比較好。第 7 章也提過，keyspace 名稱、帳密、叢集拓撲這類會隨環境改變的值，適合從程式碼外部化出來。

動手試：組一個 session

下面的實驗讓你勾選 contact points、local datacenter 與 keyspace，看產生的 Java 程式碼、等價的 HOCON 設定，以及連線時會發生什麼事。建議先預測再操作。實驗用的是簡化模型，哪些地方做了簡化，實驗裡有說明。

先想想：給了 contact points，卻沒有指定 local datacenter，會怎麼樣？

在 Java driver 4.x，建立 session 會丟 IllegalStateException，要求你明確指定 local DC。書只說「你還需要指定 local data center」，沒有說明不指定的後果，這個行為來自 4.1.0 的原始碼，見上一節的補充。

操作時留意三件事：

  1. 把 contact points 全部取消勾選，產生的程式碼長什麼樣？它會連到哪裡？對照 contact points 一節的預設行為。
  2. 勾選兩個 contact points 之後，拿掉 local datacenter。結果和你的預測一致嗎？
  3. 有沒有 keyspace，Java 和 HOCON 各差在哪一行？之後的 CQL 需不需要加前綴？

建立 session 時，driver 做了什麼

書用兩句話交代這個過程。第一，建立 CqlSession 時，driver 連到其中一個 contact point 取得叢集的 metadata。第二，session 管理對叢集的連線，用 Cassandra native protocol 執行查詢與控制操作，並且為每個 host 維持一個 TCP 連線池。把這兩句展開，大致是：

  1. 連上入口driver 連到其中一個 contact point，向它取得叢集的 metadata。
  2. 認識整個叢集metadata 讓 driver 知道叢集裡有哪些節點，並依 local datacenter 決定哪些節點歸這個 session 使用。
  3. 建立連線池為要使用的節點各建一個 TCP 連線池。之後的查詢與控制操作都走這些連線。
  4. 設定預設 keyspace如果指定了 keyspace，它成為這個 session 的預設 keyspace。

可能的例外

建立 session 是會碰網路的動作，所以會失敗。書列了兩種：所有 contact points 都不可用時，丟出例外，書寫的是 NoHostAvailableException；驗證失敗時丟 AuthenticationException。驗證怎麼設定，第 14 章會講。

4.x 實際丟的例外類別

NoHostAvailableException 是 3.x 的類別，4.x 的 api.core 裡沒有它。4.x 的 build() 在所有 contact points 都連不上時丟 AllNodesFailedException，每個節點失敗的原因在 getAllErrors() 裡。NoNodeAvailableException 是它的子類別。細節與出處見 書後變化。

除了這個，本節提過的還有兩個：沒設 local DC 的 IllegalStateException，以及 keyspace 無效時的 InvalidKeyspaceException。叢集暫時連不上時想讓 build() 重試而不是立刻失敗，有個書沒提的選項 advanced.reconnect-on-init，同樣在 書後變化 說明。

驗證失敗時，4.x 會丟什麼

書只寫 AuthenticationException。我讀 4.1.0 原始碼後的推測是：初始化階段的驗證失敗，會被收進 AllNodesFailedException 的 getAllErrors()，而不是直接丟出。這是讀原始碼得到的結論，我沒有拿開了驗證的叢集實測過，所以只標中等把握。要靠它寫錯誤處理之前，請自己對你的叢集試一次。

在啟動階段建立 session

書說 CqlSession 在建立時就會連叢集並可能失敗，加上它是重量級物件，合理的做法是在應用程式啟動時建好，失敗就讓啟動失敗，而不是等到第一個請求才建。這是我根據書中機制做的建議，書沒有直接這樣寫。

build() 內部的實際順序（4.1.0 原始碼）

書只給了概要。我讀了 4.1.0 的 DefaultSession、ControlConnection、PoolManager 與 ProtocolInitHandler，初始化的順序是：

  1. 先建 policy各種 policy 與 listener（load balancing、retry、speculative execution、reconnection、address translator 等）一次建好。設定有誤在這一步就失敗，還沒開任何連線。
  2. 控制連線逐一嘗試 contact points，連上之後讀 system.local 與 system.peers（對 4.0 以後的伺服器是 system.peers_v2），取得節點清單。全部失敗就是 AllNodesFailedException。
  3. 協商協定版本比對所有節點支援的 native protocol 版本，必要時降到共同的版本。
  4. 載入 schema第一次 schema metadata 載入完成才往下。
  5. 初始化 load balancing policy在這裡檢查 local DC（缺少就丟 IllegalStateException），並把每個節點標成 LOCAL 或 IGNORED。
  6. 建連線池只替未被 IGNORED 的節點建池。每條連線建立時依序做 STARTUP、驗證，若指定了 keyspace 再送 USE。等所有池都完成初始化才算完成。
  7. 回傳 session此時 build() 才返回。

兩處和書的概要有出入。第一，書說每個 host 一個池。4.x 的預設 policy 把非 local DC 的節點標成 IGNORED，而 PoolManager 不替 IGNORED 的節點建池，所以實際上是每個 local DC 的節點一個池。第二，書提到連線用於「查詢與控制操作」，4.x 把它拆成兩類。控制連線專門做管理工作：查 system 表取得拓撲與 schema、檢查 schema agreement、接收伺服器事件。它建在第一個連上的節點，掉線時 driver 依 reconnection policy 找別的節點接手，獨立於一般連線池。請求連線池才是你的查詢走的路。

連線池與 session 的成本

回到書的說法：每個 CqlSession 管理對叢集的連線，用 native protocol 執行查詢與控制操作，且對每個 host 持有一個 TCP 連線池。

Sessions are expensive

因為 CqlSession 維持對多個節點的 TCP 連線，它是相對重量級的物件。多數情況下，建一個 CqlSession 在整個應用程式裡重用，不要反覆建立與銷毀。如果應用程式存取多個 keyspace，每個 keyspace 一個 CqlSession 也是可接受的做法。

一個 session 開幾條連線

粗估方式：local DC 的節點數乘以每個池的連線數，再加一條控制連線。書在 Driver 設定一節說，因為 native protocol 是非同步的，一條連線可以同時處理很多請求（v3 以後最多 32,768 個），所以預設每個節點只需要一條連線，每條連線同時在途的請求預設上限是 1,024。細節見 Driver 設定。

代入數字：local DC 有 6 個節點，每池 1 條，加 1 條控制連線，一個 session 約 7 條。服務部署 4 個 pod，每個 pod 一個 session，叢集端就有約 28 條來自這個服務的連線。pod 數量一擴，連線數就跟著乘上去。

在每個請求裡建一個 session

如果在 REST handler 裡每次請求都 build() 一個 session，每次都要重新連 contact point、取得 metadata、替每個節點建池，用完再全部拆掉。這正是書要你避免的「反覆建立與銷毀」。session 應該是應用程式啟動時建好的單例。

session 的生命週期，以及「每個 keyspace 一個 session」的另一種看法

  • 執行緒安全：4.1 手冊說 CqlSession 是 thread-safe，建議每個目標叢集建一個實例並全應用共用。
  • 要關閉：用完要 close() 釋放 TCP 連線與執行緒池。它實作了 AutoCloseable。
  • 每個 keyspace 一個 session：書說這是可接受的做法。4.1 手冊的立場較保守，它把「為每個 keyspace 開一個 session」列為反模式，理由是連線池以 session 為單位，session 加倍連線數也加倍。前面提過，4.x 的每個 session 還有自己的控制連線與 metadata。所以較省的做法是只用一個 session，在 table 名稱前帶 keyspace 前綴。

兩種說法不算矛盾：書說可行，手冊說有代價。只存取一個 keyspace 的服務，如同 Reservation Service，根本不會碰到這個取捨。

Spring 裡誰來關 session

書的範例用 Spring Boot，但沒談關閉。我的理解是：把 CqlSession 宣告成單例 @Bean 時，Spring 會自動推斷並呼叫它公開的 close() 當銷毀方法，所以通常不必自己寫關閉程式。這一點憑我對 Spring 的了解，沒有實測，也沒有對照 Spring 的原始碼，所以只標中等把握。

  • CqlSession 是 Java driver 4.x 的入口，用 builder 組出來。舊版的 Cluster 與 Session 已併入它，每個 session 有自己的 metadata、控制連線與連線池。
  • Contact points 只是進入叢集的入口，用來取得 metadata，之後 driver 靠 metadata 認識其他節點。正式環境給多個，避免入口剛好停機時建不起 session。不給就預設 127.0.0.1:9042。
  • 明確給了 contact points，就要同時指定 local datacenter，名稱必須和叢集的 snitch 設定一致。書的第一個範例省略它，在 4.x 會丟 IllegalStateException。
  • 不指定 keyspace 的後果是每個 table 都要帶前綴。一個服務對一個 keyspace 時，用 withKeyspace（或 basic.session-keyspace）最省事；不要在共用的 session 上執行 USE。
  • build() 會連線並可能失敗。所有 contact points 不可用時，書寫 NoHostAvailableException，4.x 實際是 AllNodesFailedException。建議在啟動階段建立，失敗就讓啟動失敗。
  • Session 是重量級物件：它對每個 local DC 節點持有連線池，外加一條控制連線。整個應用建一個、全程重用、結束時關閉，不要每個請求建一個。

Statements：從字串到 prepared

CqlSession 建好之後，所有讀寫都是把一個 Statement 交給 execute()。這一節走過三種做法：直接丟字串、SimpleStatement 帶參數值、PreparedStatement 先 prepare 再 bind。三者的差別在每次執行時 driver 送給節點什麼，以及節點要重做哪些事，語法反而是其次。

Statement 是什麼

在 driver 裡，一次查詢就是一個 Statement 物件。Statement 是介面，書列出的實作有三個。

SimpleStatement
一段 CQL 字串，可以另外附上參數值。每次執行都把整段字串送給節點。
BoundStatement
把值綁到 PreparedStatement 之後得到的物件。帶的是 prepare 時換回來的識別碼與參數值，不再帶整段字串。
BatchStatement
把多個寫入包成一次送出。用法與取捨留到第 9 章，這一節不展開。

最短的寫法是把字串直接交給 CqlSession.execute(String)，一行同時建立並執行查詢。

書上的同類範例沒有 LIMIT，會掃整張表。書也提醒這種查詢在大型資料庫上很貴，只當作語法示範。實際的查詢多半有搜尋條件，寫入則有一堆值要放進去。最直覺的做法是用 Java 的字串工具把值拼進語法，下面的例子說明為什麼不該這樣做。

手拼查詢字串

書的警告有兩層。手拼容易寫錯語法，而且使用者輸入若沒有清理就拼進去，應用程式會暴露在 injection 攻擊之下。

書沒有展開機制，以下是我補的說明：拼完之後資料和語法混在同一個字串裡，節點的 parser 沒有辦法分辨哪一段原本是資料。上面的輸入只要含一個單引號，字串字面值就會提早結束。惡意輸入可以因此改變查詢的語意，連姓名 O'Neil 這類合法資料也會讓語法出錯。解法是讓值與語法分開送，接下來兩節都在做這件事。

4.x 的 statement 都是不可變物件（書中未提）

  • 內建實作全部 immutable。每個 setXxx() 回傳新物件，原物件不動。單獨寫一行 statement.setIdempotent(true); 等於沒做事，要接回傳值：statement = statement.setIdempotent(true)。
  • 好處是 statement 能安全地跨執行緒、跨非同步呼叫重複使用。
  • 所有 statement 共用一組執行屬性：execution profile 名稱、idempotence、tracing、query timestamp、page size 與 paging state、一致性與 serial 一致性、逾時、路由資訊等。
  • 4.x 的 BatchStatement 用 BatchStatement.newInstance(...) 或 builder(...) 建立。第 9 章 listing 裡的 new BatchStatement() 是 3.x 的寫法。

依據：driver 4.x 手冊的 Statements 與 Batch statements 頁，以及 SimpleStatement 原始碼。

Simple Statements

想把值當參數送，就用 SimpleStatement。字串裡用 ? 標出值的位置，值另外給。書點出一個事實：session.execute(String) 其實是替你建一個 SimpleStatement 的便利方法，兩種寫法等價。

建立方式

SimpleStatement.newInstance(cql)
手上已經有固定字串時最直接，與 execute(String) 等價。
SimpleStatement.builder(cql)
回傳 builder，可以一個一個加入參數值，最後 build()。書用 addPositionalValue() 依序補上每個 ? 對應的值。

字串提供查詢的骨架：哪張表、哪些欄位。問號是值的位置。INSERT 成功時不會有任何輸出，execute() 回傳的 ResultSet 裡沒有資料列。書提醒，範例為了好讀把值寫死，真實程式的值會來自變數。

具名參數與 newInstance 的帶值版本（書中未提）

書只示範位置參數。SimpleStatement 也能用具名參數：字串裡寫 :name，builder 用 addNamedValue("name", value) 補值。同一個 statement 不能混用兩種，混用時 builder 會丟 IllegalArgumentException。

不想用 builder 時，SimpleStatement.newInstance(cql, Object... values) 可以一次帶入位置參數，另有 newInstance(cql, Map<String, Object>) 帶入具名參數。

依據：driver 4.x 手冊 Simple statements 頁，以及 SimpleStatementBuilder、SimpleStatement 的原始碼。

書中範例的欄位名稱與資料表名稱（本導讀的統一做法）

書的 SimpleStatement 與 PreparedStatement 範例把 primary key 欄位寫成 confirmation_number，第 5 章的 schema 與第 9 章的 CQL 範例寫的是 confirm_number。照第 8 章字面去跑，會得到欄位不存在的錯誤。本導讀一律用 confirm_number。

書的 INSERT 與帶參數的 SELECT 範例沒有寫 keyspace，表名單獨出現，要靠 session 建立時設定的 keyspace 才找得到表。本導讀的範例都加上 reservation. 前綴，不依賴 session 的預設 keyspace。

取回結果

讀取時要接住 execute() 回傳的 ResultSet。它可以直接用 for-each 走過每個 Row。取欄位值要用對應型別的 accessor，例如 getString()、getLocalDate()、getUuid()，accessor 的選擇由欄位的 CQL 型別決定。

結果很多時，ResultSet 會分頁取回。每頁筆數是 Driver 設定那一節講的 request.page-size，分頁的完整用法在第 9 章。

smallint 欄位要用 getShort（書中範例的筆誤）

書的讀取範例對 room_number 呼叫 getInt()。這個欄位在 schema 裡是 smallint，而 getInt() 預設只對應 CQL 的 int，smallint 要用 getShort()（driver 原始碼的 javadoc 這樣寫）。同一段的 printf 格式字串也有筆誤，%i 不是合法的格式，hotel_id 那一格的 % 後面少了轉換字元。

另外，原始型別的 accessor 遇到 NULL 欄位會回傳 0，需要分辨時先呼叫 isNull()。

SimpleStatement 每次送什麼

一次 simple statement 的往返

  1. driver 送出完整的 CQL 字串，加上值。
  2. 節點理解字串：把文字讀成一個可執行的查詢，檢查表、欄位與型別。
  3. 節點執行並回傳結果。
  4. 下一次再執行同一段字串，第 2 步從頭再來一遍。

書後面談 PreparedStatement 時，說的是結構只送給節點一次，simple statement 剛好是它的對照面：每次都要把結構送一遍，節點每次都要重新理解它。書沒有直接寫出「節點重新理解」這一半，那是由這個對照推得的，手冊的明確說法見下方補充框。

值是分開送的，而 driver 看不懂你的字串（書中未提）

  • 值和字串分離。帶 ? 的 SimpleStatement，值會以序列化後的二進位形式隨請求一起送出，不會被拼進字串裡。所以書放在 prepared 那一段的「資料與語法分離」，在帶參數的 SimpleStatement 上其實也成立。prepared 多出來的好處是跳過 parse，以及 driver 取得型別資訊；防 injection 並非它獨有。表名、欄位名這類識別字無法參數化，仍然要自己把關。
  • 沒有任何快取。手冊明講 simple statement 每次執行節點都重新 parse，client 與 server 兩邊都不快取。
  • 型別靠 Java 型別猜。driver 不 parse 你的 CQL，不知道每個 ? 對到哪個欄位型別，只能依 Java 值的型別選 codec，然後讓伺服器去檢查。手冊的例子是對 bigint 欄位傳 1（Java int，4 位元組）而被拒絕，要改傳 1L。

同樣的機制套到書中的 INSERT 範例：start_date 是 date 欄位，傳 "2020-06-08" 這個 String 會被序列化成字串，不是 4 位元組的日期；guest_id 傳字串也不是 16 位元組的 UUID；room_number 是 smallint，傳 111（int）也長度不符。我的範例改傳 LocalDate、(short)、UUID。這個推論的機制有手冊支持，但我沒有對書中那段程式實際執行過，所以錯誤訊息的確切文字不敢保證。

反過來，把值直接寫成 CQL 字面值放進字串時（execute(String) 那種寫法），'2026-03-14' 這樣的字面值是由節點的 parser 依欄位型別解讀的，所以能通。「字面值嵌進字串」與「值當參數送」，型別是由不同的一方決定的。

依據：driver 4.x 手冊 Simple statements 頁。

範例程式在哪裡

書把 SimpleStatement 的完整範例放在 Reservation Service 專案的 simple-statement-solution branch，Prepared 與 Bound statement 的範例在 prepared-statement-solution branch。

Prepared Statements

多數應用程式反覆執行同一組查詢，只有參數值不同。SimpleStatement 適合臨時的查詢，卻要每次重送結構。PreparedStatement 就是為這種重複查詢設計的：結構只送給節點一次，換回一個 handle，之後只送 handle 加參數。

  • driver 送出：完整 CQL 字串與值
  • 節點：每次都收到整段查詢結構，得重新處理
  • driver：不保留跨次的狀態
  • driver 送出：prepare 時換回的識別碼與值
  • 節點：用識別碼找到先前準備好的 statement
  • driver：保留 PreparedStatement，反覆 bind

一個 access pattern 一個 prepared statement

書的建議是，資料模型推出幾個存取模式（access pattern），就為每個模式各建一個讀取用的 PreparedStatement，另外再為支撐這些模式的寫入各建一個。下面的範例把它們集中在一處建立，之後每次要查詢或寫入，只需 bind 再 execute。

PreparedStatement 不是 Statement 的子型別

參數化的語法和 SimpleStatement 一樣，關鍵差異是 PreparedStatement 並未實作 Statement。書說這樣設計是為了防止一種錯誤：把還沒綁值的 PreparedStatement 直接丟給 CqlSession 執行。型別系統在編譯期就把「還沒綁值」和「可以執行」切開，只有 bind 之後的 BoundStatement 能交給 execute()。

另外，CqlSession.prepare() 還有一個接受 SimpleStatement 的版本，參數化的 SimpleStatement 可以直接拿來 prepare。Query Builder 搭配 prepared 就是靠這個版本。

prepare() 背後發生的事

  1. 送給一個節點driver 把查詢字串交給一個 Cassandra 節點，換回一個唯一識別碼。想看的話可以呼叫 PreparedStatement.getId()。
  2. 識別碼成為 handle之後建立 BoundStatement 時引用的就是這個識別碼。
  3. 擴散到其他節點在一個節點 prepare 成功後，driver 接著在叢集的其他節點也 prepare 同一個 statement。
  4. 節點各自記著每個節點在內部記錄自己 prepare 過的 statement。

節點怎麼保存 prepared statement

早期版本把 prepared statement 放在快取裡，節點一重啟就沒了。從 Cassandra 3.10 起，每個節點把 prepared statement 存進本機的資料表，節點掛掉再回來時它們還在。

既然每個節點各自記著，就會遇到「某個節點不認得這個識別碼」的情況，比方節點剛重啟、或是後來才加入叢集。書描述了三個層次的處理，合起來讓 driver 與各節點保持一致。

機制什麼時候發生代價或用途
prepare 時擴散 第一個節點 prepare 成功之後 一次性，讓之後各節點都已準備好
節點恢復時重新 prepare 節點從 down 變回 up。由 advanced.prepared-statements.reprepare-on-up 這組設定控制，預設開啟 主要對 3.10 之前的叢集有用，因為 3.10 起節點自己就保有 prepared statement
執行時補 prepare driver 對一個沒 prepare 過的節點執行 PreparedStatement driver 自動補，應用程式無感，但書說要多一趟往返

driver 才是維持同步的一方，補 prepare 的代價比書說的大（書中未提）

  • Cassandra 不在叢集內複製 prepared statement。讓各節點的快取保持最新，是 driver 的責任。
  • 先一個節點，再其他節點。第一次 prepare 只送給單一節點，成功後才擴散。這樣查詢字串寫錯時，不會同時打到所有節點。這一步由 advanced.prepared-statements.prepare-on-all-nodes 控制。「其他節點」實際指 query plan 裡剩下的節點，預設 policy 下就是 local DC 的節點（這一句讀自 4.1.0 的原始碼）。
  • 識別碼是確定性的。它由查詢字串算出的雜湊，所以同一段字串在所有節點上識別碼一樣。
  • 補 prepare 的路徑。實際順序是：EXECUTE 送出，節點回 UNPREPARED，driver 送 PREPARE 並收到回覆，再重送 EXECUTE。手冊算成兩趟額外往返，書寫的是「一趟」。
  • driver 端也有快取。用同一段字串（且其他執行參數相同）重複呼叫 prepare()，會拿回同一個 PreparedStatement 實例，不會送任何請求。快取依字串逐字比對，不做 trim。快取是弱參考，所以仍要自己持有 PreparedStatement 的參考，不要每次請求都 prepare 一遍。

依據：driver 4.x 手冊 Prepared statements 頁。

PreparedStatement 是樣板

書把 PreparedStatement 說成建立查詢的樣板。它除了記著查詢的形狀，還能帶一些屬性，當作由它產生的 statement 的預設值，書舉的例子是預設一致性等級、retry policy 和 tracing。

4.x 裡預設值從哪裡來，以及 retry policy 的位置（書中未提）

4.x 的 Statement 共通屬性清單裡沒有 retry policy。retry policy 在 4.x 是用設定檔的 advanced.retry-policy 或 execution profile 指定，不是掛在單一 statement 上，書這一句比較像 3.x 時代的說法。

要讓 BoundStatement 繼承屬性，做法是把屬性設在你傳給 prepare() 的那個 SimpleStatement 上，bind 出來的物件會繼承。書在 Driver 設定那一節提到 execution profile 用的是同一條繼承路徑。

依據：driver 4.x 手冊 Statements、Retries、Prepared statements 頁。

prepared 也是安全機制

除了效率，書指出 PreparedStatement 把 CQL 的查詢邏輯和資料分開。injection 攻擊的做法是把指令塞進資料欄位，資料不再被當成語法解讀，就沒有可乘之機。

prepare SELECT * 的陷阱（書中未提）

prepare 時，節點會回報這個查詢的結果集有哪些欄位，driver 把它快取起來，之後的回應就不必再附。如果你 prepare 的是 SELECT *，之後有人對表 ALTER ADD 了欄位，在 Cassandra 3 以下，driver 手上的欄位描述就過時了：新回應多了一欄，driver 卻照舊描述解碼，輕則型別對不上而失敗，重則型別相容而讀到錯位的資料。

手冊的建議是 prepare 時一律列出需要的欄位。Cassandra 4 搭配 protocol v5 修正了這個問題，版本細節見 書後變化 一節。

依據：driver 4.x 手冊 Prepared statements 頁，段落 Prepared statements and schema changes。

Bound statement：綁值與執行

PreparedStatement 本身不能執行。要先呼叫 bind()，把真實的值套上去，得到 BoundStatement，再交給 CqlSession.execute()。

bind() 的三種用法

  • 一次給齊。bind(v1, v2, ...) 依序對應 prepared 字串裡的每個變數。
  • 只給前 n 個。其餘的值在執行前要用 setter 補。
  • 不帶參數。bind() 之後全部用 setter 一個一個設。

BoundStatement 針對各種型別提供一組 setXxx()，例如 setString()、setLocalDate()、setShort()、setUuid()，書的範例用欄位名稱指定要設哪個變數。

bind 本身沒有網路動作

bind 只是把值套進樣板，產生一個物件，裡面有 prepare 時換回來的識別碼，以及這次的參數值。真正的網路往返在 execute() 才發生，送出去的就是識別碼加值。

沒綁到的值會怎樣

執行 BoundStatement 時如果有變數沒綁值，使用 protocol v4（書寫 Cassandra 3.0 以上）時，這些值在伺服器端會被忽略。更舊的 protocol 版本，driver 的行為是只要有未綁的值就丟 IllegalStateException。

未綁定（unset）和綁成 null 是兩回事，v4 的起點也比書說的早（書中未提）

  • v4 以上沒綁的變數處於 unset 狀態，節點直接略過那個欄位，原有的值保持不動，也不會產生 tombstone。若綁成 null，則是明確寫入 null，等同刪除該欄位，會產生 tombstone。這呼應書在第 9 章的建議：不要把 NULL 寫進資料表。
  • 重用已設值的 bound statement 時，可以用 unset(...) 把某個變數退回 unset。
  • protocol v4 是 Cassandra 2.2 起就有，不是 3.0。書的括號寫 3.0 以上沒有錯，只是把下限抬高了。v3 要求每個變數都要綁。

依據：driver 4.x 手冊 Prepared statements 頁的 Unset values 段。

書中 bind 範例的幾個問題，與 builder 寫法（書中未提）

  • BoundStatement 同樣是 immutable，每個 setter 回傳新物件。連續設很多值時，ps.boundStatementBuilder() 可以避免產生一堆中間物件，最後 build()。
  • setter 除了欄位名稱，也有以 0 起算的索引版本。用名稱設值時，可以搭配具名變數 :name，也可以直接用欄位名；一個欄位在字串裡出現多次時（例如兩個範圍條件），欄位名會有歧義，這時改用索引。

為什麼 prepared 才能 token-aware

書在 Driver 設定 的 load balancing 一節說明，預設的 load balancing policy 在使用 PreparedStatement 時，會依 partition key 的 token 挑出持有該資料的 replica，讓需要被問到的節點變少。書的第 9 章也提到，客戶端用 token-aware 策略時，協調節點本身就可能是 replica。這一節補上書沒有說的部分：為什麼是 prepared 才做得到。

routing key 從哪裡來（書中未提）

  1. prepare 時節點的回應除了識別碼，還附上每個變數的 CQL 型別，以及哪幾個變數是 partition key 的組成部分。driver 把這些存在 PreparedStatement 裡，可以用 getPartitionKeyIndices() 看到。
  2. bind 時driver 知道哪幾個值是 partition key，就把它們序列化成 routing key。
  3. 挑節點時load balancing policy 用 routing key 算出 token，查出持有它的 replica，把這些節點排在 query plan 的前面。

SimpleStatement 不一樣。driver 不 parse 字串，不知道哪個 ? 對到 partition key，所以路由資訊從來不會自動算出，query plan 退化成本地資料中心節點的輪流排序。想要的話可以在 statement 上手動呼叫 setRoutingKeyspace() 與 setRoutingKey() 補上。

依據：driver 4.x 手冊 Load balancing 頁的 Token-aware 一節，以及 Prepared statements 頁。

同一筆寫入的四種寫法

把前面三節收在一起。先定義兩個共用的 CQL 字串，再看同一筆訂房在各種寫法下長什麼樣。

做法每次執行送什麼適合
execute(String) 完整字串，值已經在裡面 沒有變動值的固定查詢、臨時查看資料
SimpleStatement 帶值 完整字串，加上分開的值 只跑一兩次的臨時查詢
PreparedStatement + bind() 識別碼加值 反覆執行的查詢，也就是應用程式裡絕大多數的 access pattern

書的建議：臨時查詢用 simple，重複的查詢用 prepared

書把 SimpleStatement 定位成適合 ad hoc 查詢，PreparedStatement 則是反覆執行查詢時更有效率的做法。書的其他章節也呼應這個建議：第 13 章（Performance Tuning）的客戶端調校提示要求重複的查詢使用 prepared statement，以省頻寬並得到安全上的好處；第 9 章談 batch 大小限制時，說 prepared statement 因為只送識別碼與值，計入的大小比 simple statement 小。

  • Statement 是介面，實作有 SimpleStatement、BoundStatement、BatchStatement。execute(String) 是建 SimpleStatement 的便利寫法。手拼字串容易出錯，也有 injection 風險，值應該和語法分開送。
  • SimpleStatement 是字串加參數值，每次執行都把整個結構送給節點，節點每次重新理解它。適合臨時查詢。
  • PreparedStatement 把結構送一次、換回識別碼，之後只送識別碼和值。driver 會在其他節點也 prepare，節點恢復時重新 prepare，執行時發現節點不認得也會補 prepare。
  • PreparedStatement 不是 Statement。要 bind() 成 BoundStatement 才能執行。bind 可以一次給齊、給前 n 個、或全用 setter。v4 以上沒綁的值會被伺服器略過。
  • prepared 同時帶來效率與安全，也是 token-aware routing 的前提：prepare 時 driver 學到哪些變數是 partition key，simple statement 沒有這份資訊。
  • SimpleStatement 的值型別由 Java 型別推出來，容易對不上欄位型別；prepared 的型別在 prepare 時就已知。

Query Builder · p.285

Query Builder：用方法鏈組出 CQL

Query Builder 是 driver 另外提供的 fluent API，用 Java 方法鏈在程式裡組出查詢，最後 build 成 SimpleStatement。它對付的是查詢結構會在執行期變動的情況，也就是 PreparedStatement 的固定文字不好用的地方。

它解決什麼問題

前兩種工具各有強項。SimpleStatement 彈性最大，但查詢文字得自己拼。PreparedStatement 的效率和安全都好，前提是查詢文字固定。真實的應用程式常碰到第三種情況：查詢的結構本身要到執行期才決定，例如某個條件只有使用者填了才加進去。這時 prepared 很難用，因為每種條件組合都是不同的文字；手拼字串又回到上一節講過的風險。

書介紹的 Query Builder 補的就是這個洞。它以 fluent 風格的 API 用程式建立查詢，結構的變化交給一般的 Java 分支與迴圈去表達，不必動手拼字串。書也說，和 PreparedStatement 類似，它對 injection 攻擊提供一定程度的保護。

做法查詢結構能在執行期變嗎值怎麼進到查詢
手拼字串 可以 自己跳脫與拼接，容易出錯，有 injection 風險
Query Builder 可以，用 Java 程式控制 用 literal() 由 driver 轉成 CQL 字面值嵌入，或用 bindMarker() 留下佔位符
PreparedStatement 不容易，文字要固定 值走參數，不被當成 CQL 解析

官方手冊對使用時機的立場（書中未提）

  • 主要用途是動態產生。手冊舉的例子就是「依哪些搜尋參數有值，動態組出查詢」。查詢若全都能寫成編譯期的字串常數，用 Query Builder 並沒有比較好讀，也不見得比較不會出錯，手冊建議這種情況直接用字串。
  • 它不會替你保證 CQL 合法。fluent API 引導你，但沒有編碼完整的 CQL 文法，仍然可能產生非法語法。先想清楚要的 CQL，再寫出能產生它的程式，不要反過來靠它學 CQL。
  • 熱路徑上要小心。builder 的每一步都會建立新物件。手冊建議：常用的查詢用 bound statement，也就是啟動時 build 再 prepare；固定的查詢在初始化時 build 一次，存在欄位或常數；動態產生的查詢考慮加快取。

依據：driver 4.x 手冊 Query builder 頁。

座標與版本的補充（書中未提）

讓 IDE 引導你

書說這套 API 很適合搭配 IDE：每一步回傳的型別只提供合法的下一步，自動完成清單就是最好的導覽。查詢該長什麼樣的主導權在你，工具負責擋住明顯不合理的鏈法。

鏈上每一步的型別會變，缺了必要部分就 build 不了（書中未提）

書說 builder 每一步回傳「目前的查詢內容」，實際上這是一連串不同的型別。起點方法回傳的型別還不能 build，補上必要的部分之後，型別才變成可以 build 的。

起點回傳型別要補到什麼才能 build
selectFromSelectFrom至少一個 selector，例如 all() 或 column()
insertIntoInsertInto至少一個 value()
updateUpdateStart至少一個 assignment 與一個 where 條件
deleteFromDeleteSelection至少一個 where 條件
  • 每一步都產生新物件，builder 是 immutable 的。從同一個 SelectFrom 接不同的 column()，得到彼此獨立的兩個查詢，互不影響。
  • value() 定義在 InsertInto 這一側，不在 Insert 上。value() 回傳的 RegularInsert 同時是「還能繼續 value()」和「已經是 Insert」。書說 Insert.value()，是把這兩層合在一起說了。想用變數保存鏈到一半的結果，要留意宣告的型別。

build() 之後拿到什麼

鏈到一個可以 build 的物件之後呼叫 build()，書說回傳的是 SimpleStatement，可以直接交給 CqlSession.execute()。

build() 以外的出口，以及自動推斷的 idempotence（書中未提）

  • asCql() 回傳組好的 CQL 字串，拿來記 log 或寫單元測試很方便。
  • build(Object... values) 與 build(Map<String, Object>) 在 build 的同時附上位置或具名參數值。
  • builder() 回傳 SimpleStatementBuilder，可以在 build 之前再設 tracing、execution profile 之類的選項。
  • build 出來的 statement 會自動帶上推斷出的 idempotent 旗標。SELECT 一律視為 idempotent；計數器更新、對 list 的 append 或 prepend、用到不確定函式的寫入則視為非 idempotent，無法判斷時 builder 採悲觀判斷。這個旗標很重要，因為手冊說 retry 與 speculative execution 只會發生在 idempotent 的 statement 上。Driver 設定那一節會講這兩個機制，見 Driver 設定。

Insert 與 Select 的寫法

Insert

先用 insertInto(keyspace, table) 起一個 INSERT，接著對每個要寫的欄位呼叫一次 value(欄位名, 值)，最後 build()。

Select

literal() 與 bindMarker()：值怎麼進到查詢

鏈上每個要放「值」的位置，4.x 的簽名吃的是 Term，Java 的原始值得先轉換。書的 Select 範例末尾示範了 bindMarker()：它不給具體的值，只留一個佔位符，等到 PreparedStatement 被 bind 時再填。另一條路是用 literal() 把具體的值轉成 Term。

  • driver 依型別 codec 把值轉成 CQL 字面值，直接嵌進查詢文字，例如 'KT4P8N'
  • 每個不同的值都產生不同的文字
  • build 出來的 SimpleStatement 可以直接 execute()
  • 每次送的都是不同的完整查詢文字，沒有可重用的 handle
  • 文字裡留下 ?，具名版本是 bindMarker("name")，產生 :name
  • 文字固定，值留到之後
  • 值由 PreparedStatement.bind() 或 build(values) 補上
  • 配合 prepare，可以享有 prepared 的好處

書中 Query Builder 範例直接傳 Java 值，在 4.x 編譯不過

書的 insert 範例把 "RS2G0Z"、111 這類原始值直接交給 value()，select 範例也把字串直接交給 isEqualTo()。4.x 的 InsertInto.value(String, Term) 與 isEqualTo(Term) 簽名都要 Term，原始值要先經過 literal(...)（或換成 bindMarker()）才能放進去。書上的寫法看起來是更早期 API 草稿的殘留，這是我的推測，簽名本身我對照過 driver 原始碼。我的範例一律寫成正確的形式。

依據：OngoingValues、ColumnRelationBuilder、QueryBuilder 的原始碼，以及手冊 Terms 頁。

「一定程度的保護」到哪裡為止（書中未提）

  • literal() 把值交給對應型別的 codec，格式化成 CQL 字面值再嵌入，字串會被當成字串字面值處理。值走這條格式化路徑，所以從值進來的 injection 受到限制。書說「一定程度」是合理的。
  • 有幾個入口會原樣嵌入你給的字串，不跳脫也不檢查：raw()、InsertInto.json(String)，以及 selectors 或 deleteFrom 上的 raw 版本。把使用者輸入餵給這些入口，就回到手拼字串的老問題。
  • 需要自訂 Java 型別時，literal(value, codecRegistry) 或 literal(value, codec) 讓你指定轉換方式。找不到預設對應時會丟 CodecNotFoundException。

依據：driver 4.x 手冊 Terms 頁與 Insert、Delete 頁。

literal 版本不要拿去 prepare

prepared 的識別碼由查詢文字決定。把 literal(v) 版本的查詢拿去 prepare，每換一個 v 文字就不同，等於每個值都產生一個新的 prepared statement，每個值都多一趟 PREPARE 的往返，節點那邊的 prepared 快取也會被這些一次性的條目擠滿（我記得節點的這份快取有大小上限，但沒有查證）。driver 這一側的快取，依 4.x 手冊用的是 weak values 回收，你的程式不再引用的實例會被清掉，所以負擔主要落在節點與多出來的往返。這一點是我從「識別碼由文字決定」推得的，加上上面那個沒查證的細節，所以把握度標中等。要 prepare 就用 bindMarker()。

另一個小細節：literal 嵌入的是 CQL 字面值，由節點的 parser 依欄位型別解讀，所以對 date 欄位寫 literal("2026-03-14") 這種字串能通；但 uuid 欄位的 CQL 字面值不帶引號，字串版本的 uuid 我記得會被節點拒絕，這點同樣沒有查證。範例都改傳 LocalDate 與 UUID 物件，不依賴這些細節。

搭配 PreparedStatement

書示範了 Query Builder 與 prepared 的合用：把比較的值換成 bindMarker()，build 出來的 SimpleStatement 文字裡就帶 ?，再交給 CqlSession.prepare()。這條路能走通，靠的是上一節提過的事實：prepare() 有一個接受 SimpleStatement 的版本。

  1. 組出帶佔位符的查詢值的位置用 bindMarker()，其餘結構照常鏈出來，最後 build()。
  2. prepare把得到的 SimpleStatement 交給 session.prepare()，走前一節講過的流程：節點換回識別碼，driver 擴散到其他節點。
  3. 執行期 bind每次請求只呼叫 bind(值)，得到 BoundStatement 再 execute()。

bind() 回傳的是 BoundStatement，不是 SimpleStatement（書中筆誤）

書在這個例子的最後一行，把 reservationSelectPrepared.bind("RS2G0Z") 的結果存進一個 SimpleStatement 型別的變數。PreparedStatement.bind(Object...) 的回傳型別是 BoundStatement，它不是 SimpleStatement，這行無法編譯。書自己在上一節講 Bound statement 時用的也是 BoundStatement，所以這行是筆誤，不是設計。前一個 select 範例裡的變數名 reseravationSelectStatement 也拼錯了。

三種工具怎麼選

把書這一路介紹的做法排在一起，依查詢的性質選。

查詢的性質用什麼理由
臨時、只跑一兩次 SimpleStatement（可帶值） 不必先 prepare，寫起來最快
結構固定、反覆執行 PreparedStatement 結構送一次，之後只送識別碼與值
結構要依條件變化 Query Builder，build() 後執行 文字固定不下來，prepared 難用；用程式控制結構，不必拼字串

結構會變、但每種結構會重複出現時（書中未提）

兩種做法可以合用：用 Query Builder 配 bindMarker() 組出各種結構，每種結構第一次出現時 prepare，之後用結構當鍵放進自己的快取。上面修改訂房的例子有 N 個可選欄位，最多只會有 2 的 N 次方種結構，實務上通常遠少於此。driver 手冊對動態產生的查詢給的建議是考慮加快取，這裡的合用方式是我從它延伸的做法，不是手冊或書的明確步驟。

  • Query Builder 是獨立的 artifact（java-driver-query-builder），用靜態匯入使用 QueryBuilder 的靜態方法。
  • 它主要解決查詢結構會變的情況，例如可選的條件。這是 PreparedStatement 的固定文字難以處理的地方。它對 injection 只提供一定程度的保護。
  • 流程是 selectFrom、insertInto、update、deleteFrom 起頭，鏈上方法，最後 build() 得到 SimpleStatement。每一步的型別不同，缺必要部分就 build 不了。
  • 值有兩種放法：literal() 嵌進文字，或 bindMarker() 留下佔位符。4.x 這些位置吃 Term，書中直接傳 Java 值的寫法要改。
  • bindMarker() 搭配 prepare(build()) 與 bind()，結果是 BoundStatement。這是 Query Builder 與 prepared 合用的路徑。
  • 固定的靜態查詢直接寫字串更簡單；熱路徑上不要每次都重新 build，啟動時 build 並 prepare，或把動態結果加快取。

Object Mapper · p.288

Object Mapper

前面幾種寫法都要自己準備 statement，再用 Row 的 getter 一欄一欄取值。mapper 把這兩件事交給編譯期產生的程式碼：你只寫帶 annotation 的 entity、DAO 與 mapper 介面，執行時呼叫 DAO 方法，就等於送出查詢並拿回物件。

定位：statement 之上再多一層抽象

書把 mapper 排在 statement 系列技法的最後，說它多給一層抽象。你面對的是 domain model（或 API 上流通的資料型別），不是 CQL 字串和 Row。它靠原始碼裡的 annotation 運作，用 annotation 把 Java 類別對到資料表，或對到 user-defined type（UDT）。書特別點出，專案已經有 domain model 時，這個工具特別有用。

技法你親手寫的結果怎麼變成 Java 物件
SimpleStatementCQL 字串與參數值迭代 Row，用 getString() 之類逐欄取值
PreparedStatement、BoundStatementCQL 字串（prepare 一次）與 bind 的值同上
Query Builder用 fluent API 組出的查詢同上
Object Mapper帶 annotation 的 entity、DAO、mapper 介面產生的程式碼把 Row 轉成 entity

mapper 接手的三件事

  • 建 statement 並執行。書說 save() 之類的 DAO 方法會替你 build 並 execute。
  • 把結果轉成物件。find 類方法直接回傳 entity，不經過 Row getter。
  • Java 名稱與 CQL 名稱的對應。這件事交給 naming strategy，後面的 entity 小節會講。

三件事都沒有消失，只是從執行期的手寫程式碼，搬到編譯期由 processor 產生。

兩個函式庫：一個編譯期，一個執行期

書說 mapper 以兩個獨立函式庫提供，分別服務編譯期和執行期，所以 pom 要多加兩個依賴。兩個 artifact 的 groupId 都是 com.datastax.oss，版本跟 driver 用同一個 ${driver.version}。

artifact書上放在哪角色
java-driver-mapper-processor編譯路徑（compile path）編譯期工具，讀 annotation 並產生程式碼
java-driver-mapper-runtime執行期依賴應用程式執行時需要的函式庫

Maven 座標在書出版之後有調整，細節看 書後變化。

為什麼要拆成兩個

processor 只在 javac 編譯你的原始碼時派上用場，產生完程式碼就沒事了，不需要跟著應用程式一起部署。runtime 函式庫則是產生出來的程式碼在執行時要呼叫的東西，必須隨應用程式一起帶著走。兩者的生命週期不同，拆開就能各放各的位置。

「執行期依賴」不要寫成 scope runtime

書中未提：官方手冊說 java-driver-mapper-runtime 同時包含 annotation 與少量工具類別。你的 entity 和 DAO 原始碼要 import 那些 annotation，所以這個 artifact 在編譯時也必須看得到。手冊把它列為一般依賴。書的 pom 片段沒有寫 scope 元素，「runtime dependency」這個說法應該只是在講執行時也要有，不能讀成 Maven 的 <scope>runtime</scope>。照字面設成 runtime scope，你的原始碼會編譯不過。

processor 則在 javac 的主要編譯開始之前，先從你的 annotation 產生額外的 Java 原始碼，再連同你寫的程式碼一起編譯。它只需要出現在編譯路徑。Maven 裡宣告 processor 的建議方式（compiler plugin 的 annotationProcessorPaths，或 provided scope）見 書後變化的 Query Builder 與 Object Mapper。

三個角色與產生碼的鏈

mapper API 建在資料存取的標準設計模式上：entity class 與 Data Access Object（DAO）。你為設計裡的每張表寫一個 entity class，寫一個 DAO 介面來宣告對 entity 的查詢，再寫一個 mapper 介面專門用來取得 DAO 實例。mapper 依你提供的類別與介面產生程式碼。

Entity class
對應一張表（或一個 UDT）。一張表一個類別，欄位對應資料行。
DAO 介面
宣告「對 entity 能做哪些查詢」。只有方法簽名和 annotation，沒有實作。
Mapper 介面
宣告「怎麼拿到 DAO」。每個回傳 DAO 的方法都是一個工廠方法。
  1. 你寫並標註entity 加 @Entity，DAO 介面加 @Dao 並用 @Select 等標出每個方法的查詢種類，mapper 介面加 @Mapper，回傳 DAO 的方法加 @DaoFactory。
  2. 編譯時產生實作annotation processor 解讀這些 annotation。書點名的產物是 builder 類別，名稱是 mapper 介面名加 Builder，例如 ReservationMapperBuilder。mapper 與 DAO 的實作物件也由產生碼提供。
  3. 啟動時接上 session用 builder 包住你的 CqlSession，build() 得到 mapper 實作。
  4. 取得 DAO呼叫 mapper 上的 @DaoFactory 方法，拿到實作了 DAO 介面的物件。
  5. 呼叫 DAO 方法實作會替你建 statement、執行、把結果轉成 entity。
  6. 底下送出查詢最後這一環，書沒有說 DAO 實作怎麼把查詢交給 session。

最後一環：DAO 建立時 prepare，呼叫時 bind 再執行

書中未提。依官方手冊和 processor 原始碼：DAO 實作在初始化時，會先為每個 entity 建立轉換用的 helper，檢查 entity 與資料表是否對得上，再把各 DAO 方法用到的查詢逐一 prepare。之後每次呼叫 DAO 方法，只是把參數 bind 進已 prepare 的 statement，交給你的 CqlSession 送出。

手冊的 logging 範例顯示，mapper 產生的類別會在 DEBUG 層級記下它實際 prepare 的查詢字串。想知道 mapper 底下到底送了什麼 CQL，把產生碼的 logger 開到 DEBUG 最直接。prepare 發生在建立 DAO 的那一刻，第一次呼叫方法時查詢早已 prepare 好。

先想想：專案原始碼裡找不到 ReservationMapperBuilder，為什麼可以 new 它？

它是編譯時由 processor 產生的類別，名稱由 mapper 介面名加 Builder 組成。所以第一次引用它之前要先編譯過一次。IDE 如果一直報找不到這個類別，先檢查 annotation processing 有沒有跑。

Entity：欄位如何對到資料表

書的第一個例子是 ReservationsByConfirmation，對應 reservations_by_confirmation 表。它只用到三個 annotation。

  • @Entity：標記這個類別要被 mapper 處理。對象可以是表，也可以是 UDT。
  • @NamingStrategy：指定 mapper 怎麼把 Java 識別字對到 CQL 名稱。
  • @PartitionKey：標出哪個欄位是 partition key。

SNAKE_CASE_INSENSITIVE 的規則是：把 Java 風格的類別名與成員名轉成全小寫，單字之間插底線。書說這正是 CQL 建議的命名風格。

UDT 也是 entity

domain model 裡如果有類別引用另一個類別，被引用的那個也加上 @Entity，就會被當成 UDT。mapper 會沿著你標好的型別遞迴處理。

entity 的最低要求與預設值

  • 預設 mapper 預期 entity 是可變的 JavaBean：非 private 的無參數建構子，加上每個屬性一組 getter 與 setter。書中範例結尾那行「constructors, get/set methods」就是在省略這些。
  • 沒標 @NamingStrategy 時，預設就是 SNAKE_CASE_INSENSITIVE。書的範例特地寫出來，效果跟不寫一樣，但讀者一眼就看得出規則。
  • 內建 convention 的名稱轉換在編譯期就做完，結果直接寫進產生碼。只有自訂的 NameConverter 才會在執行時呼叫。
  • 名稱不符規則時，可以用 @CqlName 單獨覆寫（類別和欄位都能用）。表有 clustering column 時，那些欄位要標 @ClusteringColumn。

mapper 可能在你不知情時寫出 tombstone

第 9 章的 Deleting 一節提醒過：Cassandra 把寫入 NULL 當成刪除。像 Spring Data Cassandra 或 driver 的 Mapper 這類框架會把這個行為藏起來，entity 裡沒填的欄位就可能變成 NULL 寫進去，累積大量 tombstone 而不自知。書的建議是用任何抽象 CQL 的框架之前，先確認並設好它對 null 的處理方式。細節在第 9 章，這裡只記住：save() 一行呼叫背後的 null 行為要查清楚。

mapper 的 null 處理選項

書中未提。官方手冊說 mapper 有兩種 null saving strategy：DO_NOT_SET 遇到 null 屬性就不綁值，不產生 tombstone，代價是更新時舊值不會被清掉；SET_TO_NULL 一律綁值，null 就是寫入 null。沒指定時預設是 DO_NOT_SET，可以在方法 annotation 的 nullSavingStrategy 上設，或在 DAO 介面加 @DefaultNullSavingStrategy 一次設定。

這是現行 4.x 手冊的內容。我沒有查這個選項從哪個版本開始存在，書出版當時的預設行為請以你專案用的 driver 版本為準，所以標中等。

DAO 方法可以直接回傳 CompletionStage

書只說 mapper 有非同步的 DAO 方法。官方手冊的作法是把回傳型別包成 CompletionStage 或 CompletableFuture，例如 @Select 方法回傳 CompletionStage<ReservationsByConfirmation>，@Insert 方法回傳 CompletionStage<Void>。多列結果要換成非同步版本的 MappedAsyncPagingIterable。

  • mapper 是 statement 之上的一層抽象：你寫 annotation 過的 entity、DAO、mapper 介面，編譯期由 processor 產生實作，執行時不再手寫 statement 和 Row 轉換。
  • 兩個 artifact 分工不同：java-driver-mapper-processor 只在編譯期，java-driver-mapper-runtime 在執行期。另外（書外補充）runtime 要當一般依賴，因為你的原始碼要 import 它裡面的 annotation。
  • 鏈是 entity、DAO、mapper 介面 → 編譯期產生碼 → XxxMapperBuilder(session).build() → @DaoFactory 方法 → 呼叫 DAO 方法。builder 類別在編譯時才出現。
  • @NamingStrategy(SNAKE_CASE_INSENSITIVE) 把 confirmNumber 轉成 confirm_number。名稱得自己對上；書外補充：4.5.0 起 mapper 會在建立 DAO 時檢查 schema，對不上就丟例外。
  • @Select 預設依 key 查（書說參數對上 partition key），customWhereClause 的 placeholder 名稱要和方法參數對上（書外補充）。@Insert 對 Cassandra 就是 INSERT 或 UPDATE。
  • mapper 和 DAO 要像 CqlSession 一樣啟動時建一次、全程重用，並留意 null 欄位被寫成 tombstone。

Asynchronous Execution · p.294

非同步執行

同步的 execute() 會讓呼叫它的執行緒一路等到回應。executeAsync() 送出請求就返回一個 CompletionStage，後續處理用串接的方式掛上去，多筆互不相依的查詢因此可以同時在途。

同步 execute() 卡住的是誰

CqlSession.execute() 是同步操作。呼叫它的那條執行緒會一直等，直到拿到結果，或發生錯誤才往下走，書舉的錯誤例子是網路逾時。等待期間這條執行緒什麼也做不了。

要查 N 筆彼此不相干的資料，同步寫法就是 N 次等待首尾相接，總時間大約是各筆延遲的總和。driver 另外提供 executeAsync()：送出請求後立刻返回，不等結果。書的說法是，這種非阻塞的請求讓你更容易同時送出多個查詢，加快 client 應用程式。

下面的元件把這個差別畫成時間軸。操作時請觀察這幾件事：

  • 同步那一條的總長度隨筆數成比例增加，因為每一筆都要等前一筆做完。
  • 非同步那一條的總長度主要由最慢的一筆決定，筆數增加對它的影響小很多。
  • 筆數降到 1 時兩者沒有差別。非同步省下的是「等待時間的重疊」，單筆查詢沒有東西可以重疊。
  • 模型假設查詢之間互不相依。下一小節會看到，一旦第二筆要用第一筆的結果，先後順序就回來了。

為什麼一次送出很多請求在連線上行得通

書在 Driver Configuration 的連線池一節說明了底層：CQL native protocol 本身是非同步的，一條連線可以同時承載多個請求，協定 v3 以後最多 32,768 個。因此每個節點預設只需要一條連線，driver 設定的單連線同時請求上限預設為 1,024。executeAsync() 連發多筆，不需要多開連線，請求只是在同一條連線上同時在途。協定怎麼區分這些請求，書沒有講。設定細節見 Driver 設定。

怎麼等全部完成，以及不要無上限地送

  • 書中未提：要等一批 stage 全部完成，可以用 JDK 的 CompletableFuture.allOf(...)，把每個 stage 先用 toCompletableFuture() 轉成 future 再傳入。
  • 書也沒說同時在途的請求數量不加控制會怎樣。數萬筆一次丟出去，壓力會直接落在 client 與節點上。driver 有 request throttler（設定鍵 advanced.throttler），預設是不節流的 pass-through，另有限制同時請求數與限制每單位時間請求數兩種實作，多出來的請求先排隊，排隊佇列滿了才會以 RequestThrottlingException 失敗。自己分批或用 semaphore 控制也可以。

以上出自官方手冊。throttler 在 4.0 的 changelog 就已列出，不算書後新增。

先想想：executeAsync() 一返回，查詢已經完成了嗎？

沒有。返回的是一個還沒完成的 CompletionStage，請求才剛送出。結果要等回應到達、driver 讓 stage 完成之後才存在。想讀資料，就得把處理邏輯掛在這個 stage 上，下一小節講怎麼掛。

executeAsync() 回傳什麼

前面幾節出現過的任何 statement，都可以改用非同步方式執行。回傳的是一個之後會以 AsyncResultSet 完成的階段，資料要等它完成才拿得到。

從 driver 4.0 開始，executeAsync() 和其他非同步方法回傳的都是 Java 8 引進的 CompletionStage。3.x 系列用的是 Guava 的 ListenableFuture。CompletionStage 代表一個計算的階段，階段之間可以串接：一個階段完成時，依賴它的階段就被觸發。driver 的非同步 API 因此能組出由 CQL 查詢與結果處理程式碼交替構成的處理鏈。

AsyncResultSet 跟同步的 ResultSet 差在哪

書只在簽名裡用到 AsyncResultSet，並對它呼叫 one()，沒有解釋它。官方手冊的說明如下。

  • 設計原因：3.x 時同步與非同步 API 回傳同一種 ResultSet，非同步程式碼一不小心就會在迭代時觸發背景的同步取頁，抵消非同步的好處，還可能死結。4.x 另立 AsyncResultSet 來避免這件事。
  • 迭代範圍：只涵蓋目前這一頁，用 currentPage() 或 one() 取列，remaining() 回報這一頁還剩幾列。對照之下，第 9 章會講到同步 ResultSet 迭代到頁尾時，driver 會自動去取下一頁。
  • 取下一頁：hasMorePages() 為真時呼叫 fetchNextPage()，它回傳新的 CompletionStage<AsyncResultSet>，再用下一小節的串接方式一頁一頁接下去。

書的範例只取 one()，沒有碰到分頁。真要處理多頁結果，這套明確取頁的寫法才是非同步 API 的完整樣子。

串接：先查再刪

書用一個兩步的例子示範串接。要刪掉一筆預約，得先用確認碼從 reservations_by_confirmation 讀出主鍵欄位，再拿這些欄位去刪 reservations_by_hotel_date 裡對應的那一列。第二步依賴第一步的結果，所以是一條鏈：先有查詢那一階段（書叫 selectStage），再有刪除那一階段（書叫 deleteStage），最後掛一個回報成敗的收尾。下面的範例把這兩個階段叫作 findStage 與 removeStage。

兩個方法各有分工。書只示範了用法，沒有解釋它們的語意，下面是依 JDK 的 CompletionStage 文件補的說明：

  • thenCompose：前一步完成後要接另一個非同步呼叫時用。你的 lambda 回傳 executeAsync() 給的 stage，整條鏈就接上去了。書的 deleteStage 就是這樣來的。
  • whenComplete：成功與失敗都會被呼叫，拿到兩個參數：結果與錯誤。書的寫法是先看 error 是否為 null，再分別印出失敗與成功。
  1. 送出第一個查詢executeAsync(select) 立刻回傳尚未完成的 findStage，請求已在網路上。
  2. 登記第二步thenCompose(...) 只是登記「findStage 完成後跑這段 lambda」，同樣立刻回傳尚未完成的 removeStage。
  3. 登記收尾whenComplete(...) 再登記最後一段。到這裡這幾行程式碼已經執行完，沒有任何執行緒在等。
  4. select 的回應到達driver 讓 findStage 完成，觸發 lambda。lambda 讀出主鍵欄位，送出 delete，回傳新的 stage。
  5. delete 的回應到達removeStage 此時才完成，觸發 whenComplete，由 error 是否為 null 分成敗。

書自己說這個範例是簡化版

書提醒，實務上你可能想改用 prepared statement，也可以用 batch 一次刪掉 reservations_by_confirmation 和 reservations_by_hotel_date 兩張表裡的資料。Reservation Service repository 的 async-solution 分支有更完整的非同步範例。上面我的版本已經改用 prepared statement，batch 是第 9 章的主題。

書沒用到的其他串接方法

本節只出現 thenCompose 和 whenComplete。CompletionStage 的其他常用方法是 JDK 標準 API，書中未提：

  • thenApply：用同步函式轉換結果，回傳值包進新的 stage。lambda 若回傳的是 stage，會得到巢狀的 stage，這時要改用 thenCompose。
  • thenAccept：只消費結果、不產出值，適合純副作用的收尾。
  • exceptionally：只在失敗時介入，可以回傳一個替代值讓鏈繼續。
  • thenApplyAsync 之類帶 Async 後綴的版本：可以指定在哪個 executor 上跑 lambda。

錯誤怎麼傳，callback 在哪條執行緒跑

書中未提，出自官方手冊與 JDK 的語意：

  • select 失敗時，thenCompose 的 lambda 根本不會跑。第二步的 stage 跟著失敗，whenComplete 收到非 null 的 error。經過依賴階段傳下來的錯誤，JDK 常把它包成 CompletionException，真正的原因要看 getCause()。lambda 自己丟例外（例如 one() 回傳 null 後取值）也會讓 stage 失敗。
  • 只掛 thenAccept 而不處理錯誤，失敗會被默默吞掉：callback 不執行，錯誤不會出現在任何地方。收尾要記得用 whenComplete 或 exceptionally 接住。
  • 你登記的 callback 在 driver 自己的執行緒上跑：查詢結果在 I/O 執行緒池，建立 session 之類的管理工作在 admin 執行緒池。callback 裡不要做耗時運算，要做就用 thenApplyAsync(fn, executor) 丟到自己的 executor。
  • 不要在 callback 裡呼叫同步的 execute()。同步呼叫會等回應，若請求剛好被分到正在跑這個 callback 的 I/O 執行緒，就會死結。driver 偵測到這種情形會直接丟 IllegalStateException（在 stage 裡看到時通常被包在 CompletionException 裡）。在 callback 裡呼叫 executeAsync() 則是安全的，書的範例就是這樣。

書中範例程式的幾處問題

  • SELECT 字串寫 confirmation_number=RS2G0Z，字串值沒有加單引號。CQL 裡文字值要加單引號，這樣寫會被當成識別字而語法錯誤。同一段程式碼稍後讀 Row 用 confirm_number，欄名也不一致，這跟 Object Mapper 那節點出的 confirm_number 與 confirmation_number 是同一個問題。
  • DELETE 的第一個 ? 對應 hotel_id，書傳入的卻是 getString("confirm_number") 的值。該傳 hotel_id 欄，我的版本改正了。
  • 書沒處理 one() 回傳 null（查無此預約）的情形，我的版本補了判斷。

getInt 讀 smallint 欄位

書的範例用 getInt("room_number") 讀 room_number，這個欄位在 schema 裡是 smallint。我讀 driver 的 codec 查找程式碼，推論 smallint 預設只對應 Java short，用 getInt 讀它會丟 CodecNotFoundException，該用 getShort。我沒有實際執行驗證，所以標中等。

Reactive 風格程式設計

書中的 Reactive Style Programming 提示框

書說，想要更進階的非同步寫法，可能聽過 reactive streams。這是一項倡議，目標是提供帶有非阻塞 back pressure 的非同步串流處理。JDK 9 起它成為 Java 平台的正式部分，介面在 java.util.concurrent.Flow.*。

driver 從 4.4 開始內建 reactive 查詢支援：CqlSession 介面繼承新的 ReactiveSession 介面，後者新增 executeReactive() 之類的方法，讓你把查詢表達成 reactive streams。細節書指向 driver 的 reactive streams 文件。

CompletionStage 與 reactive streams 的分工

CompletionStage 描述「一件事之後會完成」，像 executeAsync() 這樣，完成時交出一個結果。reactive streams 描述「一串資料陸續到來」。書只點名了 back pressure，沒有展開。它在規格層面的意思是：消費端能告訴生產端「我現在只能收這麼多」，生產端因此不會把消費端淹沒。driver 實際怎麼配合這個機制，書沒講，見下方書外補充。

driver 的 reactive 型別不是 JDK 的 Flow

  • 書中未提：官方手冊說 executeReactive() 回傳的 ReactiveResultSet 是 org.reactivestreams.Publisher，需要 classpath 上有 Reactive Streams API 函式庫。JDK 9 的 Flow 介面與它規格同源、方法一一對應，但套件不同，不能直接互換。
  • executeReactive() 返回時，請求還沒有送出。要等到有人 subscribe 才會執行。例如在 doOnNext 之類的運算子裡呼叫 executeReactive()，卻沒有訂閱它的回傳值，那個查詢就不會送出。
  • 手冊談到 back pressure：讀取時 driver 隨訂閱者消費資料的節奏才去取下一頁，消費得慢會拖慢伺服器那端的輸出，但太慢的訂閱者仍可能造成 client 或伺服器逾時。寫入沒有這種調節，要自己限制並行數。
  • reactive 支援從 4.4 才有，這跟書的說法一致。再往後的變化看 書後變化的非同步與 reactive。
  • execute() 會讓呼叫執行緒一路等到回應。executeAsync() 送出就返回，互不相依的查詢因此能同時在途，總時間趨近最慢的那一筆。
  • 4.0 起非同步方法回傳 Java 8 的 CompletionStage，3.x 用 Guava 的 ListenableFuture。executeAsync() 給的是 CompletionStage<AsyncResultSet>。
  • 相依的步驟用 thenCompose 串接：lambda 回傳另一個非同步呼叫的 stage。用 whenComplete 同時處理成功與失敗，先看 error 是否為 null。
  • 相依的查詢仍然是依序進行，非同步省下的是被卡住的執行緒，不是這幾步本身的延遲。
  • 非同步操作不只 executeAsync()：還有 prepareAsync()、closeAsync()、CqlSessionBuilder.buildAsync() 和 mapper 的一些操作。範例分支是 async-solution。
  • reactive streams 是更進階的選項：串流加 back pressure。driver 4.4 起 CqlSession 繼承 ReactiveSession，用 executeReactive()。

Driver 設定

前面幾節你只是順手用 builder 設過 contact point 和 keyspace。這一節把整個設定體系攤開來看：設定檔放哪裡、哪些選項最常動，以及 driver 在負載分配、失敗重試、推測執行、連線池、協定與認證上，替你預先做了哪些決定。其中 load balancing、retry、speculative execution 三者環環相扣：query plan 是重試與推測執行挑下一個節點的依據（這個關係書沒明說，後面會補上依據），看懂這一點，就能預測節點出狀況時一個請求會怎麼走。

檔案式設定（File-based configuration）

同一份設定有兩條路進 driver。第一條是程式化：用 CqlSession.builder() 一個方法接一個方法設。第二條是設定檔，它能涵蓋的選項比 builder 完整，書的立場是多數情況偏好用設定檔。

設定檔這條路沒有自創格式：解析工作交給 Typesafe Config（JVM 語言通用的開源設定函式庫），檔案內容寫成 HOCON（Human-Optimized Config Object Notation）。連找檔案的規矩也照搬它的慣例，掃描 classpath，看有沒有 application.conf、application.json、application.properties 其中之一。「誰來讀、怎麼讀」這件事，driver 包成一個叫 config loader 的介面，而且允許抽換，預設行為不合用就自己實作一個。

設定怎麼疊起來，以及怎麼換載入來源

書沒有展開這一層，但實務上你很快會碰到。

  • driver 的 jar 裡附了一份 reference.conf，裝著所有選項的預設值。你的 application.conf 只需要寫想改的鍵，其他自動沿用預設。手冊列出的查找順序是：系統屬性、application.conf／.json／.properties、reference.conf。所以可以在啟動參數臨時覆寫單一選項，例如 -Ddatastax-java-driver.basic.request.timeout="5 seconds"。
  • 換載入來源用 DriverConfigLoader 的工廠方法：fromClasspath（換檔名）、fromFile、fromUrl，或 programmaticBuilder()（在程式裡組設定），再用 CqlSession.builder().withConfigLoader(loader) 注入。檔案類的 loader 一樣會 fallback 到 reference.conf、接受系統屬性覆寫、依 interval 重新載入。
  • builder 上有專屬方法的選項（withLocalDatacenter、withKeyspace、withAuthProvider 等），javadoc 寫明它們會蓋過設定檔裡的對應值。例外是 contact points：builder 與設定檔兩邊都給的話是合併，兩邊都沒給才退回 127.0.0.1:9042。
  • programmaticBuilder() 設的值是疊在 application.conf 與 reference.conf 之上，沒有程式化設定的鍵，照樣從這兩份檔案取值；系統屬性的優先序又比程式化的值高。這是我對照 4.1.0 與目前 4.x 分支的原始碼確認的。手冊對這個 loader 的說法是「用程式化方式取代從靜態資源載入選項」，字面上看不出 application.conf 還在不在，容易誤會。

請求參數的預設值，以及 timeout 的真正範圍

這一節只給了 reload interval 的預設值。timeout 的預設值書中沒有給；consistency 的 LOCAL_ONE 與 page-size 的 5000，書在第 9 章（談 consistency 與分頁的地方）各提過一次。4.x 參考檔裡這三個請求參數的預設值合起來是：basic.request.timeout 2 秒、basic.request.consistency 為 LOCAL_ONE、basic.request.page-size 為 5000。

client 端 2 秒與伺服器端逾時：誰先喊停

書第 13 章的節點逾時表，列出 read_request_timeout_in_ms 預設 5000、write_request_timeout_in_ms 預設 2000。拿它對照 driver 預設的 2 秒：讀取慢過 2 秒時，通常是 client 端先逾時（DriverTimeoutException），coordinator 要等到 5 秒才會回傳 ReadTimeoutException；寫入的兩個數字很接近，誰先到看時機。

這是我拿兩邊預設值做的推論，不是手冊明寫的；你的叢集若調過逾時就要重算。它也預告了後面 retry 一節的結論：RetryPolicy 處理的是伺服器回報的逾時，client 端逾時不在它的處理範圍內。

Load balancing

要解決的問題

Cassandra 沒有主節點，任何節點都能接查詢，被挑中的那個就是該次查詢的 coordinator（第 6 章）。它再視查詢內容去找其他節點湊出答案。如果 client 永遠挑同一個節點當 coordinator，那個節點會被壓垮，其他節點卻閒著；多個 client 都這樣做時更糟。所以 driver 把「這次請求交給誰」做成一個可抽換的元件，也就是實作 LoadBalancingPolicy 介面的物件。

policy 要回答的問題

兩個問題，外加一種通知

  • 這個節點離我多遠？每個節點被分成 local、remote 或 ignored。driver 偏好跟 local 節點互動，並替 local 節點維持比 remote 更多的連線。書把這個操作稱為 distance()，列舉叫 HostDistance。
  • 這次請求該依序試哪些節點？newQueryPlan() 回傳一份有順序的節點清單，這份清單就是 query plan。
  • 叢集有什麼變動？節點加入、移除、上線、下線時，driver 會通知 policy，policy 才能把 down 或已移除的節點排除在 plan 之外。

4.x 的實際名稱

書上的 distance() 與 HostDistance 是 3.x 的 API。4.x 的 LoadBalancingPolicy 沒有 distance() 這個方法：policy 在 init(...) 收到一個 DistanceReporter，之後在 init(...) 與 onAdd(...) 時呼叫它的 setDistance(node, distance) 主動回報距離；列舉叫 NodeDistance，值是 LOCAL、REMOTE、IGNORED。被判為 IGNORED 的節點，driver 不會對它開任何連線。

query plan 的方法是 newQueryPlan(Request, Session)，回傳 Queue<Node>；通知方法是 onAdd、onUp、onDown、onRemove。版本差異的整理見 書後更新。

從可組合到單一預設

driver 附多個 LoadBalancingPolicy 實作，API 設計成可以組合，由使用者挑選要哪些行為。書中提到的舊名稱有 RoundRobinPolicy、TokenAwarePolicy、DCAwareRoundRobinPolicy。

好處是可以精細調整，代價是每個使用者都得自己決定怎麼組合。

只出貨一個預設 policy，目的是簡化開發者的使用經驗。書形容它是依許多部署觀察到的最佳實務做成的「有主見」實作，下面三個行為預設全開。

預設 policy 的行為實際做什麼對應的舊 policy
輪流分配（round-robin）把請求以重複輪轉的方式分攤到各節點，攤平處理負載RoundRobinPolicy
token awareness使用 PreparedStatement 時，取 partition key 的 token，挑出持有該資料的 replica 當 coordinator，減少需要經手的節點數TokenAwarePolicy

local data center 一定要設

設法有兩種：建立 CqlSession 時用 builder 指定，或在設定檔寫 basic.load-balancing-policy.local-datacenter。預設 policy 要靠它判斷哪些節點算 local，所以不能省。

local DC 的拼法與失敗模式

  • 書上把方法寫成 withLocalDataCenter()；實際的方法名是 withLocalDatacenter()（datacenter 的 c 小寫）。
  • 明確指定了 contact points 卻沒設 local datacenter，建立 session 時會丟 IllegalStateException。完全沒給 contact points 時，driver 連本機 127.0.0.1:9042，並採用那個節點所在的 DC，這只適合開發環境。
  • builder 與設定檔都設了的話，以 builder 為準。
  • 名稱要和叢集回報的 DC 名稱完全相同（nodetool status 輸出裡 Datacenter 那一行）。書在第 10 章談 DC 命名。

一次請求怎麼得到 query plan

先想想：local DC 裡持有某筆資料的 3 個 replica 全部當機，但 local DC 還有別的節點活著，plan 會剩下什麼？

plan 裡仍有 local DC 其他活著的節點，它們還是能當 coordinator；遠端 DC 的節點不會補進來。請求最後成不成功，要看 consistency level。例如 LOCAL_QUORUM 在 local DC 沒有足夠的活 replica 時會失敗，這正是下面「舊版 DC-aware policy 的取捨」在談的場景。

  1. 請求進來，向 policy 要一份 plandriver 呼叫 newQueryPlan()。依據是這個請求本身（是不是 prepared statement、能不能算出 partition key）和 policy 目前掌握的節點狀態。
  2. 過濾不在 local DC 的節點直接不納入；已知 down 或已移除的節點也不納入。節點狀態靠上線、下線、新增、移除的通知隨時更新。
  3. 排序書交代了兩個行為：用 PreparedStatement 時，policy 靠 partition key 的 token 選出持有資料的 replica，減少經手的節點；一般情況則以輪轉分攤，連續的請求不會總落在同一個節點。這兩者在 plan 裡怎麼接合（replica 排前面，其餘 local 節點輪轉接在後面）是手冊的描述，書沒有寫，見下方補充。
  4. 取用driver 照順序取節點：第一個節點收到請求，後面的是備案，只有在需要時才會輪到。
  5. 之後的事重試與推測執行都需要「另一個節點」。備案從哪裡來，是接下來兩小節要釐清的事。

token awareness 的前提：driver 得拿到 routing 資訊

  • 要算 token，需要 routing keyspace 與 routing key（partition key 的值）。BoundStatement 的 keyspace 一定有，routing key 只在 partition key 的每個欄位都已經綁值時才有。
  • SimpleStatement 不會自動算 routing 資訊，除非你自己呼叫 setRoutingKeyspace() 與 setRoutingKey()（或直接給 token）。
  • 沒有 routing 資訊時，plan 退化成對 local 連線中節點的輪轉打散。有 routing 資訊時，local 的 replica 排最前面（彼此順序隨機），其餘 local 節點接在後面。
  • token 對應 replica 要靠 driver 載入的 token map，見 Metadata 一節。

換句話說，書說的「使用 PreparedStatement 時」是常見情境，但 token awareness 真正的條件是「driver 算得出 routing 資訊」。

與舊版 DC-aware policy 的取捨

書的描述是：query plan 先放 local 節點，後面接上 remote DC 的節點，設計意圖是可靠度的保險，本地 replica 全掛時請求還有地方可去。（3.x 要不要真的帶遠端節點，取決於一個參數，見下方補充。）

query plan 只含 local DC 的節點，不會自動補上遠端節點。

作者的解釋是：local DC 的 replica 全部不可用時，現實中通常是整個 data center 層級的大故障。這時悄悄把流量導向別的節點，實務上會帶來副作用，而且出事後很難追查流量為什麼跑到那裡。所以 4.x 選擇放棄自動的跨 DC 容錯，換取行為可預期。

3.x 的 DCAwareRoundRobinPolicy 預設其實也不帶遠端節點

  • 3.x 的 DCAwareRoundRobinPolicy 用 builder 建立，其中 withUsedHostsPerRemoteDc(n) 指定「每個遠端 DC 最多取用幾個節點」，沒呼叫就是 0。0 的意思是遠端節點全部被當成 ignored，query plan 裡只有 local 節點，預設根本不會跨 DC。要把遠端節點接在尾端，得自己把 n 設成大於 0。
  • 設成大於 0 之後，遠端節點排在所有 local 節點之後。而且對 DC-local 的 consistency level（LOCAL_ONE、LOCAL_QUORUM 這類），policy 預設不會跳去遠端；要開還得另外呼叫 allowRemoteDCsForLocalConsistencyLevel()。這兩個 builder 方法在 3.x 的 Javadoc 都標了 deprecated，註解說這項功能會在下一個大版本移除。
  • 所以書描述的「先 local 再 remote」是這個 policy 能做到的事，不是預設行為。4.x 拿掉的是這個要自己開的跨 DC 補位功能，和「預設行為改變」有出入。

依據是 3.x 的 DCAwareRoundRobinPolicy 原始碼與 Javadoc；書沒有談這個參數。下方模擬器的「3.x 對照」模式把遠端節點數預設放在 3，只是為了示範，真實的預設是 0。

擴充第二個 data center 之前先處理 client

書在第 10 章提醒：要把 keyspace 的 replication 擴充到新 DC 之前，先確認既有的 client 已經把原本那個 DC 指定為 local DC，並重新檢視 LOCAL_* 與 EACH_* consistency level 的用法。這就是 local DC 設定在營運上的意義：叢集多了一個 DC，coordinator 的挑選也不該跟著漂移。

失敗重試與重連（Retrying failed queries）

節點失效時，driver 的反應可以拆成三層。書把它們放在同一小節，分開看比較清楚。

自動換節點
節點失敗或連不上時，driver 自動且透明地改試其他節點，應用程式不用自己寫迴圈。
背景重連
被判定失效的節點，driver 會依 reconnection policy 排程在背景重新連線，設定在 advanced.reconnection-policy。書列了兩種內建：ExponentialReconnectionPolicy 與 ConstantReconnectionPolicy。
重試政策
暫時性的網路狀況也會讓節點看起來離線，所以對因協定或網路相關錯誤而失敗的查詢，driver 另有重試機制，client 程式碼不必再寫重試邏輯。具體怎麼重試，由 RetryPolicy 決定。

RetryPolicy 的介面

driver 依 RetryPolicy 介面的實作決定怎麼重試。介面上每個回呼對應一種失敗情境：

回呼觸發的情境
onReadTimeout()查詢以 ReadTimeoutException 失敗
onWriteTimeout()查詢以 WriteTimeoutException 失敗
onUnavailable()查詢以 UnavailableException 失敗
onErrorResponse()其他可恢復的伺服器錯誤
onRequestAborted()driver 在伺服器回應之前就中止了請求

這些回呼回傳 RetryDecision，告訴 driver 要不要重試。決定不重試時，例外可以被重新丟出（rethrow），也可以被忽略；忽略的話，查詢操作會回傳一個空的 ResultSet。覆寫實作的設定鍵是 advanced.retry-policy。

一個請求出錯時，driver 怎麼決定

  1. 選節點、拿連線從 query plan 取出第一個節點並向它借連線。節點已被判定失效、借不到連線時，driver 直接改試 plan 的下一個節點，應用程式看不到這一步。
  2. 送出並等待結果有三種：成功就結束；節點回了錯誤回應；或連線在回應之前出問題，請求被 driver 中止。
  3. 找對應的回呼讀取逾時、寫入逾時、不夠的活 replica 各有專屬回呼；其他錯誤走 onErrorResponse()；請求被中止走 onRequestAborted()。
  4. policy 做決定回呼收到錯誤的細節，回傳重試、rethrow 或 ignore。
  5. 執行決定重試就再送一次，rethrow 就把例外交給呼叫端，ignore 就回傳空的 ResultSet。（整段過程受 basic.request.timeout 約束，這點書沒寫，出處見前面「timeout 的真正範圍」那個補充框。）

4.x 的 RetryDecision，以及三個例外各自代表什麼

  • 4.x 的 RetryDecision 是列舉，值有 RETRY_SAME（同一個節點再試）、RETRY_NEXT（換 query plan 的下一個節點）、RETHROW、IGNORE。這個列舉本身不帶 consistency level 參數；書上「at what consistency level」是 3.x 的殘影（3.x 的決定可以指定新的 consistency level）。後續 4.x 版本的變化見 書後更新。
  • ReadTimeoutException、WriteTimeoutException、UnavailableException 都是 coordinator 回傳的伺服器端錯誤。前兩個表示 coordinator 已經向 replica 發了請求，但在它自己的逾時內沒收到足夠的回應；UnavailableException 表示 coordinator 根據自己對叢集狀態的認知，判斷活著的 replica 不夠，請求根本沒發出去。
  • client 端的逾時（DriverTimeoutException，由 basic.request.timeout 觸發）不在上面那五個回呼的清單內，不會交給 policy 決定。
  • 每個回呼都會收到這個請求已重試的次數（retryCount）。預設 policy 的 onReadTimeout、onWriteTimeout、onUnavailable 靠它做到「最多重試一次」；onRequestAborted 與 onErrorResponse 的預設實作不看這個次數。

回呼拿到的資訊，與預設政策的決定

下面是 4.x 的 DefaultRetryPolicy，也就是書說的那個唯一內建實作。「依據什麼資訊」這個問題的答案，就在每個回呼的參數裡：

  • onReadTimeout 拿到 consistency level、需要的回應數（blockFor）、實際收到的回應數（received）、有沒有收到資料（dataPresent）。預設：只有在「回應數已足夠，但沒有人帶回資料」時，對同一節點重試一次，其他情況 rethrow。
  • onWriteTimeout 拿到 consistency level、寫入型別（writeType）、blockFor、received。預設：只有型別是 BATCH_LOG（logged batch 先寫 batch log 那一步）時，對同一節點重試一次，其他 rethrow。
  • onUnavailable 拿到 consistency level、需要的 replica 數與活著的 replica 數。預設：換下一個節點重試一次，之後 rethrow。直覺是另一個 coordinator 對叢集狀態的看法可能不同。
  • onRequestAborted 預設：連線在中途被關閉（ClosedConnectionException）或 heartbeat 失敗（HeartbeatException）時，換下一個節點重試；其他情況 rethrow。
  • onErrorResponse 預設：讀寫失敗（ReadFailureException、WriteFailureException）rethrow；節點過載、伺服器內部錯誤、truncate 錯誤這類，換下一個節點重試。

依據是 4.x 的 retries 手冊。

重試不是免費的午餐：非 idempotent 的操作

這一節本身沒有提 idempotence，但書在第 4 章的 counter 一帶有一個警告框，講的正是重試的風險：counter 的增減不是 idempotent，網路失敗後 client 不知道第一次有沒有成功，重試的結果就不可預期；書說另一個非 idempotent 的 CQL 操作是對 list 附加元素。書沒有把這個警告和 driver 的自動重試連起來；兩者怎麼接上，是下面那個補充框（出自 driver 手冊）的內容。

driver 怎麼知道一個語句能不能重來

  • 預設值：basic.request.default-idempotence 是 false，也就是沒標記的語句一律當成非 idempotent。單一語句可用 Statement.setIdempotent() 或 StatementBuilder.setIdempotence() 標記；PreparedStatement 的標記會帶到由它產生的 BoundStatement。手冊還說 Query Builder 會嘗試自動推斷。
  • 在 DefaultRetryPolicy 的五個回呼裡，onWriteTimeout、onRequestAborted、onErrorResponse 只對 idempotent 語句才會被呼叫；非 idempotent 時 driver 繞過 policy，直接 rethrow。onUnavailable 與 onReadTimeout 手冊沒有提這個條件。
  • 「送出前就失敗」（借不到連線，例如節點 down 或連線池飽和）是 driver 內建規則：不問 policy，直接換 plan 的下一個節點。這一步不涉及 idempotence，因為請求根本還沒送出。

依據是 retries 與 idempotence 兩份 4.x 手冊。

為什麼 4.0 不再附 DowngradingConsistencyRetryPolicy

3.x 以前有兩個內建 policy：FallthroughRetryPolicy 從不建議重試；DowngradingConsistencyRetryPolicy 在重試時降低所需的 consistency level，想辦法讓查詢成功。4.0 起只剩一個依最佳實務設計的實作。

書對降級版本的批評是一句反問：既然特定情況下你能接受較低的 consistency level，平常堅持較高等級的理由是什麼？

重連策略的預設值

4.x 預設用 ExponentialReconnectionPolicy：base-delay 1 秒，每次失敗後延遲加倍，直到 max-delay 60 秒為止。ConstantReconnectionPolicy 則是固定間隔。重試與推測執行的次數在 node 層級各有對應的 metrics，見 除錯與監控。

Speculative execution（推測執行）

重試是失敗之後才動作的機制。但真實系統常常等不起：等一次逾時要好幾秒，coordinator 一次長時間的 GC 暫停也一樣讓人乾等。speculative execution 的想法是不等失敗：如果原本那個 coordinator 在預定的時間內還沒回，driver 就搶先對另一個 coordinator 再發一次同樣的查詢。先回來的結果交給呼叫端，其餘還在進行的就取消。

  1. t = 0照 query plan 把請求送給第一個節點 A，同時啟動長度為 delay 的計時。
  2. t = delay（例如 50 ms）A 還沒回應。driver 不取消 A，同時把同一個查詢送給另一個節點 B，這是第二次 execution。
  3. t = 2 × delay（100 ms）A 與 B 都還沒回，就再送給 C，這是第三次 execution。到達 max-executions 的上限就不再增加。
  4. 任一個回來最先到的回應成為這次 execute() 的結果，其餘 execution 被取消。
NoSpeculativeExecutionPolicy
預設值，永遠不啟動額外的 execution。也就是說，推測執行預設是關的。
ConstantSpeculativeExecutionPolicy
啟用推測執行要選它。兩個參數：max-executions（最多幾次 execution）與 delay（相鄰兩次 execution 之間的固定間隔，書以毫秒為例）。
自訂 policy
實作 SpeculativeExecutionPolicy 介面（套件 com.datastax.oss.driver.api.core.specex）。設定鍵位於 advanced.speculative-execution-policy。

參數的精確語意，以及一個書沒提的前提：idempotent

  • max-executions 計入最初那一次：設 3 代表原本的一次加最多兩次推測，下限是 1。delay 設 0 表示所有 execution 同時送出；小於 1 毫秒的精度會被捨去。
  • 推測執行只會發生在 idempotent 的語句上。basic.request.default-idempotence 預設是 false，所以只改 policy 而不標記語句，等於什麼都沒開。原因很直接：兩個節點可能都把寫入套用了，非 idempotent 的操作會被做兩次。書在這一節完全沒提這個條件。

「取消」的真正意思，與代價

  • Cassandra 的協定沒有取消進行中請求的機制。書說的「取消其餘查詢」，意思是 driver 不再理會之後才到的回應；節點端仍會把那次查詢做完。
  • 額外的 execution 就是額外的叢集負載。有多少請求會多送一次，取決於 delay 落在正常延遲分佈的哪裡。依百分位的定義，設在 p99 約 1% 的請求會超過它而多送一份，設在中位數約一半會（這是我的換算，手冊沒寫數字）。手冊建議在健康的叢集上量測，用高百分位（例如 p99.9）的延遲當 delay，並依額外流量調整連線池與叢集容量。
  • 被取消的請求在回應回來之前，仍占用連線上的 stream id（見下一節的連線池），推測執行用得多的話要留意。
  • 整個過程仍在 basic.request.timeout 這個全域上限之內，所以 delay × (max-executions − 1) 要明顯小於 timeout，否則後面的 execution 還沒來得及發出，呼叫就已經逾時。

叢集整體變慢時的連鎖效應

推測執行的觸發條件看的是時間（外加語句要是 idempotent），和叢集健不健康無關。當整個叢集都變慢（例如 compaction 壓力、跨區網路退化），幾乎每個請求都會超過 delay，額外負載會隨之放大（max-executions 設 2 時最多約多一倍，設得越大，上限越高），而叢集正是最撐不住的時候。這是我依機制推出的風險，不是手冊的原話；因此 delay 與 max-executions 值得搭配 metrics 監控，並用 execution profile 只對少數延遲敏感的查詢啟用。

三種機制：什麼時間點、依據什麼、做什麼決定

  • Load balancing：每個請求開始時。依據是請求本身的資訊（算不算得出 partition key 的 token）、節點的 up 與 down 狀態、local DC 設定。決定是一份有順序的候補節點清單。
  • Retry：請求已經送出，收到錯誤，或連線在回應前出問題時。依據是錯誤的種類與回呼拿到的細節。決定是重試（同一節點或換節點）、rethrow 或 ignore。
  • Speculative execution：請求送出後，一段固定時間內什麼都沒收到時。依據是時間（delay）與已發出的 execution 數（max-executions），不看有沒有錯誤。決定是再多發一次 execution。書沒提的前提是語句必須標成 idempotent（見上面的補充）。

前兩者是被動反應，第三個是主動搶先；三者各有各的設定鍵，彼此獨立。

書沒明說：三者共用同一份 query plan

retry 說「換節點」、speculative execution 說「另一個 coordinator」，這個「另一個」從哪裡來，書上沒有講。4.x 的做法是：一次請求只向 policy 要一份 plan，這個請求底下所有 execution 共用它，每次需要新節點就往下取。於是：

  • retry 的 RETRY_NEXT 取 plan 的下一個節點；RETRY_SAME 則留在原節點。
  • speculative execution 開出的新 execution 同樣取下一個節點，同一個請求的每個節點至多服務一次 execution。
  • 各個 execution 各自獨立計算自己的重試次數。
  • plan 的長度就是換節點這類備援的深度：local DC 只有 3 個節點，這個請求最多只會換到 3 個不同節點，而且永遠不會跨到遠端 DC。

依據是 retries 與 speculative execution 兩份 4.x 手冊。

下面的時間軸模擬器把 retry 與 speculative execution 放在同一條時間線上，每次嘗試畫成一條橫條。一開始載入的是「n1 很慢，推測執行救場」：看額外的 execution 在什麼時間點發出、誰先回來；接著把「statement 是 idempotent」關掉，確認推測執行消失；再用每個節點的下拉選單換不同的錯誤種類，對照上面預設重試政策的描述，看每種錯誤會得到什麼決定，上方的情境按鈕可以一鍵跳到幾個典型案例；最後把 request timeout 拉短，看整個請求如何被全域上限截斷。決策紀錄的編號和時間軸上的標記互相對應。節點的行為與耗時都是你設定的固定值，不是真實叢集的量測。

連線池（Connection pooling）

先抓住一個概念：native protocol 是非同步的，請求不必排隊等前一個回應，所以一條連線可以同時載著很多個請求。能載多少取決於協定版本，v2 是 128，v3 之後拉高到 32,768。載量這麼大，每個節點就用不著開很多條連線，driver 預設每個節點只開一條。

項目數值在哪裡調
協定允許的同時請求數（每條連線）v2：128；v3 以後：32,768協定本身的上限，driver 另有較低的預設限制
每個節點的連線數1advanced.connection，local 與 remote 節點各有設定
driver 允許的同時請求數（每條連線）1,024advanced.connection

4.x 的 driver 和先前版本不同，不會依負載自動增減連線數。想調整就改設定檔，下一次設定重新載入時套用。heartbeat 則是 driver 自己的保活機制，避免連線被中間的網路設備過早關閉。

128 與 32,768 從哪來：stream id

每個請求在 frame header 裡帶一個 stream id，回應照樣帶回同一個 id，所以同一條連線上的回應可以亂序返回。v2 以前 stream id 只有 1 個 byte，只能容納 128 個；v3 起放寬到 2 個 byte，上限是 32,768（max-requests-per-connection 必須小於它）。

預設 1,024 離協定上限很遠。手冊的說法是，調高到 1,024 以上沒有明顯好處，因為伺服器一次本來就只處理得了那麼多；調低也不建議，想限制整體流量請改用 throttler。

連線池與 load balancing、重試的關聯

  • 每個「已連線」的節點有一個連線池。被 policy 設為 IGNORED 的節點沒有連線池。
  • advanced.connection.pool.remote.size 只有在 policy 把某些節點回報成 REMOTE 時才用得到。預設 policy 只回報 local 與 ignored（手冊說這個行為可以改，例如前面提到的 dc-failover 選項），所以這個鍵在預設設定下實質上沒有作用。pool.local.size 與 pool.remote.size 預設都是 1。
  • 節點的連線池飽和、借不到連線時，driver 會直接換 plan 的下一個節點（上一節提過的內建規則）。
  • 池大小可以在執行期改設定檔，driver 會偵測並套用；heartbeat 的新值則只套用到之後才建立的連線。heartbeat 的運作方式是：連線閒置超過 interval 沒收到資料，就送一個假請求，失敗的話這條連線被丟棄並重建。

heartbeat 要比路徑上最短的閒置逾時更短

heartbeat 存在的理由是中間設備（防火牆、NAT、負載平衡器）會把閒置太久的連線悄悄關掉。所以調整時的判斷方式很單純：先弄清楚你的網路路徑上最短的閒置逾時是多少，再讓 heartbeat 間隔明顯比它短。預設的 30 秒對多數環境夠用；在雲端或 Kubernetes 裡如果路徑上有更短的閒置逾時，就需要調小。

Protocol version

driver 與節點之間講的是 CQL native protocol，這個協定有好幾個版本。書的說法是 Cassandra 4.0 使用 protocol v5，3.x 系列支援 v4。預設情況下，driver 在建立連線時自己協商版本，連新舊混用的叢集也能正確處理。要強制指定，就設 advanced.protocol.version。

協商到底怎麼進行

  1. 對第一個連上的節點，從 driver 支援的最高版本開始試，被拒就往下退一級。
  2. 連上之後，driver 去查 system.peers，得知其他節點的 Cassandra 版本，推算每個節點最高能講的 protocol 版本。
  3. 取全叢集的最小值。如果比目前連線用的版本低，就關掉第一條連線，用較低的版本重開，其餘連線也都用這個版本。
  4. 版本一旦選定，session 存活期間不會再變。

強制版本就跳過協商：設得比節點支援的高，會得到 UnsupportedProtocolVersionException（包在 AllNodesFailedException 裡）。設定值區分大小寫，要寫 V4 這種形式。滾動升級期間手冊建議不要強制版本，讓協商去處理新舊混用的階段。

書內的一處出入：4.0 到底用 v5 還是 v4

書在第 3 章貼了 Cassandra 4.0-alpha3 的啟動 log，其中一行寫著支援的 native protocol 版本是 v3、v4、v5-beta，預設 v4。對照這一節說的「4.0 使用 v5」，兩處說法並不一致：那份 log 裡 v5 還掛著 beta 標記，預設也是 v4，所以「4.0 使用 v5」是簡化過的講法。driver 這邊，v5 的 beta 標記到 4.11.0 才拿掉（changelog），目前手冊的對照表則寫 Cassandra 4.x 協商到 v5。協定版本在後續 4.x 的演變見 書後更新。

Compression

driver 可以依 native protocol 支援的壓縮選項，把 client 與節點之間的訊息壓縮。好處是省網路頻寬，代價是 client 與 server 兩端都要多花 CPU。目前有兩種演算法：LZ4 與 SNAPPY，預設是 NONE，用 advanced.protocol.compression 設定。

什麼時候值得開

書給的是一個取捨：壓縮省網路頻寬，代價是 client 與 server 兩邊多用 CPU。所以判斷標準就落在這兩種資源哪一個比較吃緊；沒有量測過瓶頸在哪，就別預設開比較好。

設定值與額外相依

  • 手冊中值寫成小寫的 lz4、snappy（或 none）。壓縮的是請求與回應的 body。
  • 這兩個壓縮函式庫在 driver 裡是 optional 相依，要自己加進專案：LZ4 用 lz4-java，Snappy 用 org.xerial.snappy:snappy-java。lz4-java 的 groupId 隨 driver 版本改過，以你用的 driver 版本的 pom 為準。缺函式庫時的行為我沒查到。
  • 壓縮必須在開 session 之前決定，執行期不能改。手冊稱 LZ4 是不錯的首選。

Driver 安全（認證與加密）

壓縮之後，書用一小節交代 driver 的安全機制。認證是可抽換的：可以做單純的帳號密碼登入，也可以接其他認證系統。預設不做任何認證。

選認證提供者有兩條路：把實作 AuthProvider 介面的物件（例如 PlainTextAuthProvider）交給 CqlSessionBuilder.withAuthProvider()，或在設定檔寫 advanced.auth-provider 區段。如果只是帳號密碼，用 CqlSessionBuilder.withAuthCredentials() 就會設好 PlainTextAuthProvider。

加密方面，書說 client 與 server 之間的加密選項由各節點在 cassandra.yaml 指定，並說 driver 會遵守各節點指定的加密設定。認證、授權、加密從 client 與 server 兩邊的完整做法，書留到第 14 章。

書上關於加密的說法不完整：client 端要自己明確設定 TLS

書說 driver 遵守各節點在 cassandra.yaml 指定的加密設定，聽起來像是 driver 會自動配合節點。實際上 4.x 的 driver 不會從節點得知要不要用 TLS，client 端要自己明確設定：在設定檔寫 advanced.ssl-engine-factory（class 通常是 DefaultSslEngineFactory，並附上 truststore 等參數），或在 builder 呼叫 withSslEngineFactory()、withSslContext()。參考檔寫明沒有這個設定就不啟用 SSL。結果是：節點若要求加密連線，沒有設定 TLS 的 driver 連不上。

另外，advanced.auth-provider 底下一定要有 class，沒有就不做認證（參考檔明寫）。第 14 章的設定檔範例只列了 username 與 password 兩行，讀到時請對照這一點。第 14 章的文字還把 builder 的帳號密碼方法寫成 withCredentials()，但它的程式碼範例和本章一樣用 withAuthCredentials()；withCredentials() 只在較新的 4.x 版本以已棄用的別名存在，4.4.0 的 SessionBuilder 裡沒有它。

Execution profiles

有些設定值可以在單一 Statement 上覆寫，但很多不行。如果同一個應用程式裡，某些查詢適合一組設定、另一些查詢適合另一組，該怎麼辦？driver 的答案是 execution profile：一組有名字的設定值，作為預設設定之上的疊加層（overlay），套用到個別 statement。哪些選項可以放進 profile，書要你去查參考設定檔。

  1. 載入設定檔頂層的 basic、advanced 構成預設設定；profiles 底下每個名字是一組覆寫。
  2. 指名statement 上用 setExecutionProfileName("名字") 指定要用哪個 profile。
  3. 解析driver 取某個選項的值時，先看該 profile 有沒有寫；沒寫的選項沿用預設設定的值。
  4. 繼承用 CqlSession.prepare() 把帶有 profile 的 SimpleStatement 變成 PreparedStatement，之後由它產生的每個 BoundStatement 都繼承這個 profile。SimpleStatementBuilder 也有同名的 setExecutionProfileName()。

書上套用 profile 的那個範例在 4.x 不會生效

書的範例對 statement 變數呼叫 setExecutionProfileName 之後，沒有把回傳值接起來（搜尋關鍵字：execution profiles、setExecutionProfileName）。4.x 內建的 statement 都是 immutable，所有 setter 回傳的是新的實例（方法標了 @CheckReturnValue）。原物件沒有被改，照書的寫法，profile 其實沒有套上去，而且不會有任何錯誤訊息。

另外 statement 還有 setExecutionProfile(DriverExecutionProfile)，可以套用在程式裡動態衍生出來的 profile 物件。

哪些選項能放進 profile

參考設定檔裡每個選項都標了「Overridable in a profile」是或否。依我讀到的 4.x 參考檔：

  • 可以：basic.request.*（timeout、consistency、page-size、default-idempotence）、advanced.retry-policy、advanced.speculative-execution-policy、basic.load-balancing-policy。
  • 不行（屬於整個 session 層級）：basic.config-reload-interval、advanced.reconnection-policy、advanced.connection.*、advanced.heartbeat、advanced.protocol.*、advanced.ssl-engine-factory、advanced.auth-provider。

這也呼應了本節前面的所有機制：重試、推測執行、load balancing 可以依 profile 各別設定，連線池、協定、認證不行。上面範例裡的 fast_read 就是只對延遲敏感的唯讀查詢開啟推測執行，其他查詢不受影響。

怎麼規劃 profile：以請求類別為單位

這是我的建議，書沒有講。與其讓逾時和 consistency 的數字散落在各個 DAO 裡，不如依請求的性質取幾個 profile 名字，例如一般線上讀寫、後台報表、延遲敏感的唯讀查詢。程式碼只表達「這是哪一類請求」，數字集中在設定檔，調整時不用改程式。profile 太多反而難以理解，通常三五個就夠。

  • Load balancing policy 回答兩個問題：節點的遠近分類，以及這次請求的 query plan 順序；另外接收節點上下線的通知。4.0 起只有一個有主見的預設 policy：輪轉、搭配 prepared statement 的 token awareness、只含 local DC 的節點。
  • local DC 必須設定。與舊版 DC-aware policy 相比，4.x 不再自動在 plan 尾端補遠端節點，作者的理由是本地 replica 全掛通常是整個 DC 的大故障，悄悄跨 DC 導流副作用多又難除錯。書外補充：3.x 該 policy 的遠端節點數預設是 0，要自己設成大於 0 才會補。
  • 節點失效有三層反應：自動換節點、依 reconnection policy 的背景重連、以及 RetryPolicy 針對讀寫逾時、unavailable、其他錯誤回應與請求中止做出重試、rethrow 或 ignore 的決定。4.0 只留一個依最佳實務設計的實作，不再附降級重試。
  • 重試和推測執行都會把請求重做一次。書在這節沒談 idempotence，只在第 4 章對 counter 有警告。書外補充（driver 手冊）：對非 idempotent 的語句，寫入逾時不會交給重試政策，也不會被推測執行。
  • Speculative execution 預設關閉：原 coordinator 超過 delay 沒回就向另一個節點多開一次 execution，先回的勝出。書外補充：這會增加叢集負載，而且只對標成 idempotent 的語句生效。
  • 書外補充：load balancing、retry、speculative execution 共用同一份 query plan。plan 決定了備援能找誰、能找多深，而且不會跨出 local DC。
  • 連線池靠協定的非同步多工讓一條連線承載許多請求，所以預設每節點只要一條；heartbeat 保護閒置連線；協定版本預設自動協商；壓縮是用 CPU 換頻寬。Execution profile 是預設設定之上的具名覆寫層，沒寫的選項繼承預設值。

Metadata · p.306

Metadata

driver 對叢集的所有認知都放在 CqlSession.getMetadata() 回傳的 Metadata 裡：有哪些節點、各節點是 up 還是 down、每個 keyspace 與 table 長什麼樣子。這份資料由 driver 自己維護。你可以讀它的快照，也可以註冊 listener，在變化發生時收通知。

getMetadata() 給你什麼

CqlSession.getMetadata() 回傳實作 com.datastax.oss.driver.api.core.metadata.Metadata 的物件。書上強調它是叢集在某個時間點的快照，內容分三類：

  • 叢集裡的節點，以及每個節點目前的狀態。
  • 每個節點分到的 token。
  • schema，也就是 keyspace 與 table 的描述。

這一節書上依序講 node discovery、schema access，最後順帶介紹 SchemaBuilder 與一個關於識別字大小寫的提示框。token 這一類書上只點到名，沒有展開。

「快照」在 4.x 的意思

書中未提細節。依 4.1 手冊與原始碼：Metadata 本身不可變，driver 發現叢集有變化後，下一次呼叫 getMetadata() 才會給你一份新的副本。所以不要把某次拿到的 Metadata 存起來當成永遠最新。例如先取 Metadata、再執行 CREATE TABLE，手上那份舊的不會有新表。token 的部分是 getTokenMap()，回傳 Optional<TokenMap>，並且與同一份 Metadata 裡的節點、schema 保持一致。

唯一的例外是 Node 物件。它是可變的，你抓著同一個 Node 參照，欄位會隨 driver 的認知即時更新。

Node discovery：從一個 contact point 認識整個叢集

你在 CqlSession.builder() 只給了一兩個 contact point，卻能在 getMetadata() 裡看到全部節點。這是靠 control connection 做到的。

  1. 連上入口build 時 driver 連上你設定的 contact point 之一，細節見連線到叢集。
  2. 留下一條 control connection書上說 session 會對第一個連上的節點維持一條 control connection，專門用來掌握叢集的狀態與拓撲。
  3. 讀出節點清單透過這條連線，driver 查出叢集目前有哪些節點，每個節點成為 metadata 裡的一個 Node 物件。
  4. 持續維護節點加入、離開、上線、下線時，metadata 跟著更新，你註冊的 listener 也會被呼叫。這些狀態變化同樣會寫進 driver 的 log（見除錯與監控）。

contact point 只是入口

書在連線一節說 driver 連上其中一個 contact point 取得叢集的 metadata，又建議正式環境給多個 contact point，以免其中一個剛好停機。把兩句合起來看，contact point 的作用只是讓 driver 有地方進門。進門之後節點清單來自 control connection，不需要把整個叢集的節點都列進設定。這是我從兩句話合併出的推論，書沒有直接這樣寫。

先想想：contact point 只給了 dc1 的節點，driver 看得到 dc2 的節點嗎？

看得到。節點清單來自整個叢集，不受 contact point 所在的 data center 限制。但看得到不代表會送請求過去：書上說預設的 load balancing policy 只把 local data center 的節點放進 query plan，所以 dc2 的節點會在 metadata 裡，卻不會被選為 coordinator。這部分機制在Driver 設定。

每個 Node 帶著什麼

書中只提到用 Node.getState() 看節點狀態。下表整理 4.1.0 的 Node 介面（原始碼與 Javadoc）上的主要方法。

方法內容

getEndPoint()driver 用來連這個節點的位址

書說 Metadata.getNodes() 回傳 Node 的 list。4.1.0 的原始碼簽名是 Map<UUID, Node>，key 是 host id，所以走訪節點要用 getNodes().values()。Javadoc 還說明這個 Map 可能包含目前被視為 down、或被 load balancing policy 忽略的節點。

節點狀態與 NodeStateListener

書上說可以用 Node.getState() 讀單一節點的狀態，也可以實作 NodeStateListener，在節點被加入、被移除、上線或下線時收到 callback。

NodeState 的四種值

書中只說 up 與 down。4.1.0 的 NodeState 有四個值：

  • UP：driver 對它至少有一條活著的連線；或它被 policy 忽略、不主動連線，但收到過「它已上線」的拓撲事件。
  • DOWN：driver 失去對它的所有連線並正在重連；或被忽略的節點收到「它已下線」的事件。
  • FORCED_DOWN：被外部強制標為下線，driver 永遠不會重連。典型情形是 contact point 填錯，連到一個不屬於這個叢集的位址。
  • UNKNOWN：從未嘗試連線，也沒收過任何事件。

手冊另外提到 driver 對「假的 DOWN 通知」有耐性。例如 gossip 因為節點之間的網路問題判定某節點掛了，但 driver 自己還連得上，這個節點在 driver 眼中仍是 UP。

書沒說怎麼註冊 NodeStateListener

書提到要「註冊」實作，卻沒給方法。4.1.0 有兩條路，擇一即可：builder 的 withNodeStateListener()，或設定檔的 advanced.node-state-listener.class（用程式碼註冊時，設定檔的值會被忽略）。介面有四個方法：onAdd、onUp、onDown、onRemove。只想處理其中幾個，就繼承 NodeStateListenerBase，它的方法都是空的。

  • callback 由 driver 內部執行緒呼叫，Javadoc 要求執行時間要短。要做阻塞或耗時的事，請丟到你自己的執行緒。
  • onDown 在節點變成 DOWN 或 FORCED_DOWN 時都會被呼叫。
  • onAdd 不會對初始化時給的 contact point 觸發，只對第一次連線後完整刷新節點清單時新發現的節點觸發。

control connection 的後續行為

依 4.1 手冊，control connection 做三件事：查詢 system 資料表以掌握拓撲與 schema、執行 schema agreement 檢查、接收伺服器主動推送的拓撲與 schema 事件。如果它所在的節點掛了，driver 會走 reconnection 流程去找另一個節點接手，策略沿用 advanced.reconnection-policy，挑節點的順序來自 load balancing policy 的 query plan。

它獨立於一般連線池，只做管理請求，但會算進該節點的 getOpenConnections()。例如池大小設 2，擔任 control 的那個節點會顯示 3 條連線。

Schema access

Metadata 也提供 keyspace 與 table 的描述，讓程式在執行期查得到 schema。跟著 schema 一起來的問題是：叢集裡的 schema 版本會隨著 keyspace 與 table 的建立、修改、刪除而改變，而這個「改變」並不是瞬間發生在所有節點上。

為什麼 schema 會暫時不一致

第 2 章講過 Cassandra 的最終一致性。書上的論證很直接：schema 資訊本身也存在 Cassandra 裡，所以它同樣只是最終一致。你對某個 coordinator 下了 DDL，變更需要時間傳到其他節點，傳完之前，不同節點持有不同版本的 schema 是正常現象。

DDL 後立刻查詢可能打到「還不知道這張表」的節點

由上面的機制可以推得：剛建好的表，如果下一個請求被路由到還沒收到變更的節點，那個節點對這張表一無所知。這是從書中機制做的推論，書沒有舉出實際的錯誤訊息。（書外補充：4.1 手冊的 schema 一節有張圖畫的就是這個情境，節點回報該表尚未設定。）

driver 的防呆：schema agreement

書上說 driver 內部有檢查 schema agreement 的保護機制，用意就是避開上面那個問題。所謂 agreement，是叢集內各節點回報的 schema 版本一致。

檢查發生的時間點：書與 4.1 手冊的說法不同

書的措辭是 driver 在「發起」會改 schema 的 statement 之前先檢查 agreement。4.1.0 的 Session.checkSchemaAgreementAsync() Javadoc 與 schema 手冊描述的時間點是：schema 刷新之前，以及一個成功的 schema 變更查詢完成之前。也就是 DDL 在 coordinator 上成功後，driver 才去等所有節點一致，再把結果交給你的程式。上圖照後者畫。兩種說法目的相同，但以原始碼文件為準。

  • 怎麼檢查：查 system 資料表，取得目前 UP 的每個節點的 schema 版本，全部相同才算一致，否則定期重試，直到逾時。
  • 設定鍵在 advanced.control-connection.schema-agreement 底下：interval 預設 200 毫秒，timeout 預設 10 秒（設為 0 表示跳過檢查，且一定視為失敗），warn-on-failure 預設 true。
  • 逾時不是致命錯誤。session.execute(...) 照樣回傳，你可以用 rs.getExecutionInfo().isSchemaInAgreement() 得知結果，或隨時呼叫 session.checkSchemaAgreement() 主動確認。
  • 混合版本的叢集（例如滾動升級中）永遠無法達成 agreement，因為 schema 版本的算法隨伺服器版本而異。

讀 schema 時留意 Metadata 是不是舊的

DDL 之後要查新表，記得重新呼叫 session.getMetadata()，不要沿用 DDL 之前拿到的 Metadata 變數。快照的特性見本節開頭。

SchemaChangeListener：等通知，不用輪詢

書上的註冊方式有兩種：建立 session 時在 builder 呼叫 withSchemaChangeListener()，或在設定檔使用 advanced.schema-change-listener。實作的介面是 com.datastax.oss.driver.api.core.metadata.schema.SchemaChangeListener。

介面長什麼樣

4.1.0 的 SchemaChangeListener 對 keyspace、table、user-defined type、function、aggregate、view 六類物件，各有 onXxxCreated、onXxxDropped、onXxxUpdated 三個方法（Updated 會同時給你變更前後兩份 metadata）。同樣有空實作的 SchemaChangeListenerBase，同樣由 driver 內部執行緒呼叫，要求執行時間短。

設定檔的完整鍵是 advanced.schema-change-listener.class，書上寫的是省略 .class 的形式。書出版後 listener 可註冊多個，設定鍵也跟著改，見書後更新。

讀 schema 之外，Java driver 還能幫你寫 schema。SchemaBuilder 跟 QueryBuilder 同在 com.datastax.oss.driver.api.querybuilder package，用 fluent API 產生 CREATE、ALTER、DROP 的 statement，對象涵蓋 keyspace、table、index 與 user-defined type。

提示框：大小寫敏感的識別字與 CqlIdentifier

MANAGING CASE-SENSITIVE IDENTIFIERS WITH THE JAVA DRIVER

CQL 允許用雙引號建立大小寫敏感的 keyspace、table、column 名稱，只是不建議這樣做。為了簡化這件事，Java driver 在 schema 相關 API 裡用 CqlIdentifier 包裝所有識別字。如果你寫的程式要操作 schema，書建議也用它。接受識別字的 API 同時支援 String 與 CqlIdentifier 兩種參數。

書上這個提示框第一句與前文矛盾

提示框開頭說「CQL 預設是大小寫敏感的」，但緊接著的下一句又說要加雙引號才能建立大小寫敏感的名稱，兩者互相衝突。書的第 3 章 cqlsh 小節有個「Using snake case」提示框，講的是反過來的事實：Cassandra 預設把名稱當小寫處理，混合大小寫的名稱會被存成全小寫，要用雙引號才能保留。CqlIdentifier 的 Javadoc 也寫明未加引號時不分大小寫。正確的說法是「預設不分大小寫，加雙引號才分」。

為什麼需要這個包裝類別？因為同一個名稱有兩種寫法，混用就出事。CqlIdentifier 把兩種形式分開存放：

CQL 形式
你在 CQL 裡會打的樣子。不加雙引號就不分大小寫，會被轉成小寫；加了雙引號則保留原樣。含特殊字元或撞到 CQL 關鍵字的名稱一定要加雙引號。
內部形式
名稱在 Cassandra 系統資料表裡實際存的字串，大小寫精確，沒有引號。

傳 String 時 driver 其實幫你呼叫了 fromCql

書說 API 兩種參數都接受，但沒說兩者的行為差異。依 4.1.0 原始碼，接受 String 的方法（例如 SchemaBuilder.createTable(String, String)、Metadata.getKeyspace(String)）內部都是先 CqlIdentifier.fromCql(...)。所以傳 "Reservation" 會被轉成小寫的 reservation。要處理一個用雙引號建立的 "Reservation" keyspace，要嘛自己建 CqlIdentifier.fromInternal("Reservation")，要嘛傳入帶著雙引號的字串。

最省事的做法：名稱一律 snake_case 小寫

書在 Object Mapper 一節也推薦小寫加底線的命名慣例。只要名稱全部是小寫 snake_case，String 與 CqlIdentifier 的差異就不會咬到你。需要處理大小寫敏感名稱時，才特地用 CqlIdentifier 明確表達。

這一節只涵蓋書出版當時的行為。例如 system 類 keyspace 在較新版本預設不再出現在 getKeyspaces()，這類變化集中在書後更新。

  • getMetadata() 給的是快照，內含節點、token、schema。要看最新狀態就重新呼叫，不要長期持有舊的 Metadata。
  • node discovery 靠 session 對第一個連上的節點維持的 control connection。contact point 只是入口，節點清單由此取得，書提到的狀態與 listener 事件也由此而來。
  • NodeStateListener 接 add、remove、up、down 事件。書沒說怎麼註冊，4.1 是 withNodeStateListener() 或 advanced.node-state-listener.class。
  • schema 存在 Cassandra 自己裡面，所以最終一致，不同節點可能暫時版本不同。driver 以 schema agreement 檢查防呆，SchemaChangeListener 讓你在變更發生時被通知。
  • SchemaBuilder 的 build() 產出 statement，不會自己送出。書中範例的 partition key 那行漏了右引號。
  • CqlIdentifier 區分 CQL 形式與內部形式。String 參數走 fromCql，預設不分大小寫。書中提示框的「預設大小寫敏感」是筆誤。

Logback 怎麼找設定檔

書上說 Logback 能為測試與正式環境各自指定設定。它找設定檔的順序是：

  1. 先找 logback-test.xml在 classpath 上找到就用它，這是測試用的設定。
  2. 找不到才找 logback.xml也就是一般（正式）設定。
先想想：同一份程式，測試時想看 DEBUG，正式環境只想看 INFO，要怎麼做？

只在測試用的 resources 目錄放一份 logback-test.xml，把 driver 的 logger 調到 DEBUG；正式環境用的 logback.xml 維持 INFO。跑測試時 classpath 上兩個檔案都在，但 Logback 先找到 logback-test.xml 就不再往下找。

logback-test.xml 不要進到正式的 artifact

這是由查找順序直接推得的結論：只要 classpath 上有 logback-test.xml，logback.xml 就永遠不會被讀。如果測試設定被打包進正式的 jar，正式環境的 log 層級會悄悄由它決定。

書上特別註明：v4 的 driver 預設不開 JMX reporting（v3 預設是開的），但可以設定。由這個差異可以推得，從 v3 搬到 v4 的專案若原本靠 JMX 看 driver 指標，升級後這些 MBean 會消失，要重新啟用。

所有指標預設都是關的，JMX 要自己接線

書只說 JMX「可以設定」。依 4.1 手冊與 reference.conf，實際情況更嚴格：

  • 不只 JMX，連每一個指標預設都關閉。要在設定檔 advanced.metrics.session.enabled 與 advanced.metrics.node.enabled 這兩個清單裡列出名稱才會收集。
  • 全部關閉時，CqlSession.getMetrics() 回傳 Optional.empty()，所以程式要處理沒有值的情況。
  • JMX 沒有內建開關。要加上 Dropwizard 的 metrics-jmx 依賴，拿 getMetrics() 裡的 MetricRegistry，自己建一個 JmxReporter 並啟動。
  • 指標名稱以 session-name 開頭，node 層級再加 nodes 與位址，例如 s0.nodes.127_0_0_1:9042.pool.open-connections。

書出版後 metrics 的實作又有變動（例如可選 Micrometer），見書後更新。

Python

DataStax Python Driver 2014 年推出。在它之前的 Pycassa 是建在 Cassandra 舊 Thrift 介面上的 client，Thrift 後來被移除，Pycassa 也跟著失去維護，這個 driver 接手成為主要的 Python 選擇。書上說它支援 Python 2.7，以及 Python 3.4 以上的 3.x 版本。

JDBC 與 ODBC

ODBC（Open Database Connectivity）是 Microsoft 制定的標準，讓應用程式用 SQL 存取資料。JDBC（Java Database Connectivity）是 Java 的 API，在 java.sql package 裡提供 SQL 抽象。Cassandra 的 JDBC 與 ODBC driver 由廠商提供，書上點名 Simba 與 Progress Software。

第 5 章的相關提醒：確認工具真的懂 CQL

第 5 章介紹資料建模工具時有個提示框，提醒有些號稱支援 Cassandra 的 IDE 與工具，其實沒有原生支援 CQL，只是透過 JDBC 或 ODBC，把 Cassandra 當成有 SQL 的關聯式資料庫來操作。選工具時要確認它支援 CQL，而且會強化 Cassandra 的資料建模最佳實務。這一節的 JDBC 與 ODBC，就是那個提示框背後的通道。

章首拿 JDBC 當類比：JDBC 的 Statement、PreparedStatement、ResultSet 這組抽象，在 Java driver 裡都有對應的概念，書也說 CQL 的簡單與熟悉語法，讓寫 client 的方式接近傳統資料庫 driver。所以用 DataStax Java driver 的應用，沒有理由再繞一層 JDBC。這個結論是我的判斷。

書沒有講它由誰維護。書的 Summary 把可選的 driver 分成「DataStax 的」與「社群的」兩類，而 GoCQL 的名稱前沒有 DataStax，所以應該屬於社群 driver。這是我從書中措辭推出的歸類，書上沒有直接這樣寫。

四種查詢寫法怎麼選

書依序介紹了字串與 SimpleStatement、PreparedStatement、Query Builder、Object Mapper。這四種是不同抽象層級的工具，可以在同一個專案並存：越往後，你手寫的 CQL 越少，driver 替你做的事越多。

寫法每次執行送出什麼適合要留意
字串與 SimpleStatement 查詢字串，加上分開的參數值 臨時查詢、DDL、只跑一兩次的動作 值要走參數，不要用字串拼接，否則易錯且有 injection 風險。書說預設 policy 在使用 PreparedStatement 時，會依 partition key 挑出 replica
PreparedStatement statement 識別碼加參數值，查詢結構只在 prepare 時送過一次 反覆執行的查詢，也就是每個 access pattern 它不是 Statement 的子型別，要 bind() 成 BoundStatement 才能執行。每個 access pattern 準備一個並重複使用，不要每個請求都重新 prepare。放在啟動時做是本導讀的建議（書外）
Query Builder build() 得到 SimpleStatement；也可以 prepare(build()) 走 prepared 路徑 查詢結構會變，例如有可選的條件 要另外加 java-driver-query-builder。要 prepare 的話用 bindMarker()；用 literal() 會讓查詢文字隨值而變，不適合 prepare（書外，見 Query Builder 一節）
Object Mapper DAO 的方法替你 build 並執行 statement 已有 domain model，想少寫對應程式碼 編譯期要有 processor，執行期要有 runtime。mapper 與 DAO 包著你的 CqlSession，要像 session 一樣重用

挑選時依序問三件事。查詢是不是只跑一兩次？是的話 SimpleStatement 最省事。不是的話，查詢結構固定嗎？固定就 prepare 一次、反覆 bind；會變就用 Query Builder 組出各種結構。最後，如果專案已經有成形的 domain model，再考慮把整套包進 Object Mapper。

Object Mapper 底下其實也是 prepared statement（書中未提）

書只說 DAO 會替你 build 並執行 statement。依 4.x 的 mapper 手冊與產生碼的原始碼，DAO 實作在初始化時就把各方法要用的查詢 prepare 好，之後每次呼叫只做 bind 再交給 CqlSession 執行。所以前面講的「prepare 一次、反覆 bind」，Object Mapper 替你做了，代價是 DAO 要像 session 一樣建一次重複使用，不該在每個請求裡重新取得。

依據：driver 4.x 手冊 Mapper 頁，以及 mapper-processor 產生 DAO 實作的原始碼。

一個請求從頭走到尾

把整章串成一條線。下面追蹤 Reservation Service 查一筆訂房，每一步連到講它的小節。

  1. 啟動連線。CqlSession.builder() 加上 contact points 與 local datacenter，driver 連到第一個可用的節點，之後透過這條連線掌握整個叢集的狀態與拓撲，並替每個要用的節點建立連線池。見連線到叢集與 Metadata。
  2. prepare。把查詢結構送給一個節點，換回 statement 識別碼，driver 接著在其他節點也 prepare。每個 access pattern 做一次，建議放在服務啟動時（書外建議）。見 Statements。
  3. bind。每個請求用識別碼加參數值組出 BoundStatement。查詢結構要變化時，改由 Query Builder 組出各種結構，或交給 Object Mapper 的 DAO 代勞。
  4. 挑節點。預設的 load balancing policy 為這次請求排出 query plan：只含本地資料中心的節點，用 prepared statement 時優先排持有資料的 replica，其餘輪流。見 Driver 設定。
  5. 送出。請求走池裡的連線，native protocol 是非同步的，同一條連線可以同時有很多請求在飛。呼叫端用 execute() 就等著，用 executeAsync() 就拿到 CompletionStage 先去做別的事。見非同步執行。
  6. 遇到狀況。節點連不上，driver 試 query plan 的下一個節點並排程重連；伺服器回報可恢復的錯誤，交給 RetryPolicy 決定；節點遲遲沒回應，若啟用了 speculative execution，driver 對另一個節點再送一份。見 Driver 設定。
  7. 收結果。結果依 basic.request.page-size 分頁取回。同步呼叫直接拿 ResultSet，非同步則在 stage 完成時處理。
  8. 事後觀測。log 記錄 driver 的決策與節點狀態，metrics 記錄逾時、重試、連線數的趨勢，metadata 讓程式查節點與 schema。見除錯與監控。

書中名稱與 4.x 實際 API 的對照

讀書、對照原始碼時最容易被絆到的，是書中少數名稱沿用了 3.x，或有筆誤。下面集中列出，各小節的書外補充 note 有更多細節。

勘誤與名稱對照（書中未提）

  • 所有 contact point 都連不上時，書說丟 NoHostAvailableException。那是 3.x 的類別，4.x 的 build() 丟 AllNodesFailedException。
  • 指定 local datacenter 的 builder 方法是 withLocalDatacenter()（書中有一處寫成大寫 C 的 withLocalDataCenter()）。明確指定了 contact points 卻沒設 local datacenter，建立 session 時會丟 IllegalStateException。
  • 書描述 load balancing policy 時提到 distance() 與 HostDistance，這是 3.x 的名稱。4.x 是 NodeDistance，由 policy 透過 DistanceReporter 回報。
  • 書說舊版 DCAwareRoundRobinPolicy 會把遠端節點排在本地節點之後。依 3.x 原始碼，遠端節點的數量由 usedHostsPerRemoteDc 決定，預設是 0，也就是預設不含任何遠端節點，要設成大於 0 才有書描述的行為。
  • 4.x 的預設值：basic.request.timeout 為 2 秒、basic.request.consistency 為 LOCAL_ONE、basic.request.page-size 為 5000、連線 heartbeat 為 30 秒。
  • Metadata.getNodes() 回傳的是以 host id 為鍵的 Map，書說是 list。
  • 書給的設定鍵 advanced.schema-change-listener，完整形式要以 .class 結尾。NodeStateListener 的設定鍵書沒給，4.1 是 advanced.node-state-listener.class。
  • 書的 SchemaBuilder 範例少了一個結尾引號。書說「CQL 預設區分大小寫」也和第 3 章及 CqlIdentifier 的文件矛盾，沒加引號的識別字會被轉成小寫。
  • 書的第 8 章範例有時把主鍵欄寫成 confirmation_number，第 5 章的 schema 是 confirm_number。本導讀統一用後者。

2020 年之後的版本變化，例如 Maven groupId、Micrometer、protocol v5，一律集中在書後變化一節。

對大型專案的實際影響是：改 pom 的 groupId 與版本，不用動 import。要留意傳遞依賴。Spring Data Cassandra 到 4.3 才把依賴改成新座標，更舊的版本拉進來的還是 com.datastax.oss。兩個座標的 jar 帶有相同 package 的類別，Maven 不會把它們當成同一個依賴來仲裁。這一段是我根據 Maven 的座標比對規則做的推論，沒有實際建置驗證，所以請用 mvn dependency:tree 確認 classpath 上只有一份 driver。

來源：pom.xml @ 4.17.0、pom.xml @ 4.18.0、CEP-8、DataStax Java driver matrix、Spring Data Cassandra 4.0 到 4.3 遷移指南。

連線：例外類別、local datacenter 與啟動行為

第 8 章的連線一節有兩個說法需要處理，另有一個書沒提、但會在 K8s 上碰到的設定。

NoHostAvailableException 在 4.x 不存在（勘誤，把握度：高）

書說 contact points 全部不可用時會丟 NoHostAvailableException。那是 3.x 的類別（com.datastax.driver.core.exceptions），4.x 的 api.core 裡沒有。4.x 的路徑是：

  1. 逐一嘗試session 初始化時，ControlConnection 依 query plan 一個個嘗試節點。
  2. 收集錯誤全部失敗後丟出 AllNodesFailedException.fromErrors(errors)。初始連線的這個例外會被改寫訊息，開頭是 "Could not reach any contact point, make sure you've provided valid addresses"。
  3. 原樣丟出build() 內部呼叫 CompletableFutures.getUninterruptibly。遇到 DriverException 就丟出它的副本，遇到非受檢例外就原樣丟出。呼叫端看到的就是 AllNodesFailedException。

這三步是讀原始碼得到的。4.1.0 tag 的 ControlConnection 已經是同樣的寫法，所以書出版時就是如此，不是後來才改。NoNodeAvailableException 是 AllNodesFailedException 的子類別，表示一個節點都沒嘗試過，例如 query plan 是空的。4.14.0 起，「所有連線都忙」也改成丟 AllNodesFailedException，不再是 NoNodeAvailableException。

驗證失敗的部分：ControlConnection.isAuthFailure 會檢查 AllNodesFailedException.getAllErrors() 裡是否全是 AuthenticationException，並記一則 "Authentication errors encountered on all contact points" 的警告。由此推得書上的 AuthenticationException 在 session 初始化時是包在 AllNodesFailedException 裡的。這是讀程式碼的推論，我沒有對開了驗證的叢集實際跑過。

來源：ControlConnection.java（4.1.0 版）、AllNodesFailedException.java、NoNodeAvailableException.java、CompletableFutures.java、upgrade guide 的 4.14.0。

advanced.reconnect-on-init：書未提的補充（把握度：高）

預設情況下，叢集連不上時 build() 立刻失敗。4.0.0 起可以設 advanced.reconnect-on-init = true，driver 會依 reconnection policy 週期性重試，直到至少一個 contact point 回應。build()（或 buildAsync() 回傳的 future）在那之前不會完成，所以 session 在連上之前拿不到。當 driver 所在的 Pod 可能比 Cassandra 先起來時，這個選項可以取代自己寫重試迴圈。

來源：manual: reconnection、upgrade guide 的 4.0.0、reference.conf。

沒設 local datacenter 會丟 IllegalStateException，規則沒有放寬（把握度：高）

書的範例都有設 local DC，但沒說沒設會怎樣。4.x 分支的 MandatoryLocalDcHelper 的行為是：沒設 local DC、又有明確的 contact point，就丟 IllegalStateException，訊息開頭是 "Since you provided explicit contact points, the local DC must be explicitly set"，後面列出目前的 contact points 與叢集裡的 DC。它是非受檢例外，所以 build() 原樣丟出。唯一的例外是完全沒給 contact point：driver 連 127.0.0.1:9042，採用該節點的 DC。4.1.0 的 DefaultLoadBalancingPolicy 已有同樣規則，訊息文字較舊。

替代 policy 方面，DcInferringLoadBalancingPolicy 與 BasicLoadBalancingPolicy 的原始檔最早出現在 4.3.0 tag（4.2.2 沒有）。changelog 4.3.0 的 JAVA-2459「Improve extensibility of existing load balancing policies」應是對應的改動，這個對應是我的推測。手冊對它們的定位是：前者會從 contact points 推斷 local DC，推斷不出來就在初始化時報錯，主要給 ETL 工具，不建議一般應用使用。後者是唯一能在沒有 local DC 時運作的 policy，不分資料中心地挑節點，可能造成跨資料中心流量暴增，只適合當自訂 policy 的起點。所以書上「一定要指定 local DC」在實務上仍然成立。

另有一個小筆誤：書在負載平衡段落把方法寫成 withLocalDataCenter()，實際是 withLocalDatacenter()（小寫 c）。

來源：MandatoryLocalDcHelper.java、DefaultLoadBalancingPolicy.java @ 4.1.0、manual: load balancing、manual: core、changelog。

Driver 設定：負載平衡、重試與預設值

預設 policy 多了 slow replica avoidance，cross-DC failover 回來了但預設關閉（書後變化，把握度：高）

書把預設 policy 概括成 round robin、token aware、只用本地資料中心。後兩者仍然成立，差異在細節：

  • 4.4.0 起（DSE driver 併入主 driver 時），原本只有 DSE 才有的 slow replica avoidance 併進 DefaultLoadBalancingPolicy，預設開啟，由 basic.load-balancing-policy.slow-replica-avoidance 控制。reference.conf 的說明是：有路由資訊時 replica 一律排在 query plan 前面；開啟時再依各 replica 的回應速度與 uptime 排序，關閉時只是隨機打散。所以用「round robin」描述有路由資訊的 prepared statement，已經不精確。
  • 4.10.0 起可以選擇開啟 cross-datacenter failover：advanced.load-balancing-policy.dc-failover.max-nodes-per-remote-dc 預設 0，也就是關閉。設為正數時，每個遠端 DC 會有那麼多個節點被指派 REMOTE distance 並進入 query plan。使用 LOCAL_* 一致性等級時預設仍不 failover（allow-for-local-consistency-levels = false），原因是各 DC 的 RF 可能不同，LOCAL_QUORUM 的意義會跟著變。4.18.1 起可用 preferred-remote-dcs 指定遠端 DC 的順序。
  • 官方手冊的立場沒有變：它仍認為資料中心整個掛掉多半是區域性災難，應該在應用層或基礎設施層處理 failover，這個選項是「因應需求而回歸」。書中說遠端 failover 在實務上有副作用，與手冊的警告一致。

來源：upgrade guide 的 4.4.0 與 4.10.0、manual: load balancing、reference.conf、changelog 的 JAVA-2899 與 JAVA-3142。

LoadBalancingPolicy 沒有 distance()，類別叫 NodeDistance（勘誤，把握度：高）

書說每個 policy 要提供 distance() 並回傳 HostDistance。那是 3.x 的介面。4.1.0 和現在的 LoadBalancingPolicy 都沒有 distance()，HostDistance 這個類別在 4.x 也不存在。policy 在 init(nodes, distanceReporter) 與節點事件裡呼叫 DistanceReporter.setDistance(node, NodeDistance) 回報距離，NodeDistance 有 LOCAL、REMOTE、IGNORED。4.11.0 起內建 policy 接受 NodeDistanceEvaluator，取代舊的 node filter，SessionBuilder.withNodeFilter 系列方法已 deprecated。

來源：LoadBalancingPolicy.java、upgrade guide 的 4.11.0。

RetryPolicy 多了回傳 RetryVerdict 的方法（書後變化，把握度：高）

書描述 onReadTimeout()、onWriteTimeout()、onUnavailable()、onErrorResponse()、onRequestAborted() 回傳 RetryDecision。4.10.0 起這五個方法標為 deprecated，新增對應的 onReadTimeoutVerdict() 等方法，回傳 RetryVerdict，可以在重試前改寫請求。原始碼裡，*Verdict 是 default 方法，預設實作會呼叫舊方法，所以舊的自訂 policy 不用改。想在重試時改寫請求才需要覆寫 *Verdict。舊方法在介面上仍是抽象方法，upgrade guide 說會在下個大版本移除。

另外，3.x 的 DowngradingConsistencyRetryPolicy 在 4.10.0 以 ConsistencyDowngradingRetryPolicy 的名稱回歸。reference.conf 把它列為 DefaultRetryPolicy 之外的第二個內建選項，並註明要小心使用。書提到的「降級一致性是否合理」的疑慮，官方並沒有改變預設。

來源：RetryPolicy.java、upgrade guide 的 4.10.0、reference.conf。

Protocol v5：從 beta 變成預設（書後變化，把握度：高）

書說 Cassandra 4.0 用 protocol v5，driver 會自動協商。寫書時 driver 4.1 的手冊有一則註腳：Cassandra 4 尚未發布，v5 還是 beta，必須明確啟用，自動協商的結果是 v4。4.10.0 的手冊還有同樣的註腳。4.11.0 起 v5 移除 beta 標記（JAVA-2704），upgrade guide 寫明連 Cassandra 4.0 時會自動選 v5。現在的手冊對照表寫 Cassandra 4.x 協商為 v5，driver 支援 v3 到 v5。手冊列出的 v5 實質差異有兩項：per-query keyspace，以及 schema 變動時 prepared statement 更有韌性。

由這些文件可以推論：4.11 之前的 driver 連 Cassandra 4.x 實際跑的是 v4。這是我從文件推得的，沒有逐版本比對協商程式碼。

來源：manual: native protocol @ 4.1.0、同一頁現行版、upgrade guide 的 4.11.0。

壓縮用的 LZ4 函式庫座標變了（書後變化，把握度：中）

書只說 advanced.protocol.compression 可以選 LZ4 或 SNAPPY。driver 對壓縮函式庫是 optional 依賴，要自己宣告。reference.conf 在 4.19.2 仍寫 lz4 需要 net.jpountz.lz4:lz4，到 4.19.3 改成 at.yawk.lz4:lz4-java，同一版 changelog 有「CASSJAVA-113: Bump LZ4 to 1.10.1」。把握度中的原因：我只看到設定檔註解與 changelog，沒有確認舊座標在 4.19.3 之後是否仍能被載入。

來源：reference.conf @ 4.19.2、reference.conf @ 4.19.3、changelog。

非同步、reactive 與 metrics

Reactive：書上的版本是對的（把握度：高）

書說 4.4 起內建 reactive 支援，CqlSession 繼承 ReactiveSession。4.3.0 的 tag 沒有 ReactiveSession，4.4.0 有，且 4.4.0 的 CqlSession 引用了它。upgrade guide 對 Apache Cassandra 使用者的說明是「reactive execution is now available for everyone」。方法是 executeReactive(String) 與 executeReactive(Statement<?>)，回傳 ReactiveResultSet，也就是一個 Publisher。

書沒提的補充：這些型別的 package 帶有 dse（com.datastax.dse.driver.api.core.cql.reactive），手冊說這是歷史因素，對一般 Cassandra 同樣可用。classpath 上要有 Reactive Streams API。預設的 publisher 是 cold、只允許單一訂閱者，而且可能在 driver 的 I/O 執行緒上發出元素，所以 onNext 裡不要做阻塞或重運算。

來源：upgrade guide 的 4.4.0、manual: reactive、CqlSession.java @ 4.4.0。

Metrics：多了 Micrometer 與 MicroProfile（書後變化，把握度：高）

書描述的是 Dropwizard。4.8.0 起 driver 內建三套綁定：Dropwizard（預設）、Micrometer、MicroProfile Metrics。後兩者是獨立模組 java-driver-metrics-micrometer 與 java-driver-metrics-microprofile（4.7.2 的 tag 沒有，4.8.0 有）。選擇方式是 advanced.metrics.factory.class。用 Spring Boot 的人通常會選 Micrometer。

  • 預設的 DefaultMetricsFactory 在 classpath 上有 Dropwizard 時用 Dropwizard，沒有就靜默關閉 metrics。如果你把 Dropwizard 排除了卻忘了指定 factory，結果是沒有 metrics，也沒有錯誤。
  • 所有 metric 預設關閉，要在 advanced.metrics.session.enabled 與 advanced.metrics.node.enabled 列出名稱才會收集。
  • 書提到的 CqlSession.getMetrics() 只在 Dropwizard 下可用。用其他函式庫時呼叫它，手冊說會在執行期丟 NoClassDefFoundError。要程式化存取，改用 CqlSessionBuilder.withMetricRegistry(...) 傳入自己的 registry。Micrometer 沒傳 registry 時，driver 用 Micrometer 的 globalRegistry。
  • 4.11.0 起 advanced.metrics.id-generator.class 可選 TaggingMetricIdGenerator，產生「名稱加標籤」的識別。upgrade guide 說這種格式匯出到 Prometheus 或 Graphite 時比較好看。
  • JMX：手冊說 JMX 沒有內建，要自己加 metrics-jmx 並建立 JmxReporter，沒有設定開關。4.1.0 的手冊就是這樣寫，所以不算書後變化，但書上「disabled by default but can be configured」的說法容易讓人去找一個不存在的開關。

來源：manual: metrics、reference.conf 的 advanced.metrics、changelog 的 JAVA-2808 與 JAVA-2872、upgrade guide 的 4.11.0、metrics/micrometer/pom.xml @ 4.8.0。

Metadata

system 類 keyspace 預設不在 Metadata.getKeyspaces() 裡（書後變化，把握度：高）

4.10.0（JAVA-2871）起，system、所有 system_ 開頭的 keyspace，以及 DSE 專用的 keyspace，預設被排除在 metadata 與 token map 的計算之外。它們不會出現在 Metadata.getKeyspaces()，TokenMap 對它們回傳空的 replica 與 token range。要恢復的話，修改 advanced.metadata.schema.refreshed-keyspaces，它的預設值是 ["!system", "!/^system_.*/", "!/^dse_.*/", "!solr_admin", "!OpsCenter"]。書的 schema access 一節沒有針對這點的範例，但列出 keyspace 的程式在 4.10 前後輸出會不同。

來源：upgrade guide 的 4.10.0、reference.conf。

Listener 可以註冊多個，設定鍵改成 .classes（書後變化，把握度：高）

書說用 withSchemaChangeListener() 或 advanced.schema-change-listener 註冊 SchemaChangeListener。4.13.0（JAVA-2951）起，node state listener、schema change listener、request tracker 都可以註冊多個。程式化的新方法是 addSchemaChangeListener()。withSchemaChangeListener() 還在，但會取代先前註冊的 listener。設定檔方面，舊鍵 advanced.schema-change-listener.class 已標為 deprecated，新鍵是 advanced.schema-change-listener.classes，值是類別名稱的清單。SessionBuilder 的 Javadoc 把新鍵寫成 advanced.metadata.schema-change-listener.classes，與 DefaultDriverOption 和 reference.conf 不一致，請以後兩者為準。

來源：SessionBuilder.java、DefaultDriverOption.java、upgrade guide 的 4.13.0。

Query Builder 與 Object Mapper

artifact 名稱沒變，只有 groupId（把握度：高）

  • java-driver-query-builder 仍是獨立的 artifact，README 還特別提醒要自己加。java-driver-mapper-runtime 與 java-driver-mapper-processor 也沿用原名。
  • mapper 的 annotation 還在 com.datastax.oss.driver.api.mapper.annotations：我確認過 @Entity、@NamingStrategy、@PartitionKey、@Dao、@Mapper、@DaoFactory、@Select、@Insert、@Delete、@Query 的原始檔都在，NamingConvention.SNAKE_CASE_INSENSITIVE 也還在。
  • processor 的用法沒有重要變動。書說把 processor 加到 compile path。手冊對 Maven 的建議是 compiler plugin 的 annotationProcessorPaths，或把 processor 宣告成 provided scope，原因是 processor 只在編譯期需要。Gradle 用 annotationProcessor。這份建議在 4.1.0 與 4.4.0 的手冊裡就有，所以不算書後變化。
  • 陷阱：同一份手冊的 Gradle 範例在 4.x 分支上仍寫 group: 'com.datastax.oss'，沒有跟著改。照抄會抓到舊 groupId 的舊版 driver。
  • mapper 自 4.5.0 起會在初始化 DAO 時比對 entity 與資料表的 schema（changelog 的 JAVA-2263）。書的基準版本 4.1 到 4.4 沒有這項檢查，欄位名對不上時的表現與新版不同，Object Mapper 一節有說明。
  • 4.1.0 之後 mapper 新增的功能，changelog 可查：4.7.0 自訂回傳型別（JAVA-2792）、4.9.0 不可變 entity 與計數器（JAVA-2816、JAVA-2721）、4.11.0 Java Stream（JAVA-2830）、4.12.0 寬鬆模式的 @GetEntity 與 @SetEntity（JAVA-2935）。它們都沒有與書的內容衝突，這裡不展開。

來源：README、manual: mapper config、同一頁 @ 4.1.0、changelog、annotations 目錄。

相容性、Java 版本與 vector 型別（把握度：vector 高，Cassandra 5.x 中）

  • README 現行的說法：相容 Apache Cassandra 2.1 以上、DSE 4.7 以上，需要 Java 8 以上。
  • Java 17 在 4.17.0 起納入自動化測試。Java 21 在 4.19.1 的 changelog 有「Driver testing against Java 21」。
  • vector 型別（Cassandra 5.0 引入）：4.16.0 加入型別與 codec，4.17.0 調整 CqlVector 的 API，4.19.0 支援任意子型別，並讓 SchemaBuilder 與 QueryBuilder 支援 vector。
  • Cassandra 5.x：4.19.0 的 changelog 有「support new 5.0.x」，內容是把整合測試的目標版本更新到 5.0.x。4.19.1 修正了 Cassandra 5 的 table 設定。我沒有找到針對 5.0 之後版本的明確相容聲明，這是把握度中的原因。

其他語言的 driver

Spring Boot、舊 client 與 DataStax 公司

Spring Boot 仍建立在 CqlSession 之上，但不會讀 driver 的 application.conf（補充，把握度：高）

  • Spring Boot 的參考文件寫明可以注入自動設定的 CqlSession，屬性在 spring.cassandra.*。官方範例要求提供 keyspace-name、contact-points 與 local-datacenter，與第 8 章的連線一節一致。
  • Spring Data Cassandra 5.1.1 的文件寫它需要「Datastax Java Driver 4.0 or later」，範例是用 CqlSession.builder() 建立 session 後交給 CassandraTemplate。
  • 陷阱：driver 自己的 application.conf，Boot 預設不會去讀，要用 spring.cassandra.config 指定才會載入。同一個值兩邊都設時，spring.cassandra.* 優先。第 8 章建議的檔案式設定，在 Boot 專案裡要先搞清楚是誰在讀這個檔。進階客製可用 DriverConfigLoaderBuilderCustomizer 與 CqlSessionBuilderCustomizer 這兩種 bean。
  • 座標：Spring Data Cassandra 4.3 起，自己依賴的 driver 座標已換成 org.apache.cassandra。

來源：Spring Boot：NoSQL（Cassandra 一節，我開啟時頁首顯示 4.1.1）、Spring Data Cassandra：Getting Started（5.1.1）、4.0 到 4.3 遷移指南、spring-data-cassandra issue #1467。

Hector、Astyanax 與 Thrift（把握度：高；archived 旗標未確認）

  • Hector：README 開頭是 "THIS PROJECT IS NO LONGER ACTIVE"，指向官方 java-driver。最後一個 commit 是 2015-07-30。
  • Astyanax：README 說它已 retired、不再積極開發，可能只收依賴更新，建議改用 DataStax Java driver，並提醒要把 Thrift 查詢全部改成 CQL。最後一個 commit 是 2021-08-17，根目錄的 OSSMETADATA 寫 osslifecycle=archived。
  • GitHub 上的 archived 旗標我沒能確認。抓取頁面時沒看到橫幅，但這不足以證明沒有。所以這裡只說「已退役、無人維護」，不說「已封存」。
  • Thrift：Cassandra 4.0 的 NEWS.txt 寫明移除了 Thrift 介面，以及 start_rpc、rpc_port 等相關 yaml 選項，與書一致。
  • 與搬離 Hector 有關的補充：同一份 NEWS.txt 的 Compact Storage 一節說，4.0 起不支援 Thrift，而 COMPACT STORAGE 在 ALTER ... DROP COMPACT STORAGE 脫離實驗狀態後（文中說是 5.0 之後的大版本）也將不再支援。Thrift 時代建立的表很可能是 compact storage。第 8 章沒有談這件事。我只引用 NEWS 的說法，沒有查 5.x 的實際行為。

來源：hector-client/hector、Netflix/astyanax、Cassandra 4.0 NEWS.txt。

DataStax 與 IBM（把握度：中）

IBM 在 2025-02-25 公告有意收購 DataStax。業界媒體在 2025-05-28 報導交易完成，內容引述 DataStax 的說法。我沒有找到官方文件說明這件事是否改變 driver 文件的網址或 driver 的維護主體，所以不下結論。能確認的是：Java driver 從 4.18 與 3.12 起由 ASF 維護。因此書中以 DataStax 為 driver 維護者的描述，應換成「ASF 專案」。driver 的手冊與 API 文件目前仍掛在 docs.datastax.com，README 的 API docs 連結指向 4.17 的頁面。把握度中的原因是交易完成的日期來自媒體，不是 IBM 的公告。

如果你今天要開新專案或做遷移

第 8 章仍是可靠的概念地圖，需要調整的主要是座標、例外類別、幾個自訂介面，以及和 Spring Boot 的接合方式。

  • 一個長壽的 CqlSession，用 contact points 加 local datacenter 建立。
  • Simple、Prepared、Bound statement 的用法，以及 Query Builder 與 Object Mapper 的 API。package 與 annotation 沒變。
  • executeAsync 與 CompletionStage 的寫法。4.4 起的 reactive 也如書所述。
  • 書中出現的預設值：2 秒 timeout、LOCAL_ONE、page size 5000、每節點一條連線、30 秒 heartbeat、預設不做 speculative execution。
  • 檔案式設定與 execution profile 的概念，設定鍵的主要名稱沒有變。
  • Metadata 的節點與 schema 存取方式。
  • pom 的 groupId 改成 org.apache.cassandra。版本請到 Maven Central 查最新的 4.19.x。用 mvn dependency:tree 確認沒有殘留 com.datastax.oss。
  • 例外處理改抓 AllNodesFailedException。Pod 可能先於 Cassandra 啟動時，評估 advanced.reconnect-on-init。
  • 一定要設 local datacenter。Spring Boot 用 spring.cassandra.local-datacenter。
  • 自訂 load balancing policy 用 NodeDistance 與 DistanceReporter。想在重試時改寫請求的自訂 retry policy，覆寫 *Verdict 方法。
  • 決定要不要保留 slow replica avoidance（預設開），以及是否啟用 cross-DC failover（預設關）。
  • Spring Boot 通常選 Micrometer：設 factory.class，不要依賴 getMetrics()。
  • driver 4.11 以上連 Cassandra 4.x 會自動協商 v5，4.11 以前停在 v4。
  • Boot 專案裡 driver 的 application.conf 預設不會被讀。
  • 用 Metadata.getKeyspaces() 的程式要考慮 system keyspace 預設被排除。
  • 從 Hector 搬離時，確認 Thrift 時代建立的表是否是 compact storage。
  • 其他語言的 driver 改看上一節的現況表，例如 Python 支援的版本和 GoCQL 的 module 路徑。
